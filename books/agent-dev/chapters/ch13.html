13.1.2 为什么不是所有 Agent 都要 LangGraph？

LangGraph 不是所有 Agent 的最佳选择。先看决策：

场景推荐理由
单轮 LLM 调用直接 openai.chat()LangGraph 太重
简单 ReAct 循环LangChain LCEL + AgentExecutorLangGraph 状态机过度设计
多步骤 / 多分支 / 需审批LangGraph ✅显式状态 + 显式控制流 + checkpoint
多 Agent 协作（Supervisor / Crew）LangGraph ✅Supervisor 节点 + Worker 节点 = 天然图
跨组织 / 跨进程（用 MCP / A2A）LangGraph ✅图节点 = MCP/A2A 客户端
长流程（>10 步）/ Human-in-the-LoopLangGraph ✅Checkpoint + interrupt

经验法则：当 if-else 超过 3 层 或 步骤超过 5 步 → 上 LangGraph。

13.1.3 本章的 3 大核心抽象

抽象作用类比
State（状态）图的"内存"——所有节点读写同一份数据React 的 useState / Redux 的 store
Node（节点）图的"操作"——接收 state、返回新 state函数 f(state) -> state'
Edge（边）图的"控制流"——决定下一个节点是哪个工作流的箭头

一句话总结：LangGraph = 显式状态 + 显式控制流 = 可观测 + 可 checkpoint + 可可视化。

与 ch11 的对应关系（S5 修复）：

- State = ch11 模式的"共享数据"（如 messages、worker_results、iteration）

- Node = ch11 模式的"角色"（Supervisor / Worker / Researcher / Analyst / Scheduler）

- Edge = ch11 模式的"控制流"（Supervisor → Worker 委派、Worker → Supervisor 回报、Worker → END 终止）

- 区别：ch11 是模式概念（4 大协作模式），ch13 是LangGraph 代码实现（StateGraph + add_node + add_edge）。ch13 的图结构 = ch11 模式的 1:1 落地——读完 ch11 你知道"什么是 Supervisor 模式"，读完 ch13 你能"用 LangGraph 写一个 Supervisor"。

13.2 LangGraph 是什么

13.2.1 LangChain 团队的图编排框架

LangGraph 是 LangChain 团队在 2024 年推出的图编排框架——核心定位是"让 Agent 工作流显式化"。

核心理念：

把 Agent 工作流建模成有向图（Directed Graph）。节点 = 函数（做事情），边 = 控制流（决定下一步去哪），状态 = 全局共享字典（节点之间传数据）。

与 ch04 LangChain LCEL 对比：

维度LCEL（链式）LangGraph（图式）
抽象`promptllm
控制流线性任意图（含循环 / 分支 / 并行）
状态每步独立全局共享 State
适合场景简单链复杂 Agent
学习曲线低中

关键区别：LCEL 是链式（pipe |），LangGraph 是图式（节点 + 边）。LCEL 写 5 步以内的流程，LangGraph 写 5 步以上的 Agent。

13.3 State（状态）的设计

13.3.1 TypedDict 基础

from typing import TypedDict

class AgentState(TypedDict):
    messages: list       # 对话历史
    next_action: str     # 下一步动作
    iteration: int       # 循环计数

TypedDict 的作用：给状态字段加类型提示。不强制类型（运行时仍是 dict），但 IDE 自动补全 + 静态检查友好。

13.3.2 Annotated + Reducer 函数

问题：当多个节点都返回同一个字段时，怎么合并？默认是"覆盖"。

Reducer 函数定义合并策略：

from typing import Annotated
from operator import add

class AgentState(TypedDict):
    # 消息列表：所有节点返回的消息都追加（不覆盖）
    messages: Annotated[list, add]
    # 下一步：后写覆盖前写（默认行为）
    next_action: str

常见 Reducer：

Reducer作用场景
operator.add列表追加消息历史
operator.or_集合并集已访问节点集合
自定义 lambda x, y: x + y自定义合并累加器
自定义 lambda x, y: y强制覆盖（默认行为）单值字段

13.3.3 MessagesState（内置消息列表）

LangGraph 提供 MessagesState——预定义消息列表 + Reducer：

from langgraph.graph import MessagesState

# MessagesState 等价于：
# class MessagesState(TypedDict):
#     messages: Annotated[list[AnyMessage], add_messages]

# 使用
class State(MessagesState):
    next_action: str    # 在 MessagesState 基础上扩展

add_messages Reducer 内部会处理 4 件事：

  1. 新消息追加到列表
  2. 同 ID 的消息更新（不重复追加）—— 用于工具调用返回
  3. 自动转换 BaseMessage 子类（HumanMessage / AIMessage / ToolMessage）
  4. 跨节点消息 ID 追踪

13.3.4 Channel（高级：last_value / binary_operatoraggregate）

Channel 是 LangGraph 0.2 的高级特性——细粒度控制状态字段：

from langgraph.graph import StateGraph
from langgraph.channels import LastValue, BinaryOperatorAggregate

class State(TypedDict):
    x: int                              # 默认 LastValue
    log: Annotated[list[str], add]      # BinaryOperatorAggregate(add)
    current_node: Annotated[str, lambda old, new: new]  # LastValue

3 种 Channel 类型：

Channel行为用途
LastValue后写覆盖前写单值字段（默认）
BinaryOperatorAggregate(op)用 op(old, new) 合并列表 / 集合 / 累加
Topic广播到所有下游节点多路分发

绝大多数场景用 TypedDict + Annotated 就够，Channel 是高级优化。

13.3.5 Reducer 实战陷阱与修复（ch13 真实踩坑经验）

写 LangGraph 时最常见的 bug 都来自 Reducer 误用——本节列出 3 个真实坑 + 修复。

坑 1：消息列表被覆盖

# ❌ 错误：messages 字段没 Reducer，每次节点返回都覆盖
class State(TypedDict):
    messages: list  # 默认 LastValue 行为

def agent_node(state):
    return {"messages": [response]}  # 覆盖整个消息历史！

# ✅ 正确：加 Reducer 追加
def add_messages(old, new): return old + new

class State(TypedDict):
    messages: Annotated[list, add_messages]

踩坑信号：跑图后 state["messages"] 只有 1 条消息，丢失历史。

坑 2：Reducer 收到 default 值

# 节点 A 返回 {"field": [result]} → reducer 收到 [result]，追加
# 节点 B 返回 {"other_field": x}，没动 field → reducer 收到 default 值 []？
# 答：是的！reducer 总是被调用，参数 new 是 default 值（如果没有该字段）

# ✅ 修复：在 reducer 里检查 None / 空
def add_results(old, new):
    if not new:            # 处理 None / [] / 0
        return old
    if isinstance(new, list):
        return old + new
    return old + [new]

踩坑信号：节点没动列表，但列表里多出 [] 空元素（ch13 §13.7 Supervisor 实战真实遇到的坑）。

坑 3：Reducer 返回类型不一致

# ❌ 节点 A 返回 [result_a]，节点 B 返回 "string_b"
# reducer 收到 [result_a] → 追加
# reducer 收到 "string_b" → 如果 reducer 假设总是 list，会爆 TypeError

# ✅ 修复：reducer 必须接受任意类型
def safe_add(old, new):
    if new is None: return old
    return old + (new if isinstance(new, list) else [new])

修复效果（ch13 §13.7 Supervisor 实战）：从 worker_results = [结果1, [], 结果3]（中间被覆盖成空）变为 worker_results = [结果1, 结果2, 结果3]（按预期追加）。

13.3.6 Reducer 速查表

场景Reducer 写法用途
消息历史追加def add(o, n): return o + n聊天 / ReAct
累加计数Annotated[int, lambda o, n: o + n]iteration / token 计数
集合并集`Annotated[set, lambda o, n: o \n]`
单值覆盖不用 Annotated（默认 LastValue）next_action / status
最大值Annotated[int, lambda o, n: max(o, n)]最高置信度
最新覆盖但保留 N 步Annotated[list, lambda o, n: (o + n)[-10:]]滑动窗口

经验法则：只要字段是 list / set / 累加器，加 Reducer。

13.4 Node（节点）的实现

13.4.1 节点函数签名

def my_node(state: State) -> dict:
    """节点函数：接收 state，返回 state 的更新字段"""
    # 读 state
    user_msg = state["messages"][-1].content
    # ... 做点事 ...
    # 返回要更新的字段（不是整个 state）
    return {"messages": [response], "iteration": state["iteration"] + 1}

关键约定：

  • 输入：完整的 state（LangGraph 自动注入）
  • 输出：只返回要更新的字段（LangGraph 用 Reducer 合并）
  • 不要在节点里直接修改 state["x"]——那是 dict 引用，可能污染全局状态

13.4.2 同步 vs 异步节点

# 同步节点
def sync_node(state):
    result = call_llm_sync(state["messages"])
    return {"messages": [result]}

# 异步节点（用于 I/O 密集）
async def async_node(state):
    result = await call_llm_async(state["messages"])
    return {"messages": [result]}

# 图里混用同步 + 异步节点都可以
graph.add_node("sync", sync_node)
graph.add_node("async", async_node)

LangGraph 自动识别 async def——不需要额外配置。

13.4.3 节点内调用 LLM / 工具 / 其他 Agent

from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langgraph.prebuilt import ToolNode

llm = ChatOpenAI(model="gpt-4o")

@tool
def search_web(query: str) -> str:
    """搜索网页"""
    return f"搜索结果：{query}"

tools = [search_web]
llm_with_tools = llm.bind_tools(tools)

def llm_node(state: State) -> dict:
    """调用 LLM（已绑定工具）的节点"""
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

# 工具执行节点（LangGraph 预制）
tool_node = ToolNode(tools)

3 个常用预制组件（langgraph.prebuilt）：

组件作用
ToolNode(tools)自动执行工具调用 + 返回 ToolMessage
create_react_agent(llm, tools)一行创建 ReAct Agent
tools_condition条件边的内置函数：判断是否要调工具

13.4.4 节点内调用其他 Agent

# 子图作为节点
subgraph = build_research_subgraph()  # 另一个 StateGraph
graph.add_node("research_agent", subgraph.compile())

关键能力：图可以嵌套图——一个 LangGraph 节点可以是另一个 LangGraph 图（ch13 §13.8.1 会展开）。

13.5 Edge（边）的实现

13.5.1 4 种边

边类型API用途
普通边add_edge("A", "B")无条件从 A 到 B
条件边add_conditional_edges("A", path_func, path_map)根据 path_func 返回值决定下一节点
入口边add_edge(START, "A")从 START 到 A（图起点）
终点边add_edge("A", END)从 A 到 END（图终点）

13.5.2 条件边实战（ReAct 的核心）

from langgraph.graph import START, END

def should_continue(state: State) -> str:
    """条件函数：返回下一节点的名字"""
    last_message = state["messages"][-1]
    # 如果 LLM 调用了工具 → 调工具
    if last_message.tool_calls:
        return "tools"
    # 否则 → 结束
    return END

graph.add_conditional_edges(
    "agent",
    should_continue,
    {
        "tools": "tools",     # 返回 "tools" → 去 tools 节点
        END: END,             # 返回 END → 结束
    }
)
# 工具执行完回到 agent（形成循环）
graph.add_edge("tools", "agent")

这段代码是 ReAct Agent 的核心：

  1. LLM 节点调用 LLM
  2. 如果 LLM 决定调工具 → 去 tools 节点
  3. tools 节点执行工具
  4. 回到 LLM 节点（循环）
  5. 直到 LLM 不再调用工具 → END

13.5.3 入口边 + 终点边

# 入口边
graph.add_edge(START, "first_node")

# 终点边（也可以在条件边里返回 END）
graph.add_edge("last_node", END)

注意：START 和 END 是 LangGraph 内置常量——不是字符串字面量。

13.5.4 循环边（递归调用）

循环边 = 节点 A → 节点 A 或 节点 A → 节点 B → 节点 A。

ReAct Agent 就是循环边：

  • agent → tools → agent → tools → ... → END
  • 终止条件：LLM 不再 tool_calls

防无限循环：用 state 里的计数器 + 终止条件：

def should_continue(state):
    if state["iteration"] > 10:    # 超过 10 次迭代 → 终止
        return END
    if state["messages"][-1].tool_calls:
        return "tools"
    return END

13.6 完整实战：搭建 LangGraph ReAct Agent

13.6.1 mock LLM 跑通版（无需任何外部包）

# langgraph_react_mock.py
# LangGraph ReAct Agent — mock LLM 演示版（已实测跑通）
# 运行：python3 langgraph_react_mock.py
# 真实使用：pip install langgraph==0.2.* langchain-openai

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END

# Reducer：消息列表追加（重要！不加的话每次节点返回 messages 都会覆盖整个列表）
def add_messages(old: list, new: list) -> list:
    """消息列表 Reducer：old + new"""
    return old + new

# ===== 1. State =====
class State(TypedDict):
    # 必须用 Annotated + Reducer，否则 LangGraph 默认后写覆盖，丢失历史消息
    messages: Annotated[list, add_messages]
    iteration: Annotated[int, lambda old, new: old + new]

# ===== 2. 工具 =====
def get_weather(city: str) -> str:
    return f"{city}天气：晴，25°C"

def send_reminder(content: str) -> str:
    return f"已加入日历：{content}"

TOOLS = {"get_weather": get_weather, "send_reminder": send_reminder}

# ===== 3. mock LLM 节点（按"最近结果计数"驱动，避免 keyword 误判）=====
def agent_node(state: State) -> dict:
    """按 n_calls / n_tool 计数决定下一步"""
    messages = state["messages"]
    n_calls = sum(1 for m in messages
                  if m.get("role") == "assistant" and m.get("tool_calls"))
    n_tool = sum(1 for m in messages if m.get("role") == "tool")
    # Step 3: 已发提醒 → Final Answer
    if n_tool >= 2 and n_calls >= 2:
        return {"messages": [{"role": "assistant",
                              "content": "已提醒您带伞，今天晴 25°C"}],
                "iteration": 1}
    # Step 2: 已查天气 + 未发提醒 → 发提醒
    if n_tool >= 1 and n_calls >= 1:
        return {"messages": [{"role": "assistant", "content": None,
                              "tool_calls": [{"id": "call_2",
                                              "function": {"name": "send_reminder",
                                                           "arguments": '{"content":"带伞"}'}}]}],
                "iteration": 1}
    # Step 1: 第一次 → 查天气
    return {"messages": [{"role": "assistant", "content": None,
                          "tool_calls": [{"id": "call_1",
                                          "function": {"name": "get_weather",
                                                       "arguments": '{"city":"北京"}'}}]}],
            "iteration": 1}

# ===== 4. 工具执行节点 =====
def tool_node(state: State) -> dict:
    last_msg = state["messages"][-1]
    results = []
    for tc in last_msg.get("tool_calls", []):
        # 兼容 dict 和对象两种 tool_call 形式（mock 用 dict，真实 SDK 用对象）
        if isinstance(tc, dict):
            name = tc["function"]["name"]
            args_raw = tc["function"]["arguments"]
            tc_id = tc["id"]
        else:
            name = tc.function.name
            args_raw = tc.function.arguments
            tc_id = tc.id
        import json
        args = json.loads(args_raw) if isinstance(args_raw, str) else args_raw
        result = TOOLS[name](**args)
        results.append({"role": "tool", "tool_call_id": tc_id, "content": result})
    return {"messages": results, "iteration": 0}  # iteration 不在 tool_node 累加

# ===== 5. 条件边 =====
def should_continue(state: State) -> str:
    if state["iteration"] >= 10:
        return END
    if state["messages"][-1].get("tool_calls"):
        return "tools"
    return END

# ===== 6. 构建图 =====
graph = StateGraph(State)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")
app = graph.compile()

# ===== 7. 跑 =====
result = app.invoke({
    "messages": [{"role": "user", "content": "北京今天天气怎么样？需要带伞吗？"}],
    "iteration": 0,
})
for i, msg in enumerate(result["messages"]):
    print(f"[{i}] {msg}")
print(f"总迭代: {result['iteration']}")

13.6.3 ReAct Agent 5 种终止模式

should_continue 是 ReAct Agent 的"刹车"——决定什么时候停。下面 5 种模式覆盖 95% 场景：

终止模式实现适用场景
LLM 自决（默认）LLM 返回 tool_calls = None 时停简单 ReAct
迭代计数iteration >= MAX_ITERATIONS 停防无限循环
超时time.time() - start > MAX_SECONDS 停防止单步慢请求
Token 预算total_tokens >= MAX_TOKENS 停防止成本失控（参考 ch24）
业务信号状态字段 task_done = True 停复杂任务有明确的"完成"判定
# Token 计数节点（S4 修复）：每个 LLM 调用后跑一次
def track_tokens(state: State) -> dict:
    """累加本次 LLM 调用的 token 数（从 AIMessage.usage_metadata 读）"""
    last_msg = state["messages"][-1]
    # 真实 SDK 的 AIMessage 有 usage_metadata 属性（openai / anthropic 都支持）
    usage = getattr(last_msg, "usage_metadata", None) or {}
    new_tokens = usage.get("total_tokens", 0) if isinstance(usage, dict) else 0
    return {"total_tokens": state.get("total_tokens", 0) + new_tokens}

def should_continue(state: State) -> str:
    # 5 种模式组合（按优先级）
    if state["iteration"] >= 10:
        return END                                   # 模式 2
    if time.time() - state["start_time"] > 60:
        return END                                   # 模式 3
    if state.get("total_tokens", 0) >= 5000:
        return END                                   # 模式 4：Token 预算
    if state.get("task_done"):
        return END                                   # 模式 5
    if state["messages"][-1].get("tool_calls"):
        return "tools"                               # 继续
    return END                                       # 模式 1（LLM 自决）

经验法则：生产 ReAct Agent 必须同时启用模式 2 + 3（iteration + 超时），单靠 LLM 自决会被"幻觉式循环"卡死。

13.7 实战：Supervisor 模式 + MCP 协议集成

13.7.1 设计目标

把 ch11 的 Supervisor 模式 + ch12 的 MCP 协议串起来：

  • Supervisor 节点 = 一个 LangGraph 节点，决定委派给哪个 Worker
  • Worker 节点 = 一个 LangGraph 节点，通过 MCP Client 调用外部 MCP Server
  • A2A 风格 = Supervisor ↔ Worker 通过共享 State 通信（不是真正的 HTTP，但形态类似）

13.7.2 完整代码（80 行 mock 跑通版）

# langgraph_supervisor_mcp.py
# Supervisor + MCP 集成 — mock 演示版（已实测跑通）
# 运行：python3 langgraph_supervisor_mcp.py

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END

# Reducer：worker_results 追加新结果（每个 Worker 必须返回 list，即使只有一个）
def add_results(old: list, new):
    """如果 new 是 list，每个元素追加；否则把 new 作为一个元素追加"""
    if new is None:
        return old
    if isinstance(new, list):
        return old + new
    return old + [new]

def set_value(old, new):
    """Reducer：后写覆盖前写（default 行为）"""
    return new if new is not None else old

# ===== State =====
class State(TypedDict):
    query: str
    next_worker: Annotated[str, set_value]
    worker_results: Annotated[list, add_results]

# ===== MCP Server 模拟（ch12 §12.2.4 的 subprocess 风格）=====
class MockMCPServer:
    """模拟 MCP Server 暴露 3 个工具"""
    def call(self, tool_name: str, args: dict) -> str:
        if tool_name == "search":
            return f"[Search MCP] 找到 {args.get('q', '?')} 的 3 条结果"
        if tool_name == "calculator":
            try:
                expr = args.get('expr', '0')
                return f"[Calculator MCP] {expr} = {eval(expr)}"
            except Exception as e:
                return f"[Calculator MCP] 错误: {e}"
        if tool_name == "calendar":
            return f"[Calendar MCP] 已加日程：{args.get('event', '?')}"
        return f"[Unknown MCP] {tool_name}"

mcp_server = MockMCPServer()

# ===== Worker 节点（每个 Worker 都返回 list 形式的结果）=====
def researcher(state: State) -> dict:
    result = mcp_server.call("search", {"q": state["query"]})
    return {"worker_results": [result], "next_worker": "analyst"}

def analyst(state: State) -> dict:
    import re
    nums = re.findall(r'\d+', state["query"])
    if len(nums) >= 2:
        expr = f"{nums[0]} * {nums[1]}"
        result = mcp_server.call("calculator", {"expr": expr})
    else:
        result = "[Calculator MCP] 无数字可算"
    return {"worker_results": [result], "next_worker": "scheduler"}

def scheduler(state: State) -> dict:
    result = mcp_server.call("calendar", {"event": f"跟进：{state['query'][:30]}"})
    return {"worker_results": [result], "next_worker": "END"}

# ===== Supervisor 节点（也返回空 list worker_results，避免 reducer 收 default）=====
def supervisor(state: State) -> dict:
    n = len(state["worker_results"])
    if n == 0:
        return {"next_worker": "researcher", "worker_results": []}
    if n == 1:
        return {"next_worker": "analyst", "worker_results": []}
    if n == 2:
        return {"next_worker": "scheduler", "worker_results": []}
    return {"next_worker": END, "worker_results": []}

# ===== 路由函数 =====
def route(state: State) -> str:
    return state["next_worker"]

# ===== 构建图 =====
graph = StateGraph(State)
graph.add_node("supervisor", supervisor)
graph.add_node("researcher", researcher)
graph.add_node("analyst", analyst)
graph.add_node("scheduler", scheduler)

graph.add_edge(START, "supervisor")
graph.add_conditional_edges("supervisor", route, {
    "researcher": "researcher",
    "analyst": "analyst",
    "scheduler": "scheduler",
    END: END,
})
graph.add_edge("researcher", "supervisor")
graph.add_edge("analyst", "supervisor")
graph.add_edge("scheduler", "supervisor")

app = graph.compile()

# ===== 跑 =====
result = app.invoke({
    "query": "查一下 Q4 销量并加日程跟进，假设销量是 1000 和 25",
    "next_worker": "",
    "worker_results": [],
})
print("\n=== Worker Results ===")
for r in result["worker_results"]:
    print(r)

实测输出（2026-06-25 / langgraph 0.2.76 / Python 3.13）：

=== Worker Results ===
[Search MCP] 找到 查一下 Q4 销量并加日程跟进，假设销量是 1000 和 25 的 3 条结果
[Calculator MCP] 4 * 1000 = 4000
[Calendar MCP] 已加日程：跟进：查一下 Q4 销量并加日程跟进，假设销量是 1000 和 2

运行提示：直接 python3 langgraph_supervisor_mcp.py 即可。真实场景用 pip install mcp 把 MockMCPServer 换成 MCPClient，subprocess 启动真正的 MCP Server 子进程（参考 ch12 §12.9.2 FastMCP 实战）。

⚠️ 安全警告（S1 修复）：MockMCPServer.calculator 用 eval(expr) 在生产场景有 Code Injection 风险——攻击者可注入 __import__('os').system('rm -rf /')。本章 mock 演示场景用 eval 简化（用户输入可控），生产必须改用：

- simpleeval 库（沙箱表达式求值）

- 预定义算式白名单（如 ["+", "-", "*", "/"] + 数字）

- 调用外部 math 服务（如 Wolfram Alpha API / SymPy 服务）

踩坑提示：Worker 节点必须返回 {"worker_results": [result]}（list 形式），否则 reducer 收到的是单个 string，会触发「把字符串包成 list 追加」的 fallback 行为。Supervisor 节点必须返回 "worker_results": [] 显式空 list，不能省略字段——否则 reducer 会收到 default value（也是 []），导致 add_results([], []) 在某些 langgraph 版本中无法区分「节点没动」 vs 「节点把 worker_results 清空了」。

                Top Supervisor (战略层)
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   Mid Sup1      Mid Sup2      Mid Sup3   (战术层)
    │  │          │  │          │  │

13.8.2 Checkpointing（持久化 + 时间旅行）

API 验证（S2 修复）：本节代码使用 langgraph 0.2.76 实测通过（S2 修复验证：cron venv python3 -m pip show langgraph 输出 Version: 0.2.76）。SqliteSaver.from_conn_string(...) 是 0.2.x 的 factory classmethod；0.1.x 用 SqliteSaver(sqlite3.connect("checkpoints.db"))；0.3.x API 可能再变。升级前请核对官方 migration guide（参考 langgraph-ai.github.io/langgraph/concepts/storage.html）。

from langgraph.checkpoint.memory import MemorySaver
from langgraph.checkpoint.sqlite import SqliteSaver

# 内存版（开发用）
memory = MemorySaver()
app = graph.compile(checkpointer=memory)

# SQLite 版（生产用）
db = SqliteSaver.from_conn_string("checkpoints.db")
app = graph.compile(checkpointer=db)

# 跑
config = {"configurable": {"thread_id": "user_123"}}
result1 = app.invoke({"query": "..."}, config=config)
result2 = app.invoke({"query": "继续"}, config=config)  # 接着上次的状态

# 时间旅行：回到第 2 步
snapshot = app.get_state(config, version="v2")
app.update_state(config, snapshot.values)

Checkpoint 3 大用途：

  1. 持久化：图执行到一半崩溃，重启从 checkpoint 继续
  2. 时间旅行：回溯到任意步骤、修改状态、重新跑
  3. Human-in-the-Loop：暂停图执行、等待人工审批、继续

13.8.3 Human-in-the-Loop（interrupt_before / interrupt_after）

app = graph.compile(
    checkpointer=memory,
    interrupt_before=["high_risk_action"],   # 在 high_risk_action 节点前暂停
    interrupt_after=["review"],              # 在 review 节点后暂停
)

# 跑到 high_risk_action 前暂停

# 人工审批：检查 state，决定是否继续

生产场景：支付 / 删除 / 写敏感数据前必须人工确认 → 用 interrupt 实现。

13.10 5 大坑 + 生产经验

13.10.1 状态设计陷阱

坑：把所有字段都放一个 State 里 → 节点之间意外覆盖、字段冲突。

修复：

  • 按子图分 State（每个子图有自己的 State）
  • 用 TypedDict 严格定义字段类型
  • 用 Annotated + Reducer 显式说明合并策略

13.10.2 循环边无限循环

坑：ReAct Agent 调工具失败 → 不断重试 → 永远不停。

修复：

  • 加 iteration 计数器 + 终止条件（最多 10 次）
  • 加 should_continue 显式判断 + END 分支
  • 加 timeout（LangGraph 0.2 支持 step_timeout）
def should_continue(state):
    if state["iteration"] >= 10:
        return END
    ...

13.10.3 Checkpoint 文件锁

坑：用 SQLite 做 checkpoint，多进程并发写 → 文件锁冲突。

修复：

  • 开发用 MemorySaver（无锁）
  • 生产用 PostgresSaver（行级锁，支持多进程）
  • 单机用 SqliteSaver + journal_mode=WAL

13.10.4 并发执行

问题：节点 A → 节点 B 和节点 C 并行 → 怎么收集结果？

方案：langgraph.constants.Send + 条件边动态分支：

from langgraph.constants import Send

def route_parallel(state):
    return [
        Send("worker_1", {"input": state["query"]}),
        Send("worker_2", {"input": state["query"]}),
        Send("worker_3", {"input": state["query"]}),
    ]

graph.add_conditional_edges("fan_out", route_parallel, ["worker_1", "worker_2", "worker_3"])
graph.add_edge(["worker_1", "worker_2", "worker_3"], "fan_in")  # 等所有 worker 完成

5Checkpoint 选型单机用 SqliteSaver + WAL；多机用 PostgresSaver文件锁 / 数据丢失
6可观测性接 LangSmith / OpenTelemetry线上 bug 难定位
7流式输出走 astream_events，别用 invoke用户体验差（长任务无反馈）
8重试策略工具调用失败 + LLM 超时都要重试 + 退避偶发错误放大
9Schema 校验节点输入用 Pydantic 校验 + LLM 输出 JSON Schema字段缺失 / 类型错误
10降级路径关键节点失败 → 走 fallback 节点返回默认结果一个故障全系统瘫

经验法则：1-4 项必须上线前完成；5-8 项第一周内完成；9-10 项第一个月优化。

13.10.7 5 大常见错误信息 + 修复速查

跑 LangGraph 时遇到错误信息不知道怎么修——下面 5 个错误覆盖 90% 场景：

错误信息原因修复
KeyError: 'messages'节点返回的 dict 没包含 messages 字段，且 state 里也没初始化在 invoke 时初始化所有字段为默认值；或节点显式返回 messages
InvalidUpdateError: [..., ..., ...]节点返回了 state 里不存在的字段检查 State TypedDict 是否包含返回的所有字段
GraphRecursionError: Recursion limit reached条件边形成死循环，超过默认 25 步加 iteration 计数 + 终止条件；或 app.invoke(input, config={"recursion_limit": 100})
TypeError: 'NoneType' object is not iterable节点的返回值是 None（不是 dict）节点函数必须返回 dict，即使是空 dict：return {}
ValueError: Node 'X' not foundadd_edge 或 add_conditional_edges 引用的节点名未注册先 add_node，再 add_edge；检查拼写

调试三板斧（按顺序）：

  1. app.get_graph().print_ascii() —— 看图结构对不对
  2. app.get_state(config) —— 看当前 state 字段值
  3. set_debug(True) —— 看每个节点的输入输出

13.11 本章小结 + 概念桥

13.11.1 8 条速记

  1. LangGraph = 显式状态 + 显式控制流 —— 可视化、可 checkpoint、可调试
  2. 3 大核心抽象 —— State（全局数据）/ Node（操作）/ Edge（控制流）
  3. State 用 TypedDict + Annotated —— Reducer 定义字段合并策略
  4. Node 是 (state) -> dict —— 只返回要更新的字段
  5. 条件边 = 决策点 —— ReAct Agent 的核心
  6. 循环边需终止条件 —— 加 iteration 计数
  7. 5 步以内用 LCEL，>5 步用 LangGraph —— 经验法则
  8. Supervisor + MCP + LangGraph = ch11+ch12+ch13 整合 —— 真实生产架构
