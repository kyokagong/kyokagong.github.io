26.1 引子——当工具从固定列表变成生态系统

26.1.1 ch25 留下的隐含假设

ch25 讨论了 Agent 如何从失败轨迹中学习，但它默认了一件事：Agent 的工具集合相对固定。模型可以学会更好地调用搜索、数据库和代码执行器，却很少追问这些工具从哪里来、怎样升级、如何授权、能否跨客户端复用。

于是，“工具市场 / Skills 体系 / MCP 生态——第二十六章聊”不只是下章预告，而是 Agent 从单体应用走向生态系统的转折点。Agent 自己学会做事之后，下一步不是继续堆 prompt，而是让能力能够被发现、安装、组合、审计和替换。

26.1.2 三个经常混在一起的问题

层核心问题代表机制
连接层Agent 怎样以统一方式访问外部数据与动作？MCP
分发层开发者怎样发现、发布、安装这些能力？Registry / 工具市场
方法层Agent 怎样知道完成某类任务的可靠步骤？Agent Skills / SKILL.md

MCP 解决“插头不统一”，Registry 解决“去哪里找插头”，Skills 解决“插上以后怎样把事做对”。三者相互增强，却不能互相替代。

26.1.3 从 N×M 集成到 N+M 集成

没有协议时，N 个 Agent 客户端接 M 个工具，最坏需要维护 N×M 组适配。统一协议把问题近似拆成 N 个客户端适配器加 M 个服务端适配器。它不会消灭业务差异，却把重复的连接、发现、schema 和错误处理收敛到公共层。

时代典型做法主要代价
手写时代每个 Agent 直接调用 REST/SDK凭据、重试、schema 各写一遍
Function Calling 时代模型获得结构化函数描述仍由应用自行发现和托管工具
MCP 时代Client 连接标准化 Server需要治理服务供应链与权限
生态时代Registry + MCP + Skills发现更容易，信任判断更重要

26.1.4 Part 6 为什么从生态开始

前五部分回答“Agent 是什么、怎样构建、怎样协作、怎样实战、怎样工业化”。最后一部分要把视野拉远：技术能力正在变成生态，生态进入企业后又会碰到组织与治理，最后才有资格讨论 Agent 与 AGI。ch26 因此不是工具清单，而是一张能力如何流动的地图。

26.2 MCP 到底标准化了什么

26.2.1 一句话定义

MCP（Model Context Protocol）是连接 AI 应用与外部系统的开放协议。官方文档把它类比为 AI 应用的 USB-C：数据源、工具和工作流通过统一接口接入 Host，Host 再决定把哪些能力交给模型或用户。

这个类比很好用，但不能过度延伸。USB-C 连接的大多是确定性硬件；MCP Server 暴露的可能是数据库写操作、云资源删除或浏览器控制，风险远高于普通外设。因此“能插”从来不等于“应该信任”。

26.2.2 Host、Client、Server 三方架构

角色职责例子不应承担的职责
Host承载模型、用户界面、权限与上下文策略IDE、桌面助手、Hermes Agent不应无条件信任 Server 描述
ClientHost 内的一条 MCP 连接mcp_github 连接器不代表整个应用身份
Server提供上下文与能力文件、GitHub、数据库服务不应读取未授权的 Host 上下文

一个 Host 可以拥有多个 Client；通常每个 Client 与一个 Server 建立有状态会话。把 Client 理解成“会话级连接器”，就不容易把它误认为前端应用。

26.2.3 协议骨架：JSON-RPC + 生命周期

MCP 消息建立在 JSON-RPC 2.0 之上，包含 request、response 与 notification。一次典型连接不是上来就 tools/call，而是：

  1. Client 发送 initialize，声明协议版本与客户端能力；
  2. Server 返回自身能力与信息；
  3. Client 发送 notifications/initialized；
  4. 双方按协商结果使用 tools、resources、prompts 等能力；
  5. 连接结束时释放资源。

能力协商（capability negotiation）很关键：协议存在某个功能，不代表当前两端都支持。生产代码必须按协商结果启用功能，不能只看版本号猜能力。

26.2.4 MCP 不是什么

误解为什么错正确理解
MCP 就是 Function CallingFC 描述一次模型调用可用的函数；MCP还管发现、会话、资源、提示、传输等FC 可作为 Host 内部执行工具的一环
MCP 是 Agent 框架它不负责规划、记忆和状态机LangGraph/CrewAI 等仍负责业务编排
MCP Server 一定运行在远端stdio Server 常是本地子进程本地与远端都是一等场景
进 Registry 就安全Registry 提供发现与元数据，不等于安全背书安装前仍需审计、签名与权限策略
MCP 会自动解决权限协议只提供承载机制Host 与组织必须实施最小权限

26.2.5 与 ch07 Function Calling 的关系

ch07 教的是“模型如何给出结构化调用参数”；ch26 教的是“这些可调用能力如何被发现并跨应用复用”。常见链路是：MCP Server 提供 tool schema → Host 转成模型能理解的工具描述 → 模型产生调用 → Host 经 MCP Client 发送 tools/call → Server 执行并返回结果。二者是上下游，不是竞争标准。

26.3 MCP 六类能力与两种传输

26.3.1 Server 提供的三类核心原语

原语谁主导选择用途例子
Tools通常由模型选择执行动作或计算创建 issue、查天气、跑 SQL
Resources通常由应用选择提供可寻址上下文文件、数据库记录、文档 URI
Prompts通常由用户显式选择提供模板化消息/工作流入口“审查 PR”“生成周报”

“通常”二字不能删。不同 Host 可以设计不同交互，但这个控制边界能帮助工程师判断：工具调用要重审批，资源读取要重范围，Prompt 模板要重可见性与用户意图。

26.3.2 Client 提供的三类反向能力

能力方向解决什么问题风险控制
SamplingServer → Client → 模型Server 请求 Host 代为生成内容模型白名单、token 上限、轮数限制
RootsClient → Server告知 Server 可操作的文件/URI 根范围目录隔离、只读优先
ElicitationServer → Client → 用户向用户索取缺失信息或确认明示字段、禁止索取秘密、用户可拒绝

Sampling 让 Server 不必自带模型密钥，但也创造了“Server 消耗 Host 模型预算”的新边界。Roots 是范围提示，不应被当作唯一沙箱；真正的文件权限仍须由操作系统或容器保证。Elicitation 把追问纳入协议，但不能绕过用户同意。

26.3.3 两种主流传输

维度stdioStreamable HTTP
位置本地子进程本地或远端服务
通信stdin/stdoutHTTP POST，可配流式响应
部署简单，适合开发者工具适合共享、多租户与云服务
身份继承受控环境或显式变量常结合 HTTP 授权与 OAuth
扩缩容进程级服务级
主要风险本地文件与环境变量泄露网络攻击、租户隔离、令牌泄露

旧版独立 HTTP+SSE transport 在生态中仍可能遇到；当前规范的 Streamable HTTP 自身也可以使用 SSE 返回流式事件。新实现应优先跟随当前规范，并对旧 Server 做显式兼容，而不是把“旧 transport 名称”误解成“SSE 技术已经失效”。

26.3.4 工具 schema 是产品契约

一个好 tool schema 至少要做到：名称可区分、描述明确边界、参数有类型与约束、危险动作显式标记、错误可恢复。把 50 个含糊工具一次性暴露给模型，会同时增加 token、误选率和攻击面。

坏描述问题改进
run(query)不知道查询什么、是否写入search_readonly_docs(query, top_k)
manage_repo(action)一个入口混合读写删拆成 list/create/update，删除单独审批
execute(code)权限边界无限固定运行时、超时、网络与目录白名单

26.3.5 结果也需要结构

工具返回一大段自然语言并非最佳实践。结果应优先包含机器可检查的状态、结构化内容、可展示文本与可追踪错误。Host 还应区分“协议错误”“工具执行错误”和“业务未找到”，否则模型只能把所有失败都当成同一类重试。

26.4 从零理解一个最小 MCP 服务

26.4.1 先用 mock 看懂协议，不被 SDK 隐藏细节

下面不是生产 Server，而是一个可运行的 JSON-RPC mock。它展示 initialize、tools/list 与 tools/call 三条主路径，并故意把工具集合做成 allowlist。为聚焦方法分派，示例省略 jsonrpc、id、标准 error object 与 framing，不是线缆级兼容实现。真实项目应使用官方或成熟 SDK 处理 framing、并发、取消、通知和传输。

import json

class MiniMCPServer:
    def __init__(self):
        self.tools = {
            "add": {
                "description": "两个整数相加",
                "inputSchema": {
                    "type": "object",
                    "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}},
                    "required": ["a", "b"],
                },
            }
        }

    def handle(self, req):
        method, params = req.get("method"), req.get("params", {})
        if method == "initialize":
            return {"protocolVersion": "2025-06-18",
                    "capabilities": {"tools": {"listChanged": False}},
                    "serverInfo": {"name": "mini-math", "version": "0.1.0"}}
        if method == "tools/list":
            return {"tools": [{"name": name, **spec} for name, spec in self.tools.items()]}
        if method == "tools/call":
            name, args = params.get("name"), params.get("arguments", {})
            if name not in self.tools:
                return {"isError": True, "content": [{"type": "text", "text": "unknown tool"}]}
            if not all(isinstance(args.get(k), int) for k in ("a", "b")):
                return {"isError": True, "content": [{"type": "text", "text": "a/b must be integers"}]}
            return {"content": [{"type": "text", "text": str(args["a"] + args["b"])}]}
        raise ValueError(f"unsupported method: {method}")

server = MiniMCPServer()
for request in [
    {"method": "initialize", "params": {}},
    {"method": "tools/list"},
    {"method": "tools/call", "params": {"name": "add", "arguments": {"a": 20, "b": 26}}},
]:
    print(json.dumps(server.handle(request), ensure_ascii=False))

预期最后一行返回 46。代码没有网络、API key 或第三方依赖，适合先建立协议直觉。

26.4.2 生产实现多出来的工作

mock 省略项生产要求
请求 ID 与 JSON-RPC envelope正确关联并发 request/response
notifications/initialized完整生命周期与通知
参数校验库严格 JSON Schema、长度与枚举限制
超时/取消截止时间、取消传播、幂等重试
身份权限用户、租户、scope、审批
可观测性trace_id、tool、版本、耗时、结果类别

26.4.3 错误设计决定 Agent 能否自愈

“失败”至少拆成四类：invalid_arguments 让模型改参数；permission_denied 让 Host 请求授权；rate_limited 根据 retry_after 延迟；internal_error 触发有限重试或人工接管。若一律返回“something went wrong”，再强的模型也只能盲猜。

26.4.4 版本兼容策略

协议版本由初始化协商，工具版本则是另一条线。工具 schema 的破坏性修改应发布新 major 版本或新工具名；新增可选字段通常可保持兼容。Server 更新后若工具列表变化，可以通过相应能力通知 Client 刷新，但 Host 仍应缓存上一个可用版本用于回退。

26.5 工具市场与 MCP Registry

26.5.1 Registry 是“目录”，不是“运行时”

官方 MCP Registry 的目标是让 Client 发现可安装的 Server，类似 MCP Server 的应用目录。它保存发布元数据与版本信息，却不替你运行所有 Server，也不天然替你承担安全审计。Client 从 Registry 找到条目后，仍需根据包、远程 URL 或部署说明完成安装和连接。截至 2026 年，具体 API 稳定性与审核范围仍是日期敏感事实，部署前应核对官方状态页。

26.5.2 从发布到调用的生命周期

阶段关键对象必查问题
开发Server + manifest工具边界是否单一、schema 是否稳定
发布包/镜像/远程端点作者身份、版本、许可证、哈希
发现Registry 元数据名称、能力、兼容客户端、更新时间
安装Client/Host 配置来源可信度、依赖、权限、密钥
连接initialize 协商协议版本、能力、超时
运行tool/resource/prompt审批、审计、预算、速率限制
升级新版本schema diff、迁移、回退
下架撤销/隔离已安装副本、凭据吊销、告警

26.5.3 为什么企业一定会建私有 Registry

公共市场适合通用能力，企业真正有价值的工具往往连接 CRM、ERP、数据仓库、工单和内部知识库，不能公开发布。私有 Registry 的价值不只“藏起来”，更是把审批状态、数据等级、责任团队、SLA、成本中心与可用租户写进元数据。

公共 Registry企业私有 Registry
强调开放发现与跨客户端兼容强调身份、合规、SLA 与资产责任人
作者声誉和社区反馈重要安全评审、数据分级和变更流程重要
常见安装是 npm/PyPI/容器/远程 URL常见安装是内部镜像与受控远程服务
用户自行判断是否可信平台团队维护 allowlist 与撤销机制

26.5.4 市场排序不能只看下载量

工具市场若只按下载量排序，会把“流行”等同于“适合”。面向 Agent 的排序至少要综合：任务相关度、权限需求、组织 allowlist、schema 质量、维护活跃度、调用成本、历史成功率和安全事件。对写操作，合规等级应当拥有一票否决权。

26.5.5 供应链是新攻击面

恶意或被接管的 Server 可以在描述中诱导模型泄露上下文，在更新中扩大权限，或借依赖包执行本地代码。因而市场需要包签名、不可变版本、来源证明、依赖清单（SBOM）、漏洞扫描、维护者双因素认证与快速撤销。“安装一个工具”在安全意义上更接近安装 IDE 插件，而不是收藏一个网页。

26.6 Agent Skills——把“会做事”打包

26.6.1 Skill 不是工具，而是可移植的操作手册

Agent Skills 是一种轻量开放格式，用文件夹打包专门知识与工作流。最小 Skill 只有一个带 YAML frontmatter 的 SKILL.md；复杂 Skill 还能带 scripts/、references/、assets/ 等资源。

my-skill/
├── SKILL.md          # 必需：名称、描述、工作步骤
├── scripts/          # 可选：确定性代码
├── references/       # 可选：规范、API、长文档
└── assets/           # 可选：模板、图片、样例

工具提供“能做什么”，Skill 描述“怎样稳定地做”。比如 GitHub MCP Server 能列 issue、改文件、开 PR；release-hotfix Skill 则规定先复现、再写测试、检查变更、走审批、发布与回滚。

26.6.2 SKILL.md 的最小契约

---
name: release-hotfix
description: 生产故障热修复流程；当用户要求紧急修复和发布时使用。
---

# Hotfix
1. 建立隔离分支并记录事件编号。
2. 先写失败测试，再做最小修复。
3. 运行安全扫描、回归测试和回滚演练。
4. 经审批后发布，并记录验证证据。

描述字段尤其重要：Agent 通常先看到 Skill 的名称和描述，再决定是否加载正文。描述过宽会误触发，描述过窄会漏触发；好的描述同时写“做什么”和“何时使用”。按 Agent Skills 规范，名称应使用小写字母、数字与连字符并与目录名一致；description 必填，长度为 1-1024 个字符。

26.6.3 渐进式披露为什么重要

把所有 Skill 全文塞进 system prompt 会迅速耗尽上下文。渐进式披露通常分三层：

  1. 目录层：只加载名称与描述，用于路由；
  2. 正文层：命中后加载 SKILL.md；
  3. 附件层：执行到具体步骤时才读取脚本、参考和模板。

这样既节省 token，也减少无关说明之间的冲突。Skills 的优势不是“prompt 更多”，而是在正确时机加载正确上下文。

26.6.4 一个可运行的渐进加载器

from pathlib import Path
from tempfile import TemporaryDirectory


def read_skill(skill_dir, load_references=False):
    text = (Path(skill_dir) / "SKILL.md").read_text(encoding="utf-8")
    if not text.startswith("---\n"):
        raise ValueError("SKILL.md must start with YAML frontmatter")
    _, frontmatter, body = text.split("---", 2)
    meta = {}
    for line in frontmatter.strip().splitlines():
        if ":" in line:
            key, value = line.split(":", 1)
            meta[key.strip()] = value.strip()
    result = {"metadata": meta, "instructions": body.strip()}
    if load_references:
        ref_dir = Path(skill_dir) / "references"
        result["references"] = {
            p.name: p.read_text(encoding="utf-8") for p in ref_dir.glob("*.md")
        } if ref_dir.exists() else {}
    return result


with TemporaryDirectory() as tmp:
    root = Path(tmp) / "demo-skill"
    (root / "references").mkdir(parents=True)
    (root / "SKILL.md").write_text(
        "---\nname: demo-skill\ndescription: 演示渐进加载\n---\n\n先读说明，再按需读参考。",
        encoding="utf-8",
    )
    (root / "references" / "api.md").write_text("API v1", encoding="utf-8")
    print(read_skill(root, load_references=False)["metadata"])
    print(read_skill(root, load_references=True)["references"])

真实实现应使用 YAML 解析器并校验规范字段；这里刻意只用标准库，展示“先元数据、后正文、再附件”的加载时机。

26.6.5 Skills 的版本与评测

Skill 是代码旁边的过程资产，也要进版本控制。每次修改应记录触发条件、步骤差异和兼容性，并用一组真实任务评测：该触发时是否触发、不该触发时是否沉默、步骤是否完成、脚本是否可执行、最终证据是否齐全。

评测维度示例指标
触发准确率20 个正例命中率、20 个负例误触发率
执行完成率验收项通过数 / 总数
稳定性同任务重复 5 次的方差
成本加载 token、工具调用数、耗时
可维护性过期链接、脚本测试、责任人

26.6.6 Skills 不应藏秘密

Skill 文件夹通常可被提交、共享或安装，不能把 API key 写进正文或脚本。Skill 应声明需要哪些凭据，再由 Host 的秘密管理系统注入；日志中也要脱敏。过程知识可移植，身份凭据不可移植。

26.7 MCP、Skills、Prompt、Plugin 如何分工

26.7.1 四者不是同一层

机制核心资产最适合不适合
Prompt一段即时上下文当前任务约束、输出格式长期维护复杂流程
Skill可版本化流程包领域方法、重复工作、模板脚本直接提供远程系统权限
MCP标准能力接口跨客户端工具/资源/Prompt 接入替代业务编排与审查制度
Plugin/原生工具Host 内代码扩展深度 UI、性能或平台特性每个客户端重复开发通用接口

判断口诀：需要“知道怎么做”写 Skill；需要“能够去做”接 Tool/MCP；需要“只在本轮这样做”写 Prompt；需要“改变 Host 本身”才做 Plugin。

26.7.2 最强组合：Skill 编排 MCP

以“发布周报”为例：Skill 规定从 Linear 汇总已完成 issue、从 GitHub 取 PR、按部门模板生成摘要、让负责人确认后发到文档系统；MCP Servers 分别提供 Linear、GitHub 和文档写入能力。若换掉 GitHub Client，只要工具语义兼容，Skill 的业务步骤仍可复用。

26.7.3 何时不该上 MCP

  • 只有一个应用、一个稳定内部函数，且不存在复用计划；
  • 调用在同一进程内且性能极敏感；
  • API 仍高速变动，连基本 schema 都不稳定；
  • 数据不能跨进程或网络边界；
  • 团队尚无权限、审计和版本治理能力。

标准化有固定成本。MVP 可以先用原生函数，但接口边界应保持清晰，成熟后再封成 MCP Server。

26.7.4 何时不该写 Skill

一次性、两行即可说明的任务不需要 Skill；没有验证过的个人偏好也不应立刻固化；纯事实知识若更适合 RAG，就不必伪装成流程。Skill 应保存可复用的程序性知识，而不是成为所有上下文的垃圾抽屉。

26.8 发现、路由与组合

26.8.1 工具越多，选择越难

1000 个工具全部注入模型上下文，会导致描述成本上升、相似名称互相竞争、误调用增加。生态规模化的关键不是无限曝光，而是两阶段甚至三阶段路由：先找领域，再找候选工具，最后按权限和任务状态筛选。

26.8.2 一个可解释的路由评分器

TOOLS = [
    {"name": "github_search", "tags": {"code", "search"}, "risk": 1, "latency": 2},
    {"name": "github_merge", "tags": {"code", "write"}, "risk": 5, "latency": 2},
    {"name": "docs_search", "tags": {"docs", "search"}, "risk": 1, "latency": 1},
]


def rank_tools(task_tags, allow_write=False):
    ranked = []
    for tool in TOOLS:
        overlap = len(task_tags & tool["tags"])
        blocked = "write" in tool["tags"] and not allow_write
        score = overlap * 10 - tool["risk"] * 2 - tool["latency"]
        if not blocked and overlap:
            ranked.append((score, tool["name"]))
    return sorted(ranked, reverse=True)


print(rank_tools({"code", "search"}))
# github_search 应排名第一；github_merge 因 write 未授权被过滤

真实系统会加入语义向量、历史成功率、租户策略与实时成本，但“先硬过滤、后软排序”原则不变。安全条件不能只是一个可被相关度抵消的负分。

26.8.3 Skill 路由与工具路由不同

Skill 路由看用户意图是否匹配“何时使用”；工具路由看当前步骤需要哪项外部能力。一个任务通常先命中一个 Skill，然后 Skill 的每一步再触发不同工具。若反过来让工具描述承担完整流程，工具会变得又长又脆弱。

26.8.4 上下文预算的三级漏斗

阶段输入规模输出
目录检索数百/数千条短描述5-20 个候选 Skill/Server
能力展开候选 schema 与 Skill 正文3-8 个当前可用工具
执行时加载具体参考、模板、资源本步骤最小上下文

这与 ch08 记忆系统的混合检索同构：先粗召回，再重排，最后按需读取原文。生态越大，越不能省掉检索层。

26.8.5 组合需要显式状态

跨 Server 工作流要保存调用结果、来源、版本和授权状态。例如“查客户 → 查未付账单 → 创建提醒”涉及 CRM、财务和消息三个 Server。任何一步失败，都要知道哪些动作已产生副作用，才能补偿或请求人工接管。MCP 统一调用接口，不自动提供分布式事务。

26.9 安全、权限与治理

26.9.1 MCP 把 ch23 的攻击面扩大到供应链

ch23 的提示注入在 MCP 生态里出现新载体：工具描述、Resource 内容、Prompt 模板、Server 返回值和 Registry 元数据都可能携带恶意指令。Host 必须把它们当作不可信数据，而不是高优先级系统指令。

威胁例子防线
Tool poisoning描述诱导模型先读取密钥描述扫描、来源签名、上下文隔离
Rug pull更新版偷偷新增写权限版本锁定、schema diff、重新审批
Confused deputy低权限用户借 Host 调高权限工具端到端用户身份与 scope
Data exfiltrationResource 内容指示把数据发外网出站 allowlist、数据分类、DLP
Dependency compromisenpm/PyPI 依赖被接管SBOM、哈希锁定、镜像扫描
Prompt injection文档要求忽略 Host 策略指令/数据分层、结果净化

26.9.2 最小权限要落到每个工具

不要只给整个 Server 一个“可信/不可信”开关。GitHub Server 可以同时包含读仓库、写 issue、合并 PR、删除分支；它们的风险完全不同。Host 应允许按 Server、tool、参数、用户、租户和环境分别授权。

26.9.3 一个参数级策略门

from pathlib import PurePosixPath

POLICY = {
    "read_file": {"roots": [PurePosixPath("/workspace/docs")], "approval": False},
    "publish_report": {"roots": [], "approval": True},
}


def authorize(tool, args, user_approved=False):
    rule = POLICY.get(tool)
    if not rule:
        return False, "tool_not_allowlisted"
    if rule["approval"] and not user_approved:
        return False, "approval_required"
    if tool == "read_file":
        path = PurePosixPath(args.get("path", ""))
        allowed = any(path == root or root in path.parents for root in rule["roots"])
        if not allowed or ".." in path.parts:
            return False, "path_outside_roots"
    return True, "allowed"


print(authorize("read_file", {"path": "/workspace/docs/guide.md"}))
print(authorize("read_file", {"path": "/etc/passwd"}))
print(authorize("publish_report", {}, user_approved=False))

策略检查必须发生在真正执行之前，且不能让模型通过自然语言说“用户已同意”来设置 user_approved=True。审批状态应来自 Host UI 的可信事件。

26.9.4 凭据不能交给模型上下文

stdio Server 只应继承必要环境变量；远程 Server 使用短期 token、细粒度 scope 与安全存储。Host 调用工具时引用凭据，但不把明文 key 放进 prompt、Resource 或工具结果。凭据轮换和吊销也要独立于 Skill 与 Server 版本。

26.9.5 零信任 MCP 清单

  1. 默认不安装，来源进入 allowlist；
  2. 默认只读，写操作按 tool 单独开；
  3. 默认锁版本，升级先做 schema 与依赖 diff；
  4. 默认隔离，本地 Server 在容器或受限账户运行；
  5. 默认限流，限制调用次数、时长、token 与费用；
  6. 默认留痕，记录用户、模型、Server/tool 版本、参数摘要和结果；
  7. 默认可撤销，出现事件能停用 Server 并吊销所有凭据；
  8. 默认人工确认不可逆动作。

26.9.6 Tool annotations 不是安全边界

Server 可以声明工具只读、破坏性或幂等等属性，Host 可借此改善 UI 与默认策略；但这些注解来自 Server 自己，不能替代独立策略。恶意 Server 完全可能把删除动作标成只读。安全判断必须以组织策略、代码审计和运行时观测为准。

26.10 2026 生态现状与企业参考架构

26.10.1 从协议采用到生态竞争

截至 2026 年，MCP 已从单一厂商倡议走向多种 AI 客户端、开发工具与服务提供商共同支持的开放生态。竞争焦点也从“是否支持 MCP”转向“发现体验、授权、远程托管、工具筛选、企业治理和可观测性做得多好”。协议统一底座，并不会让上层产品同质化。

Skills 同样体现这一趋势：团队不再只共享 prompt，而是共享带触发条件、脚本、参考和模板的过程包。MCP 让能力跨客户端流动，Skills 让方法跨模型与团队流动。

26.10.2 Hermes Agent 的组合示例

Hermes 的原生 MCP Client 可以连接 stdio 与 HTTP Server，启动时发现工具并注册为一等工具；工具名带 Server 前缀以避免冲突。Hermes Skills 则按需加载知识文档，并通过渐进式披露控制 token。两者组合恰好展示了本章结论：

用户任务
  ↓
Skill 路由：加载“怎样做”的步骤、模板、检查表
  ↓
Agent 规划：决定当前步骤需要哪种能力
  ↓
MCP 工具路由：从允许的 Server/Tool 中选择
  ↓
策略门：用户、scope、参数、预算、审批
  ↓
执行 + 观测 + 结果回到 Agent

26.10.3 企业双 Registry 参考架构

企业可以把公共生态与内部资产分开治理：

层组件职责
体验层IDE、助手、业务 Agent用户交互、审批、结果展示
编排层Agent Runtime + Skill Catalog计划、流程、上下文预算
连接层MCP Clients / Gateway发现、会话、协议、限流
治理层Policy Engine + Audit + Secretsscope、DLP、凭据、追踪
目录层公共 Registry 镜像 + 私有 Registry审核、版本、撤销、责任人
能力层SaaS/内部/本地 MCP Servers业务数据与动作

公共 Registry 条目应先进入隔离环境扫描和评测，再被镜像到企业 allowlist；内部 Server 则必须绑定资产责任人、数据等级和 SLA。Agent 只能看见与当前用户和租户匹配的子集。

26.10.4 5 大落地坑

坑症状根因修复
工具海啸上百工具全塞 prompt，误选上升无检索与分层目录召回 → 重排 → 最小暴露
权限扁平一个 token 能读写所有系统只按 Server 授权tool/参数/用户/环境四维策略
版本漂移昨天可用，升级后 schema 变了未锁版本、无契约测试semver、schema diff、回归与回退
Skill 腐化步骤和链接过期无责任人和评测版本控制、使用遥测、定期复核
市场即信任看到 Registry 就直接安装把发现误当背书签名、SBOM、扫描、沙箱、allowlist

26.10.5 三阶段落地路线

阶段 1：受控试点。 选 3-5 个只读工具和 2-3 个高频 Skill，在沙箱中验证发现、权限、日志和成本。

阶段 2：私有目录。 建立 Server/Skill 负责人、版本规则、审批、评测集和撤销机制；接入统一秘密管理与 SSO。

阶段 3：生态运营。 开放内部发布，按任务成功率、成本和安全事件持续排序；对公共生态采用镜像审查；把重复的 Agent 轨迹沉淀回 Skills，把稳定能力沉淀为 MCP Server。

26.10.6 生态飞轮

成功轨迹 → 提炼成 Skill → Skill 调用标准 MCP 能力 → 运行产生可观测数据 → 发现缺失能力 → 发布或升级 Server → Registry 分发 → 更多轨迹。ch25 的自我改进因此没有结束，而是从“模型策略”扩展到“组织能力资产”的持续改进。

26.11 小结、速查与概念桥

26.11.1 8 步落地清单

  1. 盘点现有工具与数据源，先区分读、写和不可逆动作；
  2. 把可复用能力封装成边界清晰的 MCP Server；
  3. 用严格 schema、结构化错误和能力协商建立契约；
  4. 建立公共 Registry 镜像与企业私有 Registry；
  5. 把重复流程沉淀成 Skills，而不是继续堆 system prompt；
  6. 使用渐进式披露与两阶段路由控制上下文；
  7. 在调用前执行 tool/参数/用户/环境级策略；
  8. 用审计、评测、版本锁定和撤销机制持续运营。

26.11.3 五个必须记住的判断

  • MCP 标准化连接，不标准化信任；
  • Registry 负责发现，不等于安全认证；
  • Skill 保存程序性知识，不保存凭据；
  • 工具数量越多，越需要检索、路由和最小暴露；
  • 能力生态的终点不是“安装更多”，而是“用更少、更可信的能力完成任务”。

26.11.5 概念桥 ch26 ↔ ch27

ch26 看起来给出了一个漂亮答案：接口统一、工具可发现、流程可复用，企业似乎只要建个市场就能获得 Agent 生产力。但技术目录不会自动改变责任边界，协议兼容也不会自动带来 ROI、数据质量、员工采纳、采购流程与合规批准。
