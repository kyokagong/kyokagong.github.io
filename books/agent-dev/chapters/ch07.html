7.1 引子：从"function call"到"tool use"

2023 年 6 月，OpenAI 在 GPT-4 和 GPT-3.5-turbo 上推出了一个**让 LLM 能"算"的功能**——`function calling`。之前的 LLM 只会生成文本：你问"3.14 × 2.71 等于多少？"，它会编一个答案（经常错）。推出 `function calling` 之后，LLM 不直接回答，而是**输出一个结构化的函数调用请求**：

{
  "name": "calculate",
  "arguments": "{\"x\": 3.14, \"y\": 2.71}"
}

你的代码**真的去调 `calculate(3.14, 2.71)`**——拿到准确答案 8.5104——再**把这个数字回传给 LLM**，让它用自然语言回复用户。**这就是 Function Calling 的本质**：LLM 不再"假装计算"，而是**输出调用意图**，让真实代码去执行。

7.1.3 为什么 Function Calling 改变了 LLM 的能力边界

在 Function Calling 出现之前（2023-06 之前），LLM 是**纯文本生成器**——你说"3.14 × 2.71 等于多少"，它会编一个答案（经常错）。Function Calling 出现之后，LLM 有了**3 个新的能力**：

能力之前（纯文本）之后（Function Calling）真实场景
**算术**编答案（错）调 `calculate(x, y)` 返回准确值财务计算、单位换算
**实时信息**幻觉（"2024 年奥运会在巴黎"——2024 还真有）调 `get_current_date()` / `get_news()`实时天气、新闻、股价
**操作外部系统**只能"说"调 `send_email()` / `create_order()`客服自动退款、运维脚本

**关键洞察**：**Function Calling 把 LLM 从"知识库 + 文本生成器"升级成了"调度器 + 控制器"**。它不再"知道答案"，而是"知道该调什么工具"——这是 Agent 能"做事"的根本原因。

**2024-2025 业界共识**：**没有 Function Calling 就没有 Agent**。所有 Agent 框架（LangGraph / AutoGen / CrewAI / OpenAI Agents SDK）的底层都依赖 tool use 协议——ch04 学的 7 个框架只是"对 tool use 协议的不同封装"。

7.2 OpenAI Tools API 全景

OpenAI 的 Tool Use（2025 年最新）通过 `tools` 字段声明工具、`tool_choice` 控制选择策略、`parallel_tool_calls` 控制是否并行。响应中 LLM 用 `finish_reason="tool_calls"` + `message.tool_calls` 数组告诉你"我要调这些函数"。

7.2.1 完整请求结构

from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "你是一个天气助手"},
        {"role": "user",   "content": "北京今天天气怎么样？"}
    ],
    tools=[
        {
            "type": "function",
            "function": {
                "name": "get_weather",
                "description": "查询指定城市的当前天气",
                "parameters": {
                    "type": "object",
                    "properties": {
                        "city": {
                            "type": "string",
                            "description": "城市名，如 '北京'、'上海'"
                        },
                        "unit": {
                            "type": "string",
                            "enum": ["celsius", "fahrenheit"],
                            "description": "温度单位"
                        }
                    },
                    "required": ["city"]
                }
            }
        }
    ],
    tool_choice="auto",          # "auto" | "none" | "required" | {"type": "function", "function": {"name": "..."}}
    parallel_tool_calls=True,    # 允许一次返回多个 tool_calls
)

**4 个关键参数**：

  • `tools`：JSON Schema 数组，每个 tool 一个对象
  • `tool_choice`：`auto`（LLM 决定） / `none`（禁止调用） / `required`（必须调一个） / 指定具体函数
  • `parallel_tool_calls`：是否允许一次输出多个 tool_call
  • `messages`：标准多轮对话结构

7.2.2 完整响应结构

# response.choices[0].finish_reason == "tool_calls"
# response.choices[0].message.tool_calls == [
#     {
#         "id": "call_abc123",
#         "type": "function",
#         "function": {
#             "name": "get_weather",
#             "arguments": '{"city": "北京", "unit": "celsius"}'
#         }
#     }
# ]

**5 个关键字段**：

  • `finish_reason = "tool_calls"`：告诉你"我决定要调工具，不是在正常聊天"
  • `tool_calls[].id`：每个调用的唯一 ID，**回传结果时要用这个 ID 配对**
  • `tool_calls[].function.name`：函数名
  • `tool_calls[].function.arguments`：参数（**JSON 字符串**，不是 dict）
  • `tool_calls[].type`：固定 `"function"`

7.2.3 完整实战代码（OpenAI hello world）

"""
OpenAI Tools API hello world——一个能"查天气" + "发提醒"的 Agent。
可运行（mock LLM 模式），实际使用替换 client 即可。
"""
import json
from typing import Any
from openai import OpenAI

# ---------- 1. 真实业务函数 ----------
def get_weather(city: str, unit: str = "celsius") -> dict:
    """查询天气（真实场景调 API，这里 mock）"""
    return {"city": city, "temp": 18, "unit": unit, "condition": "有雨"}

def send_reminder(content: str) -> dict:
    """发提醒（真实场景调推送服务，这里 mock）"""
    return {"status": "已加入日历", "content": content}

# ---------- 2. 工具 Schema（OpenAI 格式）----------
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的当前天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city":  {"type": "string", "description": "城市名"},
                    "unit":  {"type": "string", "enum": ["celsius", "fahrenheit"]}
                },
                "required": ["city"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "send_reminder",
            "description": "向用户发送一条提醒（会加入日历）",
            "parameters": {
                "type": "object",
                "properties": {
                    "content": {"type": "string", "description": "提醒内容"}
                },
                "required": ["content"]
            }
        }
    }
]

# ---------- 3. 工具执行映射 ----------
AVAILABLE_FUNCS = {
    "get_weather":  get_weather,
    "send_reminder": send_reminder,
}

# ---------- 4. 主循环 ----------
def run_agent(user_query: str) -> str:
    client = OpenAI()  # 真实场景用 api_key 初始化
    messages = [
        {"role": "system", "content": "你是天气助手，查到天气后给用户提醒。"},
        {"role": "user",   "content": user_query}
    ]

    for step in range(5):  # 最多 5 轮工具调用
        resp = client.chat.completions.create(
            model="gpt-4o",
            messages=messages,
            tools=TOOLS,
            tool_choice="auto",
        )
        msg = resp.choices[0].message

        # 终态：LLM 给最终答案
        if msg.content and not msg.tool_calls:
            return msg.content

        # 工具调用：执行 → 把结果塞回 messages
        messages.append(msg)  # 追加 assistant 消息（含 tool_calls）
        for tool_call in msg.tool_calls:
            func_name = tool_call.function.name
            func_args = json.loads(tool_call.function.arguments)
            result = AVAILABLE_FUNCS[func_name](**func_args)
            # 把结果作为 "tool" role 消息塞回
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": json.dumps(result, ensure_ascii=False)
            })

    return "[max steps reached]"

# ---------- 5. 测试 ----------
if __name__ == "__main__":
    print(run_agent("查下北京天气"))

**4 个关键步骤**：

  • **声明** `TOOLS` 数组（JSON Schema）
  • **调用** API，传 `tools` + `tool_choice="auto"`
  • **判断** `finish_reason`：是 `"tool_calls"` 就执行工具，是 `"stop"` 就拿到最终答案
  • **回传**：把工具结果作为 `role="tool"` 消息塞回 `messages` 数组，**带 `tool_call_id` 配对**
**关键概念摘要**：
- OpenAI 协议核心：`tools` 字段 + `tool_calls` 响应 + `role="tool"` 回传
- `tool_call_id` 必须配对——LLM 一次可能调多个工具，每个 ID 唯一
- `arguments` 是 JSON 字符串，要 `json.loads` 解析

7.3 Anthropic Tool Use 全景

Anthropic 的 Tool Use（从 2023-11 Claude 2.1 开始就是这个名字，**比 OpenAI 早用 "tool" 一词**）结构上和 OpenAI 很像，但有三个**关键差异**：

  • **工具位置不同**：OpenAI 用 `messages` 外的 `tools` 字段；Anthropic 的 `tools` 也在顶层，但**响应里工具调用是一个 `content` block**（不是单独的 `tool_calls` 数组）
  • **system prompt 位置**：OpenAI 的 system 是 `messages` 的第一条；Anthropic 的 system 是**独立的 `system` 字段**（在 `messages` 外）
  • **`stop_reason` 命名**：OpenAI 用 `"tool_calls"`，Anthropic 用 `"tool_use"`

7.3.1 完整请求结构

import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-3-5-sonnet-20241022",
    max_tokens=1024,
    system="你是一个天气助手",        # ← 注意：system 是独立字段，不在 messages 里
    tools=[
        {
            "name": "get_weather",
            "description": "查询指定城市的当前天气",
            "input_schema": {           # ← 注意：参数叫 input_schema，不是 parameters
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名"},
                    "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
                },
                "required": ["city"]
            }
        }
    ],
    messages=[
        {"role": "user", "content": "北京今天天气怎么样？"}
    ]
)

**3 个关键差异（vs OpenAI）**：

  • `system` 是**独立字段**（不在 `messages` 数组里）
  • 参数叫 `input_schema`（不是 `parameters`）
  • 工具没有 `type: "function"` 外层（直接 `name` + `description` + `input_schema`）

7.3.2 完整响应结构

# response.stop_reason == "tool_use"
# response.content == [
#     {"type": "text",      "text": "让我查一下北京天气"},
#     {"type": "tool_use",  "id": "toolu_abc123", "name": "get_weather", "input": {"city": "北京"}}
# ]

**Anthropic 响应特点**：`content` 是一个**多类型 block 数组**，可以同时包含 `text`（文字）和 `tool_use`（工具调用）。这意味着**LLM 可以一边说"我先查一下"一边调用工具**——OpenAI 只能要么纯文字、要么纯 tool_call（除非 `content: null` + `tool_calls: [...]`）。

7.3.3 完整实战代码（Anthropic hello world）

"""
Anthropic Tool Use hello world——和 7.2.3 同样业务，对照展示协议差异。
"""
import json
import anthropic

# ---------- 1. 真实业务函数（与 7.2.3 同） ----------
def get_weather(city: str, unit: str = "celsius") -> dict:
    return {"city": city, "temp": 18, "unit": unit, "condition": "有雨"}

def send_reminder(content: str) -> dict:
    return {"status": "已加入日历", "content": content}

# ---------- 2. 工具 Schema（Anthropic 格式）----------
TOOLS = [
    {
        "name": "get_weather",
        "description": "查询指定城市的当前天气",
        "input_schema": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名"},
                "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
            },
            "required": ["city"]
        }
    },
    {
        "name": "send_reminder",
        "description": "向用户发送一条提醒（会加入日历）",
        "input_schema": {
            "type": "object",
            "properties": {
                "content": {"type": "string", "description": "提醒内容"}
            },
            "required": ["content"]
        }
    }
]

AVAILABLE_FUNCS = {"get_weather": get_weather, "send_reminder": send_reminder}

# ---------- 3. 主循环 ----------
def run_agent(user_query: str) -> str:
    client = anthropic.Anthropic()
    messages = [{"role": "user", "content": user_query}]

    for step in range(5):
        resp = client.messages.create(
            model="claude-3-5-sonnet-20241022",
            max_tokens=1024,
            system="你是天气助手，查到天气后给用户提醒。",
            tools=TOOLS,
            messages=messages,
        )

        # 终态：stop_reason="end_turn" 或 "stop_sequence"
        if resp.stop_reason == "end_turn":
            return "".join(b.text for b in resp.content if b.type == "text")

        # 工具调用：遍历 content blocks
        if resp.stop_reason == "tool_use":
            # 追加 assistant 消息（整个 content 数组）
            messages.append({"role": "assistant", "content": resp.content})
            # 遍历所有 tool_use blocks
            tool_results = []
            for block in resp.content:
                if block.type == "tool_use":
                    result = AVAILABLE_FUNCS[block.name](**block.input)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,        # ← 配对 ID
                        "content": json.dumps(result, ensure_ascii=False)
                    })
            # 把所有 tool_result 一起作为 user 消息回传
            messages.append({"role": "user", "content": tool_results})

    return "[max steps reached]"

if __name__ == "__main__":
    print(run_agent("查下北京天气"))

**4 个关键差异（vs OpenAI 实现）**：

  • `system` 是独立参数，不在 `messages` 数组里
  • 工具参数叫 `input_schema`（不是 `parameters`）
  • 响应是 `content` 数组遍历，**不是 `tool_calls` 字段**
  • 回传工具结果是 `role="user"` + `type="tool_result"` block（OpenAI 是 `role="tool"` 消息）
**关键概念摘要**：
- Anthropic 协议核心：`tools` 字段 + `content` block 数组 + `tool_use` / `tool_result` 配对
- **回传工具结果用 `role="user"`**（不是 `role="tool"`）——这点最反直觉
- `system` 独立字段——别放错位置

7.4 Google Gemini Function Calling 全景

Google 的 Function Calling（2024-04 Gemini 1.5 首发）和 OpenAI 比较像，但有两个**关键差异**：

  • **system prompt 用 `system_instruction` 独立字段**（类似 Anthropic）
  • **响应/请求都把消息包在 `parts` 数组里**（嵌套更深）
  • **工具调用返回是 `functionCall` 对象**，**回传结果是 `functionResponse` 对象**（命名不同）

7.4.1 完整请求结构

import google.generativeai as genai

genai.configure(api_key="YOUR_KEY")
model = genai.GenerativeModel(
    model_name="gemini-2.0-flash",
    system_instruction="你是一个天气助手",  # ← 类似 Anthropic，system 独立
    tools=[
        {
            "function_declarations": [   # ← 注意：外面包一层 function_declarations
                {
                    "name": "get_weather",
                    "description": "查询指定城市的当前天气",
                    "parameters": {       # ← 这里又和 OpenAI 一样叫 parameters
                        "type": "object",
                        "properties": {
                            "city": {"type": "string", "description": "城市名"},
                            "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
                        },
                        "required": ["city"]
                    }
                }
            ]
        }
    ]
)

chat = model.start_chat()
response = chat.send_message("北京今天天气怎么样？")

**3 个关键差异**：

  • `system_instruction` 独立字段
  • 工具声明**多一层 `function_declarations` 包裹**
  • 工具参数叫 `parameters`（和 OpenAI 一样）

7.4.2 完整响应结构

# response.candidates[0].content.parts == [
#     {"function_call": {"name": "get_weather", "args": {"city": "北京"}}}
# ]

**Google 响应特点**：工具调用是 `parts` 数组里的一个 `function_call` 对象，没有独立的 `tool_calls` 字段。回传时要构造 `parts: [{"function_response": {...}}]`。

    resp = chat.send_message(user_query)

    for step in range(5):
        # 找所有 function_call parts
        # 注：Google SDK 的 fc.args 是 MapComposite 对象（类似 dict 但不是纯 dict），
        #     必须用 dict() 转换后才能 ** 解包，否则会报"argument of type MapComposite is not iterable"
        func_calls = [p.function_call for p in resp.parts if p.function_call]
        if not func_calls:
            return resp.text

        # 执行所有函数调用，回传 function_response
        func_responses = []
        for fc in func_calls:
            args = dict(fc.args) if fc.args else {}   # ← dict() 转换 MapComposite
            result = AVAILABLE_FUNCS[fc.name](**args)
            func_responses.append({
                "function_response": {
                    "name": fc.name,
                    "response": result   # ← 直接传 dict（不是 JSON 字符串）
                }
            })
        resp = chat.send_message(func_responses)   # ← Google 把 function_response 作为新消息

    return "[max steps reached]"

if __name__ == "__main__":
    print(run_agent("查下北京天气"))

**4 个关键差异（vs OpenAI / Anthropic）**：

  • `system_instruction` 独立字段（类似 Anthropic）
  • 工具声明**包在 `function_declarations` 里**
  • 工具调用是 `parts[].function_call`，**不是 `tool_calls` 数组**
  • 回传用 `function_response` 对象，**直接传 dict**（OpenAI/Anthropic 都传 JSON 字符串）
**关键概念摘要**：
- Google 协议核心：`function_declarations` 嵌套 + `parts[].function_call` 响应 + `function_response` 回传
- 工具结果**直接传 dict**（不是 JSON 字符串）——这点最特别
- `system_instruction` 独立字段（类似 Anthropic）

光看代码看不出"协议层到底长啥样"。下面用**同一查询 "北京天气"** 走完三家协议，对比**原始 JSON 响应**——这是协议层最直观的差异。

7.6 JSON Schema 高级模式

ch06.3 讲了"工具描述的 7 条军规"，那是**基础**。本节讲 4 个**高级模式**——生产中真正常用，ch03 那种基础 schema 不够用。

7.6.1 嵌套对象

工具的参数如果是个**结构化对象**（如 `address: {street, city, zip}`），要用 `properties` 嵌套。

{
  "name": "create_shipping_order",
  "description": "创建一个物流订单",
  "parameters": {
    "type": "object",
    "properties": {
      "customer_name": {"type": "string"},
      "address": {
        "type": "object",
        "properties": {
          "street":  {"type": "string", "description": "街道地址"},
          "city":    {"type": "string", "description": "城市"},
          "zip":     {"type": "string", "description": "邮编", "pattern": "^[0-9]{6}$"}
        },
        "required": ["street", "city", "zip"]
      }
    },
    "required": ["customer_name", "address"]
  }
}

**适用场景**：订单类、地址类、配置类工具——参数本身就是结构化的。

7.6.2 enum 限制

**用 `enum` 限制参数取值范围**——LLM 不会传错值。

{
  "name": "update_order_status",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string"},
      "status":   {
        "type": "string",
        "enum": ["pending", "paid", "shipped", "delivered", "cancelled"],
        "description": "订单状态"
      }
    },
    "required": ["order_id", "status"]
  }
}

**经验值**：**所有"状态/类型/分类"参数都该用 enum**——能消除 80% 的 LLM 幻觉参数。

7.6.3 anyOf 多态

**参数可以是多种类型之一**（如值可以是字符串或数字）。

{
  "name": "search",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "anyOf": [
          {"type": "string", "description": "搜索词"},
          {"type": "object", "properties": {"field": {"type": "string"}, "value": {"type": "string"}}}
        ]
      }
    },
    "required": ["query"]
  }
}

**适用场景**：搜索/筛选类工具——查询条件既可以是简单字符串也可以是结构化对象。

7.6.4 $ref 引用（Anthropic / Google 完整支持，OpenAI 有限支持）

**`$ref` 让多个工具共享同一个 schema 片段**——避免重复定义。

{
  "definitions": {
    "Address": {
      "type": "object",
      "properties": {
        "street": {"type": "string"},
        "city":   {"type": "string"},
        "zip":    {"type": "string"}
      },
      "required": ["street", "city", "zip"]
    }
  },
  "tools": [
    {
      "name": "ship_to_home",
      "parameters": {
        "type": "object",
        "properties": {
          "address": {"$ref": "#/definitions/Address"}
        }
      }
    },
    {
      "name": "ship_to_store",
      "parameters": {
        "type": "object",
        "properties": {
          "store_address": {"$ref": "#/definitions/Address"}
        }
      }
    }
  ]
}

**注意**：**OpenAI 2024-2025 不支持 `$ref`**——它用自定义子集。Anthropic / Google 完整支持。

7.6.5 4 个高级模式对照表

模式语法适用场景三家支持
**嵌套对象**`properties.address.properties.street`订单、地址、配置三家全支持
**enum**`enum: ["a", "b", "c"]`状态、类型、分类三家全支持
**anyOf**`anyOf: [{type: string}, ...]`搜索、筛选、多态输入三家全支持
**`$ref`**`$ref: "#/definitions/X"`多工具共享结构Anthropic/Google 完整，OpenAI 不支持

7.6.6 JSON Schema 5 大反例（与 ch06.3 工具描述军规呼应）

ch06.3 讲了"工具描述的 7 条军规"——那是**人类写 description 的规范**。本节讲**JSON Schema 本身**的 5 个常见反例——**写错了，LLM 调工具时就会出问题**。

#反例错在哪修复
**1**`description: "查订单"`（8 字符）description 太短，LLM 不知道何时调30-80 字符 + 场景 + 反例
**2**`status: {type: "string"}`（无 enum）LLM 传 `"canceled"`（美式）业务期望 `"cancelled"`（英式）`enum: ["pending", "paid", "shipped", "cancelled"]`
**3**`required: []`（没标必填）LLM 调工具时漏传关键参数显式列 `required: ["order_id", "amount"]`
**4**`parameters: {city: {type: "string"}}`缺外层 `type: "object"` 和 `properties`标准 4 件套：`type + properties + required + (additionalProperties)`
**5**多个相似工具 `get_order` / `get_order_detail` / `fetch_order_info`LLM 不知道该调哪个合并成 1 个工具 + `include_detail: bool` 参数

**5 反例 → 5 修复**——这套 checklist 在写生产工具时是**必过**的。

**关键概念摘要**：
- 嵌套对象 = 让参数"自带结构"
- enum = 限制 LLM 不传错值，**消除 80% 幻觉参数**
- anyOf = 多态输入
- `$ref` = 多工具共享（**OpenAI 不支持，要慎用**）
- JSON Schema 5 反例 = ch06 工具描述军规的"协议层补完"

7.7 工具调用错误处理 5 大模式

LLM 调工具时**不会自动重试**。错误处理是**业务代码的责任**。生产中最常见的 5 类错误：

7.7.1 错误 1：参数类型不匹配

LLM 传 `"3.14"`（字符串）给 `calculate(x: float)`，JSON Schema 校验失败。

**处理代码**：

try:
    result = func(**json.loads(arguments))
except TypeError as e:
    # 把错误信息作为 tool 结果回传，让 LLM 自己修正
    result = {"error": f"参数类型错误: {e}", "hint": "请检查参数类型"}
    messages.append({
        "role": "tool", "tool_call_id": tool_call.id,
        "content": json.dumps(result, ensure_ascii=False)
    })
    # 继续主循环，让 LLM 重试

7.7.2 错误 2：必填字段缺失

LLM 调 `get_weather()` 但没传 `city`。

**处理代码**：

try:
    args = json.loads(arguments)
    if "city" not in args:
        raise ValueError("missing required field: city")
    result = func(**args)
except (ValueError, TypeError) as e:
    result = {"error": str(e), "hint": "请补全必填字段"}
    # 同 7.7.1 回传

7.7.3 错误 3：工具执行异常

数据库连接失败、API 限流、文件不存在。

**处理代码**：

import logging
try:
    result = func(**args)
except Exception as e:
    logging.exception(f"Tool {func_name} failed")
    result = {"error": f"{type(e).__name__}: {e}", "recoverable": True}
    # 把"业务异常"也回传给 LLM——让它决定是换工具还是重试

7.7.4 错误 4：工具超时

工具执行时间过长（如查数据库 30s 没返回）。

**处理代码**：

import concurrent.futures

def call_with_timeout(func, args, timeout_sec=10):
    with concurrent.futures.ThreadPoolExecutor() as ex:
        future = ex.submit(func, **args)
        try:
            return future.result(timeout=timeout_sec)
        except concurrent.futures.TimeoutError:
            return {"error": f"Tool timeout after {timeout_sec}s", "hint": "请重试或换工具"}

7.7.5 错误 5：工具返回超大结果

工具返回了 1MB 文本——超过 LLM context window。

**处理代码**：

def truncate_result(result: dict, max_chars: int = 5000) -> dict:
    text = json.dumps(result, ensure_ascii=False)
    if len(text) > max_chars:
        # 截断 + 提示 LLM 缩小范围
        return {
            "warning": f"结果已截断（{len(text)} → {max_chars} 字符）",
            "data": text[:max_chars],
            "hint": "请缩小查询范围"
        }
    return result

7.7.6 5 大错误模式对照表

错误触发条件处理策略是否回传 LLM
**类型不匹配**`TypeError`错误信息 + 类型提示✅
**必填缺失**`ValueError`缺失字段名 + 提示✅
**业务异常**DB/API 异常异常类名 + 消息 + 标记 `recoverable`✅
**超时**>10s超时时长 + 重试提示✅（让 LLM 决定）
**超大结果**>5000 字符截断 + 缩小范围提示✅（带 warning）

**核心原则**：**所有 5 类错误都要回传 LLM**，让 LLM 决定下一步（重试/换工具/告诉用户）。**不要静默吞掉错误**——LLM 不知道发生了什么，会卡死。

7.7.7 错误处理决策树

5 类错误处理方式不是"一视同仁"——**根据错误类型决定是让 LLM 重试，还是直接告诉用户**。下面是**业务级**的判断流程：

工具执行出错
    │
    ├── 1. 是否是参数错误（类型 / 必填缺失）？
    │   ├─ YES → 回传 LLM，让 LLM 修正（重试率高）
    │   └─ NO ↓
    │
    ├── 2. 是否是临时业务错误（DB 连接 / API 限流）？
    │   ├─ YES → 业务层重试 1-2 次，失败后回传 LLM（标记 recoverable: true）
    │   └─ NO ↓
    │
    ├── 3. 是否是逻辑错误（找不到订单 / 权限不足）？
    │   ├─ YES → 不重试，直接回传 LLM（让 LLM 决定是否告诉用户）
    │   └─ NO ↓
    │
    ├── 4. 是否是超时？
    │   ├─ YES → 重试 1 次（不同 endpoint），失败后回传 LLM
    │   └─ NO ↓
    │
    └── 5. 是否是超大结果？
        └─ YES → 业务层截断，回传 LLM（带 warning + 缩小范围建议）

**4 条决策原则**：

  • **可重试错误**（参数 / 临时业务 / 超时）：**业务层先重试 1-2 次**，失败再回传 LLM
  • **不可重试错误**（逻辑 / 权限）：**直接回传 LLM**，让 LLM 决定下一步
  • **所有错误必须带 `recoverable: true/false` 标记**——LLM 看到标记后能更聪明地决策
  • **业务层最多重试 2 次**——超过 2 次是浪费 token，应该让 LLM 换策略
**关键概念摘要**：
- 5 大错误：类型 / 必填 / 业务异常 / 超时 / 超大
- 所有错误都**回传 LLM**——LLM 不会自动重试，但能看到错误信息
- 超时用 `concurrent.futures` 包裹（10s 是常见阈值）
- **可重试 vs 不可重试**是错误处理决策树的核心维度
- 业务层最多重试 2 次

7.8 流式 Tool Calls（OpenAI 2024+）

当工具参数特别长（如 3000 字符 JSON），等整个响应完整返回太慢。**流式 tool calls** 让 LLM **一边生成参数一边回传**——你的代码可以**增量解析**。

7.8.1 为什么需要流式

场景非流式流式
参数长度3000 字符3000 字符
首字节延迟等所有 token 生成完（~5s）第 1 个 token 即可处理（~0.2s）
总耗时5s5s（一样）
适用短参数长参数 / 用户可感知延迟的场景

7.8.2 完整实战代码

"""
OpenAI 流式 Tool Calls——增量解析长参数。
"""
import json
from openai import OpenAI

def run_streaming_tool_call():
    client = OpenAI()
    stream = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": "生成一个 3000 字的 markdown 报告"}],
        tools=[{
            "type": "function",
            "function": {
                "name": "save_report",
                "description": "保存报告",
                "parameters": {
                    "type": "object",
                    "properties": {
                        "content": {"type": "string"}
                    },
                    "required": ["content"]
                }
            }
        }],
        stream=True,
    )

    # 增量累积 tool_calls
    tool_call_buffer = {}   # index -> {id, name, arguments_str}
    for chunk in stream:
        if not chunk.choices:
            continue
        delta = chunk.choices[0].delta
        # 注意：delta.tool_calls 在 OpenAI 不同版本可能是 None 或 []，统一用 `if not ...` 兼容
        if not delta.tool_calls:
            # 普通文本流
            if delta.content:
                print(delta.content, end="", flush=True)
            continue

        # 工具调用流——按 index 累积
        for tc in delta.tool_calls:
            idx = tc.index
            if idx not in tool_call_buffer:
                tool_call_buffer[idx] = {
                    "id": tc.id or "",
                    "name": tc.function.name if tc.function else "",
                    "arguments_str": ""
                }
            if tc.id:
                tool_call_buffer[idx]["id"] = tc.id
            if tc.function and tc.function.name:
                tool_call_buffer[idx]["name"] = tc.function.name
            if tc.function and tc.function.arguments:
                tool_call_buffer[idx]["arguments_str"] += tc.function.arguments

    # 流结束后，解析累积的 arguments
    print("\n--- Tool calls received ---")
    for idx, tc in tool_call_buffer.items():
        args = json.loads(tc["arguments_str"])
        print(f"  {tc['name']}({args})")

if __name__ == "__main__":
    run_streaming_tool_call()

**3 个关键点**：

  • `stream=True` 开启流式
  • `chunk.choices[0].delta.tool_calls` 是**增量数组**（不是完整对象）
  • 用 `tc.index` 作为 key，**累积同一调用的多个 chunk**——最后解析

7.8.3 流式 vs 非流式 选型对照表

场景推荐方式原因
**参数 < 500 字符**非流式流式增量累积反而增加复杂度
**参数 500-2000 字符**都可以差异不大，按团队习惯
**参数 > 2000 字符****流式**首字节延迟从 5s 降到 0.2s
**用户可感知延迟**（聊天 UI）**流式**用户能看到"在生成中"，体验更好
**后台批处理**（脚本）非流式无人感知，省复杂度
**参数极大 > 10000 字符****流式 + 业务截断**避免 OOM
**关键概念摘要**：
- 流式 tool calls = `stream=True` + `delta.tool_calls` 增量累积
- 用 `tc.index` 作为累积 key
- 适用：长参数（>1000 字符 JSON）+ 用户可感知延迟场景
- **参数 < 500 字符不必用流式**——增加复杂度收益小
- **参数 > 10000 字符必用流式 + 截断**——避免 OOM 是硬要求

7.10 Function Calling 5 大坑

7.10.1 坑 1：tools 太多让 LLM 选错

**症状**：Agent 给了 30 个工具，LLM 经常选错——成功率 60%。

**原因**：context window 里塞 30 个 JSON Schema 描述，LLM 注意力分散。

**修复**：

  • **分层声明**：高频工具放 system prompt，低频工具按需动态注入
  • **合并相似工具**：5 个"查订单"工具 → 1 个带 `order_type` 参数的工具
  • **经验值**：**单个对话中 tools ≤ 10 个**是甜区

7.10.2 坑 2：description 太短

**症状**：`description: "查询订单"`（8 字符）——LLM 不知道这个工具和 `get_order_detail` 的区别。

**修复**：

  • description 至少 30-80 字符
  • 包含**使用场景**（"当用户问订单状态、退款、物流时调用"）
  • 包含**反例**（"不要用于查询用户信息"）

7.10.3 坑 3：不用 enum 限定

**症状**：status 参数没 enum，LLM 传 `"canceled"`（美式拼写），但代码期望 `"cancelled"`（英式）。

**修复**：`enum: ["pending", "paid", "shipped", "delivered", "cancelled"]`——LLM 100% 不会拼错。

7.10.4 坑 4：忽略并行调用

**症状**：用户问"查北京和上海天气"——LLM 串行调 2 次 `get_weather`，多花 1 倍时间。

**修复**：`parallel_tool_calls=True`（OpenAI 默认），让 LLM 一次返回 2 个 `tool_call`，业务代码并发执行。

7.10.5 坑 5：不处理 tool 错误就回 LLM

**症状**：工具执行失败，业务代码直接 `raise`——LLM 看不到错误，主循环崩。

**修复**：所有 5 类错误（见 7.7）**都包装成 `{"error": "..."}` 回传**——LLM 看到错误会自己决定重试或换工具。

7.10.6 5 大坑 × 修复对照表

坑症状修复修复后效果
**tools 太多**选错率 40%分层 / 合并，≤10 个选错率 < 10%
**description 太短**LLM 不知道何时调30-80 字符 + 场景 + 反例选对率 +20 pp
**不用 enum**拼写错enum 限定拼写错率 0%
**忽略并行**时间 ×2`parallel_tool_calls=True`时间 -50%
**不处理错误**主循环崩包装成 `{"error": ...}` 回传健壮性 +++

7.11 本章小结 + 概念速查 + 概念桥

7.11.1 8 条速记

  • **Function Calling = LLM 输出调用意图 + 代码真执行**——LLM 不再"假装算"
  • **2025 年三家协议趋同**：都叫 "tool"，都用 JSON Schema，都支持并行和流式
  • **OpenAI 协议核心**：`tools` 字段 + `tool_calls` 响应 + `role="tool"` 回传 + `tool_call_id` 配对
  • **Anthropic 协议核心**：`system` 独立 + `content` block 数组 + `tool_use` / `tool_result` 配对 + `role="user"` 回传
  • **Google 协议核心**：`system_instruction` 独立 + `function_declarations` 嵌套 + `parts[].function_call` + `function_response` 回传（**直接传 dict**）
  • **JSON Schema 高级模式**：嵌套对象、enum、anyOf、`$ref`（OpenAI 不支持 `$ref`）
  • **5 大错误处理**：类型 / 必填 / 业务异常 / 超时 / 超大——**全部回传 LLM**
  • **流式 tool calls** = `stream=True` + `delta.tool_calls` 增量累积，按 `tc.index` 拼参数

7.11.5 选型决策树：3 家协议选谁

读完本章你可能会问："**我应该用哪家协议？**" 下面是**业务级**的选型决策树：

Q1: 你的预算敏感吗？
├─ 高度敏感 → Google Gemini（性价比最高，免费层厚）
└─ 不敏感 ↓

Q2: 你的任务是"严谨逻辑"（代码 / 推理 / 长文档）？
├─ 是 → Anthropic Claude（严谨，200K context）
└─ 否（创意 / 通用）↓

Q3: 你需要最成熟的生态（最多教程 / 最大社区）？
├─ 是 → OpenAI（行业事实标准，工具链最丰富）
└─ 否 → 回到 Q1

Q4: 你需要 3 家同时支持（多模型 fallback）？
└─ 是 → 协议抽象层（LangChain / LlamaIndex 都支持，ch04 框架选型）

**4 条经验值**：

  • **创业公司 MVP**：默认 OpenAI（最成熟，文档最全）
  • **企业级生产**：Anthropic（严谨 + 200K context + 安全）
  • **成本敏感项目**：Google（Flash 系列便宜 70%）
  • **多模型路由**：用 LangChain / LlamaIndex 抽象层，**不要硬编码到某家**
**关键概念摘要**：
- **MVP 选 OpenAI**（成熟 + 文档）
- **企业选 Anthropic**（严谨 + 安全）
- **成本敏感选 Google**（便宜 70%）
- **多模型用框架抽象**（LangChain / LlamaIndex）
- **协议选 OpenAI 但成本敏感时** → 选 OpenAI GPT-4o-mini 而不是 GPT-4o（输入 $0.15/M vs $2.5/M tokens，便宜 16 倍）
