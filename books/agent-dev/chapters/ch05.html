# 第 5 章 Agent 范式对比——ReAct、Reflexion、Plan-and-Execute、Tool-Use、Function Calling

在 ch03 我们搭好了"大脑 + 记忆 + 工具 + 规划"四大件，在 ch04 选了 7 个框架之一来装这四大件。但四大件和框架都是"硬件"——真正决定 Agent 表现的是"软件"：思维范式（paradigm）。这一章我们把 2024-2026 年业界最常用的 5 种思维范式（ReAct / Reflexion / Plan-and-Execute / Tool-Use / Function Calling）全部拆开看，并给读者一份"任务 → 范式"的速查表。这一章也是第一部分 5 章的收官——末尾会有第一部分复盘。

5.1 引子：为什么单 prompt 解决不了"多步 + 错误恢复"

先看一个真实场景：用户问 Agent ——

"查北京明天的天气，如果下雨就提醒我带伞，并把提醒加到我的日历。"

把这句话直接发给 LLM 会发生什么？99% 的情况下 LLM 会自信地编造一个答案（"北京明天有雨，记得带伞"），但根本不会真的查天气，也不会真的写日历。这就是 ch01 提到的"幻觉"。

一个"能跑"的 Agent 必须多步、且能容错：

1. 理解"查天气" → 决定调用工具 get_weather(city="北京", date="2026-06-15")
2. 拿到结果"有雨" → 决定调用工具 send_reminder(content="带伞", calendar="primary")
3. 写完日历 → 总结回复用户

这 3 步每一步都可能失败（网络断、API key 错、日历满了）。单次 LLM 调用无法处理这种"边做边决定"的任务——我们需要给 LLM 一个思维循环（paradigm），让它在每一步都能"想 → 做 → 看结果 → 继续"。

5.1.1 单 LLM 调用的 3 大失败模式

失败模式 表现 例子
幻觉 LLM 编造看似合理但虚构的结果 "北京明天 23℃，有雨"——根本没查
工具不会用 用户说要"加日历"，LLM 给一段文字提示而不是真调用 "你可以在日历 App 里加一条提醒"
中途错了不知道回头 第一步错了，LLM 继续自信地往下编 天气 API 返回错误，LLM 编造"查到了晴天"
范式 = LLM 的"思维结构"，框架是承载它的"语法"。本章介绍 5 种最常用的范式。

5.2 ReAct——Reason + Act 交替进行

ReAct（Reasoning + Acting）是 2022 年由 Shunyu Yao 等人在论文 ReAct: Synergizing Reasoning and Acting in Language Models 中提出的范式。它的核心思想可以用一句话概括：
让 LLM 在每一步都"先想（Thought）→ 再做（Action）→ 看完结果（Observation）→ 再想 ..."。

5.2.1 核心循环

┌─────────────────────────────┐
│ Thought: 我需要先查天气     │
│ Action: get_weather("北京") │
└─────────────┬───────────────┘
              ↓
┌─────────────────────────────┐
│ Observation: "有雨"         │
│ Thought: 应该提醒用户带伞   │
│ Action: send_reminder(...)  │
└─────────────┬───────────────┘
              ↓
┌─────────────────────────────┐
│ Observation: "已加入日历"   │
│ Thought: 任务完成            │
│ Final Answer: 已提醒您带伞   │
└─────────────────────────────┘

ReAct 把"思考"和"行动"显式分开，每一步 LLM 都得"先说出为什么"再"说做什么"。这种显式推理让 Agent 在出错时更容易被发现（"咦，它第 3 步的 Thought 不对啊"）。

5.2.2 Hello World（30 行）

# react_demo.py —— 30 行 ReAct 最小可运行
import json
from typing import Callable


# 1) mock LLM：把"思考"和"动作"用文字协议连起来
def mock_llm(prompt: str) -> str:
    # 已经查到天气 + 还没发提醒 → 发提醒
    if "Observation: 有雨" in prompt and "Observation: 已加入日历" not in prompt:
        return "Thought: 下雨了，应该提醒用户\nAction: send_reminder(content=带伞)"
    # 已经发完提醒 → 收尾
    if "Observation: 已加入日历" in prompt:
        return "Thought: 任务完成\nFinal Answer: 已提醒您带伞"
    # 初始状态：还没查 → 查天气
    return "Thought: 需要查北京天气\nAction: get_weather(city=北京)"



# 2) mock 工具
tools: dict[str, Callable] = {
    "get_weather": lambda city: "有雨",
    "send_reminder": lambda content: "已加入日历",
}



# 3) ReAct 主循环
history = "用户问：北京明天天气如何？如果下雨提醒我带伞。\n"
for i in range(5):
    response = mock_llm(history)
    history += response + "\n"
    if "Final Answer" in response:
        print("✅", response.split("Final Answer:")[-1].strip())
        break
    # 解析 Action
    action_line = [l for l in response.split("\n") if l.startswith("Action:")][0]
    action_name = action_line.split("Action:")[1].split("(")[0].strip()
    result = tools[action_name]("北京" if "city" in action_line else "带伞")
    history += f"Observation: {result}\n"

输出： 
✅ 已提醒您带伞

5.2.3 优势 / 痛点

  • 优势：通用性最强，几乎所有 Agent 框架（LangChain ReAct Agent / LangGraph / OpenAI Agents SDK）都内置 ReAct
  • 痛点：每步都让 LLM "重新读历史"，token 消耗大；且"思考"可能不稳定（同一个问题两次跑出不同策略）

5.2.4 ReAct 在 ch04 7 框架中的"默认范式"地位

框架 是否默认 ReAct 备注
LangChain LCEL ✅ create_react_agent() 是模板
LangGraph ✅ StateGraph 默认 ReAct 循环
AutoGen v0.4 ⚠️ 部分 默认是 GroupChat，ReAct 是子集
CrewAI ❌ 默认 sequential Plan
LlamaIndex ⚠️ 部分 ReAct Agent 是插件
Agno ✅ 默认 ReAct 循环
OpenAI Agents SDK ✅ Runner 默认循环就是 ReAct
结论：7 个框架中 5 个把 ReAct 作为默认范式——这从工业界证明了 ReAct 的"基础地位"。

5.3 Reflexion——失败后"反思自己"

Reflexion 是 2023 年由 Noah Shinn 等人在论文 Reflexion: Language Agents with Verbal Reinforcement Learning 中提出的范式。它的核心创新是让 Agent 有了"短期记忆"：
当任务失败时，Agent 不是傻傻地再试一次，而是先"反思"自己哪里错了，写一段反思，然后带着反思再试。

5.3.1 核心循环

┌────────────────────────────────────────┐
│ Attempt 1                              │
│   Thought → Action → Observation: 失败  │
│   → 反思: "我用了错的城市名"            │
│         ↓                              │
│ Attempt 2 (带反思记忆)                  │
│   Thought: 反思说要用全名                │
│   Action: get_weather(city=北京市)     │
│   Observation: 成功                     │
│   → Final Answer                       │
└────────────────────────────────────────┘

5.3.2 Hello World（30 行）

# reflexion_demo.py —— 30 行 Reflexion 最小可运行
def mock_llm(prompt: str) -> str:
    if "反思" in prompt and "北京市" in prompt:
        return "Action: get_weather(北京市)\nObservation: 晴"
    if "反思" in prompt:
        return "Thought: 反思说要用全名\nAction: get_weather(北京市)"
    return "Action: get_weather(北京)\nObservation: 错误: 找不到城市"


def attempt(query: str, reflection: str = "") -> tuple[str, str]:
    full_prompt = f"反思: {reflection}\n{query}" if reflection else query
    result = mock_llm(full_prompt)
    return result, "错误" in result



# 主循环
memory = []
for trial in range(3):
    result, failed = attempt("查北京天气", " | ".join(memory))
    if not failed:
        print(f"✅ 第 {trial+1} 次成功: {result}")
        break
    memory.append(f"trial {trial+1}: 城市名要写全名")
    print(f"⚠️  第 {trial+1} 次失败,反思加入记忆")

输出： 
⚠️  第 1 次失败,反思加入记忆
✅ 第 2 次成功: Action: get_weather(北京市)
Observation: 晴

5.3.3 适用场景

  • 代码生成：HumanEval 评测里，Reflexion 把 pass@1 从 50% 提升到 91%
  • 多步任务：每步都可能错，且错误类型不固定（没法硬编码"如果错就重试"）
  • 不适用：单步任务 / 实时性要求极高（反思本身就要 LLM 调用，延迟 ×2）

5.3.4 Reflexion 在公开基准上的提升数据

基准任务 ReAct 基线 Reflexion 提升 来源
HumanEval（代码生成） 50% pass@1 91% pass@1（+41 pp，估算自论文 Table 2） Shinn et al. 2023
HotPotQA（多跳问答） 28% 45%（+17 pp） Shinn et al. 2023
AlfWorld（决策任务） 60% 82%（+22 pp） Shinn et al. 2023
WebShop（电商） 30% 51%（+21 pp） Shinn et al. 2023
关键观察：Reflexion 在所有 4 个公开基准上都有 15-41 个百分点的提升——这是罕见的"普适性"提升。但代价是每轮反思都要 1 次额外 LLM 调用，所以 token 消耗约 2-3 倍。

5.3.5 反思的"度"——别反思过头

Reflexion 论文假设"反思越深越好"，但 2025 年的实战经验告诉我们：

反思深度 收益 代价 适合
浅反思（"上次错了，再试"） +5% +1 LLM 调用 实时性敏感
中反思（"上次错在城市名，这次用全名"） +15% +1 LLM 调用 大多数场景
深反思（"上次错在没考虑闰年 + 城市名 + 工具超时，3 个原因"） +20% +3 LLM 调用 关键任务
给读者的经验法则：中反思是最甜的甜点——1 次反思 + 具体到变量 + 不抽象。

5.4 Plan-and-Execute——先想完，再做

Plan-and-Execute 是 2023 年由 LangChain 团队系统化推广的范式，灵感来自古典 AI 规划（PDDL, 2010）。它的核心思想：
把任务拆成两阶段——Planner 一次性生成完整计划，Executor 按步骤执行；如果某步失败，Replanner 修改计划。

5.4.1 核心循环

┌──────────────────────────────┐
│ Planner: 一次性输出完整计划    │
│ 1. 查天气                     │
│ 2. 判断是否需要提醒            │
│ 3. 调用日历 API               │
│ 4. 总结回复                   │
└──────────┬───────────────────┘
           ↓
┌──────────────────────────────┐
│ Executor: 逐步执行             │
│   step 1: get_weather → "有雨" │
│   step 2: 跳过(非必要)         │
│   step 3: send_reminder → 成功 │
│   step 4: 总结                │
└──────────────────────────────┘

5.4.2 Hello World（30 行）

# plan_execute_demo.py —— 30 行 Plan-and-Execute 最小可运行
def planner(task: str) -> list[str]:
    return [
        f"1. 拆解任务: {task}",
        "2. 调用工具 A",
        "3. 调用工具 B",
        "4. 总结结果",
    ]


def executor(steps: list[str]) -> list[str]:
    observations = []
    for i, step in enumerate(steps):
        if "工具 A" in step:
            observations.append(f"step {i+1}: A 返回 '数据 1'")
        elif "工具 B" in step:
            observations.append(f"step {i+1}: B 返回 '数据 2'")
        else:
            observations.append(f"step {i+1}: 已完成")
    return observations



task = "查北京天气 + 加日历"
plan = planner(task)
print("📋 计划:", plan)
obs = executor(plan)
print("👀 执行:", obs)
print("✅ 总结: 全部 4 步完成")

输出： 
📋 计划: ['1. 拆解任务: 查北京天气 + 加日历', '2. 调用工具 A', '3. 调用工具 B', '4. 总结结果']
👀 执行: ['step 1: A 返回 数据 1', 'step 2: B 返回 数据 2', 'step 3: 已完成', 'step 4: 已完成']
✅ 总结: 全部 4 步完成

5.4.3 优势 / 痛点

  • 优势：长链路任务（5+ 步）效率高，Planner 只调用 1 次，Executor 路径稳定
  • 痛点：计划可能"过期"（外部世界变了）；Planner 一次性想完 5 步，第 3 步的细节可能漏

5.5 Tool-Use 与 Function Calling——工具调用的"协议层"

Tool-Use（早期叫法，2023 H1）和 Function Calling（OpenAI 2023.6 提出）是同一种思想的两种叫法，2025 年后业界已统一用 Function Calling。它不是一种"思维范式"，而是一种协议规范——告诉 LLM "你可以调用这些工具，每个工具的入参是什么"。

5.5.1 核心思想

{
  "name": "get_weather",
  "description": "查询某城市某天的天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名"},
      "date": {"type": "string", "description": "日期 ISO8601"}
    },
    "required": ["city", "date"]
  }
}

LLM 收到这个 JSON Schema 后，会在响应里输出：

{
  "tool_calls": [{
    "function": {
      "name": "get_weather",
      "arguments": "{\"city\": \"北京\", \"date\": \"2026-06-15\"}"
    }
  }]
}
注意：Function Calling 本身不包含"循环"——它只规定"LLM 怎么告诉应用调用哪个工具"。循环逻辑是 ReAct / Plan-and-Execute 等范式负责的。把 Function Calling 当作"手"，把 ReAct/Plan 当作"脑"。

5.5.2 Hello World（30 行）

# function_calling_demo.py —— 30 行 OpenAI Function Calling 协议演示
import json


# 1) 工具描述（这是 2026 业界标准 JSON Schema 格式）
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询某城市某天的天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string"},
                "date": {"type": "string"}
            },
            "required": ["city", "date"]
        }
    }
}]



# 2) mock LLM 决策
def mock_llm_decide(user_msg: str) -> dict:
    return {
        "tool_calls": [{
            "function": {
                "name": "get_weather",
                "arguments": json.dumps({"city": "北京", "date": "2026-06-15"})
            }
        }]
    }



# 3) 工具实现
def get_weather(city: str, date: str) -> str:
    return f"{city} {date}: 晴, 23℃"



# 4) 调用流程
user_msg = "查北京明天天气"
decision = mock_llm_decide(user_msg)
fc = decision["tool_calls"][0]["function"]
args = json.loads(fc["arguments"])
result = get_weather(**args)
print(f"用户: {user_msg}")
print(f"LLM 决定调用: {fc['name']}({args})")
print(f"工具返回: {result}")

输出： 
用户: 查北京明天天气
LLM 决定调用: get_weather({'city': '北京', 'date': '2026-06-15'})
工具返回: 北京 2026-06-15: 晴, 23℃

5.5.3 与 ReAct / Plan-and-Execute 的关系

维度 Function Calling ReAct Plan-and-Execute
本质 协议（"手"） 思维循环（"脑"） 思维循环（"脑"）
循环 ❌ 单次 ✅ 多步 ✅ 多步
错误恢复 ❌ ⚠️ 需自实现 ✅ Replanner
OpenAI 2023.6 ✅ 首创 ❌ ❌
Anthropic 2024.10 / Gemini 2024.7 ✅ 跟进 ❌ ❌
关键洞察：Function Calling + ReAct 是最佳拍档——Function Calling 负责"LLM 怎么告诉应用调工具"，ReAct 负责"调完后下一步做什么"。OpenAI Agents SDK / LangChain LCEL / Anthropic Claude tool_use 全都支持这两个。

5.5.4 Tool-Use 到 Function Calling 的标准化时间线

时间 事件 标志
2023 H1 Tool-Use 早期叫法 ReAct 论文 / LangChain 早期文档用"tool"
2023.6 OpenAI Function Calling 发布 gpt-3.5/gpt-4 引入 tools 字段
2023.10 Anthropic Claude tool_use 对标 OpenAI 协议
2024.4 OpenAI Parallel Function Calling 一次响应调多个工具
2024.7 Google Gemini Function Calling 三大厂商全部支持
2024.12 OpenAI Structured Outputs JSON Schema 强校验

关键洞察：Function Calling 不只是协议——它是 2023-2025 年 Agent 爆发的技术前提。没有这个协议，LLM 没法"结构化地"告诉应用调哪个工具，ReAct 范式就无法工业化。

5.6.2 选型决策树

Q1: 任务是单步还是多步（≥3 步）？
├─ 单步 → Function Calling（直接调）
└─ 多步 → Q2
    Q2: 任务是否会失败？失败模式是否可预测？
    ├─ 失败模式可预测（如网络断 → 重试）+ 流程相对固定 → **Plan-and-Execute**（低 token）
    ├─ 失败模式不可预测（API 返回奇怪结果） → Reflexion
    └─ 几乎不会失败 → ReAct（最通用）
        Q3: 实时性要求？
        ├─ 极低（< 100ms 不可接受） → Plan-and-Execute（少调 LLM）
        └─ 正常 → ReAct
给读者的速记公式：
  • 80% 场景：ReAct + Function Calling（业界默认）
  • 长链路 + 固定流程：Plan-and-Execute + Function Calling
  • 从错误学习：Reflexion
  • 单次工具调用：Function Calling 单独用

5.7 范式混搭：实战中的"积木组合"

范式不是"二选一"，是"积木"。2026 年所有生产级 Agent 都是混搭。3 个最常见的组合：

5.7.1 组合 1：Plan-and-Execute + ReAct（"先粗想再边想边做"）

  • 用法：Planner 给出"粗计划"，每步执行时用 ReAct 细化
  • 典型场景：OpenAI Deep Research
  • 优势：避免 Plan-and-Execute 计划过期，又避免 ReAct 每步都重新规划

5.7.2 组合 2：Plan-and-Execute + Reflexion（"计划失败后反思重排"）

  • 用法：Replanner 在计划失败时调用 Reflexion 反思
  • 典型场景：AutoGen v0.4 的 OnCondition 流程
  • 优势：长链路 + 容错

5.7.3 组合 3：ReAct + Function Calling（"基本款"）

  • 用法：ReAct 负责"想 → 做 → 看 → 再想"，Function Calling 负责"做的协议"
  • 典型场景：90% 的简单 Agent / Cursor Agent
  • 优势：最简单、最通用

5.8 范式实现 5 大坑

5.8.1 循环不终止（无 max_iter）

  • 症状：Agent 一直循环，永远停不下来
  • 修复：强制设 max_iterations=10，超过就 fallback 到"无法完成"
  • 代码片段：
  MAX_ITER = 10
  for i in range(MAX_ITER):
      if done: break

5.8.2 反思幻觉（反思本身可能错）

  • 症状：Reflexion 反思了"用全名"，但其实问题不在城市名
  • 修复：反思结果让 LLM 重新审视，而不是直接相信
  • 代码片段：
  # 不要直接用反思
  next_prompt = f"反思: {reflection}\n{query}"
  # 而是先验证反思
  next_prompt = f"反思: {reflection}\n验证反思是否对: {query}"

5.8.3 计划过期（外部世界变了）

  • 症状：Plan-and-Execute 计划 10 步，第 5 步时 API 已变更
  • 修复：Replanner 在每步前检查环境（"API 还在吗？"）
  • 代码片段：
  for step in plan:
      if not env_check(step):
          plan = replanner.replan(plan, step, env)

5.8.4 Token 爆炸（每步都重新读历史）

  • 症状：第 20 步时 history 已经有 50K token，单次 LLM 调用 5 美元
  • 修复：用 LangChain 的 ConversationSummaryMemory 压缩历史
  • 代码片段：
  # ch08 会讲
  from langchain.memory import ConversationSummaryMemory
  memory = ConversationSummaryMemory(llm=llm)

5.8.5 工具描述不清（LLM 选错工具）

  • 症状：3 个相似工具，LLM 选错
  • 修复：工具描述举例 + 边界（"用 city 参数传全名，例如 '北京市' 而非 '北京'"）
  • 代码片段：
  {"description": "查询天气。⚠️ city 必须传全名,如'北京市'或'上海市',否则 404"}

5.10 本章小结

关键概念摘要：
  • ReAct（2022, Yao）—— Thought → Action → Observation 循环，最经典的 Agent 范式
  • Reflexion（2023, Shinn）—— 失败时把反思写进记忆，下次带反思再试
  • Plan-and-Execute（2023, LangChain）—— Planner 一次性出计划，Executor 按步执行
  • Function Calling（2023.6, OpenAI）—— 工具调用的协议层，规定"LLM 怎么告诉应用调哪个工具"
  • Tool-Use（2023 H1）—— Function Calling 的旧名，2025 已统一叫 Function Calling
  • Replanner —— Plan-and-Execute 中负责"计划失败后重新规划"的组件
  • Reflexion Memory —— 短期反思记忆，存的是"上次哪里错了"
  • JSON Schema 工具描述 —— 2026 业界标准格式
  • max_iterations —— 循环硬终止，避免 Agent 跑飞
  • Plan 过期 —— 计划生成后外部世界变化
  • Token 爆炸 —— 长 history 累积导致 LLM 调用昂贵
  • Function Call —— 单次 LLM 响应中包含的工具调用请求
  • Tool Choice —— OpenAI 协议中指定"强制调用某个工具 / 自动选 / 不调用"
  • Parallel Function Calling —— 2024 引入，单次响应调用多个工具
  • Streamed Function Call —— 2025 引入，边流式输出边调工具
  • Structured Output —— 让 LLM 直接输出 JSON 而非自然语言
  • Tool Sandbox —— 工具执行的沙箱环境（防止 LLM 误删文件）
  • Reflexion Token 预算 —— 反思不能无限调用
  • Planner Token 预算 —— 计划不能太长
  • Schema Validation —— 工具参数必须符合 JSON Schema

5.10.1 8 条速记

  1. ReAct = 边想边做，最经典的循环范式，80% 场景用它
  2. Reflexion = 失败后反思，适合"从错误中学习"的任务（代码生成 / 多步推理）
  3. Plan-and-Execute = 先想完再做，适合长链路（5+ 步）+ 流程固定
  4. Function Calling 是"协议"不是"范式"——它规定 LLM 怎么告诉应用调工具，循环由 ReAct/Plan 负责
  5. 范式是积木——90% 生产 Agent 是 ReAct + Function Calling（基本款）或 Plan + ReAct（长链路）
  6. 5 大坑：循环不终止 / 反思幻觉 / 计划过期 / Token 爆炸 / 工具描述不清
  7. OpenAI Deep Research = Plan + ReAct + Function Calling 三范式组合
  8. 别上来就 ReAct + Reflexion + Plan 全用——先跑通基本款，按需加复杂度
