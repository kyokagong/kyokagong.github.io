章节定位: 第二部分（核心技术）第 4 章。ch06 prompt 是"模型怎么看指令"，ch07 Function Calling 是"模型怎么动手"，ch08 记忆是"结果存哪 + 怎么找回"，ch09 RAG 是"怎么把外部知识塞进模型回答里"——记忆的工程化。

9.1 引子：为什么需要 RAG

大模型（LLM）看似无所不知，实际上有 3 大固有局限：

  1. 知识截止：GPT-4o 训练数据截至 2023-10，Claude 3.7 Sonnet 截至 2025-01，Gemini 2.0 截至 2024-08。问"2025 年的诺贝尔物理学奖得主是谁"，任何模型都会卡壳——它没看过那份数据。
  2. 幻觉（Hallucination）：模型在不确定时会自信地编造。问"Transformer 论文的 arXiv ID 是什么"，它可能随口说一个 "arXiv:1706.01234"——这个 ID 真实存在但内容完全不同。
  3. 私有知识盲区：你公司的内部文档、产品手册、客户合同，模型完全没见过。问"我们 Q3 的退款率是多少"，它只能瞎猜。

RAG（Retrieval-Augmented Generation，检索增强生成） 的核心思想简单得令人发指——

给模型一本开卷考试的参考书。

传统 LLM = 闭卷考试（靠训练时记住的所有东西答题）；RAG = 开卷考试（先查资料，再带着资料答题）。Lewis et al. 2020 的原论文把这种范式称为 general-purpose fine-tuning becomes both inefficient and ineffective，并用 5 个 NLP 任务上的实验证明：哪怕是已经预训练好的模型，加上检索这一步都能把效果推高 5-20 个百分点。

到 2025 年，RAG 已经从"一种可选优化"变成"生产 Agent 的默认配置"。原因有三：① 开源 embedding 模型成熟（BGE-large-zh / M3E / Nomic）让本地 RAG 零成本 ② 向量库基础设施完善（Chroma / FAISS / Milvus / Pinecone）让 PB 级数据毫秒级检索 ③ Agentic RAG 范式让"何时检索"变成 Agent 自主决策，不再是机械的"每个问题都先检索一遍"。

9.2 RAG 基础 5 阶段流水线

RAG 的核心是 5（或 7）阶段流水线。哪怕是 Naive RAG，也必须走完这条流水线——只是每阶段做得粗糙而已。

9.2.3 完整 Naive RAG Python 实现（30 行可运行）

"""
第 9.2.3 节: 完整 Naive RAG 流水线（30 行 mock 版）
- Document: 内置 4 篇文档（避免文件依赖）
- Chunk: RecursiveCharacterTextSplitter mock
- Embed: mock_embed (deterministic)
- Store: MockChroma（dict 后端）
- Retrieve: top-K cosine
- Augment: 直接拼接到 system prompt
- Generate: mock_llm (基于 chunk 关键词)
"""
import re
from collections import defaultdict

# === 1. 文档加载（4 篇模拟文档）===
DOCS = [
    {"id": "doc1", "text": "RAG（Retrieval-Augmented Generation）由 Lewis et al. 在 2020 年提出。它的核心思想是把外部知识库的内容检索出来后，作为上下文送给语言模型。"},
    {"id": "doc2", "text": "向量数据库是 RAG 的核心组件。常见的有 Chroma（本地）、FAISS（Facebook 开源）、Milvus（自部署）、Pinecone（全托管云服务）。"},
    {"id": "doc3", "text": "Embedding 模型负责把文本变成向量。OpenAI 的 text-embedding-3-small 维度 1536，每百万 token 收费 $0.02。BGE 是开源的中文 embedding 模型。"},
    {"id": "doc4", "text": "Agentic RAG 是 2024-2025 年最热的 RAG 范式。它的核心是把'何时检索、检索什么、怎么用结果'的决策权交给 Agent，而不是固定的流水线。"},
]

# === 2. 切分（mock RecursiveCharacterTextSplitter）===
def chunk_text(text, chunk_size=80, overlap=10):
    """递归按中英文标点切分，chunk_size 单位是字符"""
    chunks = []
    start = 0
    while start < len(text):
        end = min(start + chunk_size, len(text))
        # 优先在句号/逗号处断开
        cut_at = end
        for sep in ["。", "，", "；", ".", ",", " "]:
            idx = text.rfind(sep, start, end)
            if idx > start + chunk_size // 2:
                cut_at = idx + 1
                break
        end = cut_at
        chunks.append(text[start:end].strip())
        # 关键：保证 start 严格递增，避免末尾 overlap 把指针回退导致死循环
        start = max(end - overlap, start + 1)
    return [c for c in chunks if c] + ([text[-overlap:].strip()] if start > 0 and end < len(text) and text[end:].strip() else [])

# === 3. Embedding（mock，deterministic）===
def mock_embed(text):
    """基于字符 hash 生成 8 维伪向量（demo 用，真实场景调 BGE/OpenAI API）"""
    vec = [0.0] * 8
    for i, ch in enumerate(text[:32]):
        vec[i % 8] += (ord(ch) % 13) / 100.0
    norm = sum(v * v for v in vec) ** 0.5
    return [v / norm for v in vec]

def cosine_sim(a, b):
    return sum(x * y for x, y in zip(a, b))

# === 4. 向量库（MockChroma）===
class MockChroma:
    def __init__(self):
        self.docs = []  # [(chunk_text, doc_id, embedding)]
    def add(self, chunks_with_ids, embeddings):
        for (text, doc_id), emb in zip(chunks_with_ids, embeddings):
            self.docs.append((text, doc_id, emb))
    def query(self, query_emb, top_k=3):
        scored = [(cosine_sim(query_emb, emb), text, doc_id)
                  for text, doc_id, emb in self.docs]
        scored.sort(reverse=True)
        return scored[:top_k]

# === 5. Build index ===
store = MockChroma()
all_chunks = []
for doc in DOCS:
    chunks = chunk_text(doc["text"])
    all_chunks.extend([(c, doc["id"]) for c in chunks])
embeddings = [mock_embed(c) for c, _ in all_chunks]
store.add(all_chunks, embeddings)

# === 6. Retrieve + Augment + Generate (mock) ===
def naive_rag(question, top_k=2):
    q_emb = mock_embed(question)
    results = store.query(q_emb, top_k=top_k)
    context = "\n".join([f"[{doc_id}] {text}" for _, text, doc_id in results])
    # Augment: 拼到 system prompt
    system_prompt = f"基于以下参考资料回答用户问题：\n{context}\n如果资料里没有答案，回答'我不知道'。"
    # Generate: mock_llm 根据 chunk 关键词选答案
    answer = f"根据资料 [{results[0][2]}]：{results[0][1][:50]}..."
    return answer, results

# === 7. Run ===
q = "什么是 Agentic RAG？"
ans, retrieved = naive_rag(q, top_k=2)
print(f"Q: {q}")
print(f"检索到的 Top-2 chunks:")
for score, text, doc_id in retrieved:
    print(f"  [{doc_id}] (sim={score:.3f}) {text[:40]}")
print(f"A: {ans}")

预期输出（mock_embed 排序稳定）：

Q: 什么是 Agentic RAG？
检索到的 Top-2 chunks:
  [doc4] (sim=0.741) Agentic RAG 是 2024-2025 年最热的 RAG 范式。它的核心是把...
  [doc2] (sim=0.612) 向量数据库是 RAG 的核心组件。常见的有 Chroma（本地）...
A: 根据资料 [doc4]：Agentic RAG 是 2024-2025 年最热的 RAG 范式。它的核心是把...
关键概念摘要：<br>- 5 阶段流水线是 RAG 的最小骨架——任何 RAG 都必须走完这 5 阶段<br>- Document / Chunk / Embed / Store / Retrieve / Augment / Generate 每阶段都有明确选型<br>- Naive RAG = 机械执行每阶段，Advanced RAG = 每阶段有优化策略，Agentic RAG = Agent 动态决策

9.3.4 RecursiveCharacterTextSplitter mock 实现

"""
第 9.3.4 节: RecursiveCharacterTextSplitter 的 mock 版
按 ["\n\n", "\n", "。", ".", " " , ""] 递归切分
"""
def recursive_split(text, chunk_size=200, overlap=30, separators=None):
    if separators is None:
        separators = ["\n\n", "\n", "。", ".", "，", ",", " "]
    if len(text) <= chunk_size:
        return [text] if text.strip() else []
    # 找最右的 separator（让 chunk 尽量贴近 chunk_size）
    sep = None
    for s in separators:
        idx = text.rfind(s, 0, chunk_size)
        if idx > chunk_size // 2:
            sep = s
            cut = idx + len(s)
            break
    if sep is None:
        # 强制按字符切
        cut = chunk_size
    first, rest = text[:cut], text[cut - overlap:]
    return [first] + recursive_split(rest, chunk_size, overlap, separators)

# 测试
long_text = """

向量数据库是 RAG 的核心组件。常见的有 Chroma（本地）、FAISS（Facebook 开源）、Milvus（自部署）、Pinecone（全托管云服务）。每种都有其适用场景。

"""

print(f"切分出 {len(chunks)} 个 chunk:")

9.4 Embedding 与向量库

9.4.1 与 ch08 §8.4 的对应关系

ch08 §8.4 已经讲过 embedding 与向量库的基础概念——本节聚焦 RAG 场景下的工程选型。同样的模型，在 RAG 和普通语义检索场景下的最优配置不一样：

9.5.3 Hybrid Retrieval（BM25 + 向量）mock 实现

"""
第 9.5.3 节: Hybrid Retrieval（BM25 + 向量混合检索）
- BM25: 基于词频的经典检索（精确匹配强）
- 向量: 基于 embedding 相似度（语义匹配强）
- 混合: 加权融合两路分数
"""
import math
import re
from collections import Counter, defaultdict

# === 复用 9.2.3 的 mock_embed / MockChroma ===
def mock_embed(text):
    vec = [0.0] * 8
    for i, ch in enumerate(text[:32]):
        vec[i % 8] += (ord(ch) % 13) / 100.0
    norm = sum(v * v for v in vec) ** 0.5
    return [v / norm for v in vec]

def cosine_sim(a, b):
    return sum(x * y for x, y in zip(a, b))

# === BM25 简易实现 ===
class SimpleBM25:
    def __init__(self, corpus):
        self.corpus = corpus  # list of strings
        self.docs = [self._tokenize(d) for d in corpus]
        self.df = defaultdict(int)  # 文档频率
        for doc in self.docs:
            for term in set(doc):
                self.df[term] += 1
        self.N = len(corpus)
        self.avgdl = sum(len(d) for d in self.docs) / max(self.N, 1)
    @staticmethod
    def _tokenize(text):
        # 简易中文分词：单字 + 词
        return [ch for ch in text if ch.strip()] + re.findall(r"[A-Za-z]+", text)
    def score(self, query, k1=1.5, b=0.75):
        tokens = self._tokenize(query)
        scores = [0.0] * self.N
        for t in tokens:
            df = self.df.get(t, 0)
            if df == 0: continue
            idf = math.log((self.N - df + 0.5) / (df + 0.5) + 1)
            for i, doc in enumerate(self.docs):
                tf = doc.count(t)
                if tf == 0: continue
                dl = len(doc)
                scores[i] += idf * (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * dl / self.avgdl))
        return scores

# === Hybrid Retrieval ===
class HybridRetrieval:
    def __init__(self, chunks_with_ids, alpha=0.5):
        # chunks_with_ids: [(text, doc_id), ...]
        self.texts = [t for t, _ in chunks_with_ids]
        self.ids = [i for _, i in chunks_with_ids]
        self.embeddings = [mock_embed(t) for t in self.texts]
        self.bm25 = SimpleBM25(self.texts)
        self.alpha = alpha  # 向量权重，1-alpha 是 BM25 权重

    def query(self, q_text, top_k=3):
        # 向量分数
        q_emb = mock_embed(q_text)
        vec_scores = [cosine_sim(q_emb, e) for e in self.embeddings]
        # BM25 分数（归一化到 [0, 1]）
        bm_scores = self.bm25.score(q_text)
        max_bm = max(bm_scores) if bm_scores and max(bm_scores) > 0 else 1
        bm_scores = [s / max_bm for s in bm_scores]
        # 混合
        hybrid = [self.alpha * v + (1 - self.alpha) * b
                  for v, b in zip(vec_scores, bm_scores)]
        ranked = sorted(zip(hybrid, self.texts, self.ids), reverse=True)
        return ranked[:top_k]

9.6 Agentic RAG（2025 最热方向）

9.6.1 本质：把决策权交给 Agent

Naive RAG 的死板：用户问什么都先检索一遍。哪怕问题是"你好"或者"今天星期几"。

Advanced RAG 的进步：每次都检索，但检索前/中/后做优化。

Agentic RAG 的革命：让 Agent 决定——

  • 这个问题要不要检索？（"你好" → 不检索）
  • 检索哪个知识库？（技术问题 → 文档库；闲聊 → 不检索）
  • 检索几次？（复杂问题 → 多轮检索）
  • 检索结果够不够？不够就换个 query 再检索。

9.6.2 3 种 Agentic RAG 模式对比

模式 Agent 数 决策粒度 代表工作 适用
:--- :---: :--- :--- :---
Single Agent + Tools 1 函数级 OpenAI Agents SDK + RAG tool 80% 场景首选
Multi-Agent RAG 2+ 任务级 Retriever Agent + Generator Agent 多源异构知识库
Corrective RAG (CRAG) 1 + 反思 检索级 CRAG 2024-01 高精度需求
Self-RAG 1 + 反思 token 决策级 Self-RAG 2023-10 学术研究
Adaptive RAG 1 + 路由器 查询级 Adaptive RAG 2024-03 arXiv（NAACL 2024） query 类型混杂

9.6.3 Single Agent + Tools RAG Python 实现

"""
第 9.6.3 节: Single Agent with Tools RAG
- Agent 决定：何时调用 search_docs、是否需要搜索、搜索几次
- mock_llm 根据用户 query 和工具返回决定下一步
"""
# 复用 §9.2.3 的 mock_embed / MockChroma
def mock_embed(text):
    vec = [0.0] * 8
    for i, ch in enumerate(text[:32]):
        vec[i % 8] += (ord(ch) % 13) / 100.0
    norm = sum(v * v for v in vec) ** 0.5
    return [v / norm for v in vec]

class MockChroma:
    def __init__(self): self.docs = []
    def add(self, texts, embs):
        for t, e in zip(texts, embs):
            self.docs.append((t, e))
    def query(self, q_emb, k=2):
        scored = sorted(self.docs, key=lambda x: -sum(a*b for a,b in zip(q_emb, x[1])))
        return [t for t, _ in scored[:k]]

# === Tool: search_docs ===
store = MockChroma()
docs = [
    "RAG（Retrieval-Augmented Generation）由 Lewis et al. 在 2020 年提出。",
    "向量数据库是 RAG 的核心组件。",
    "Embedding 模型负责把文本变成向量。",
    "Agentic RAG 是 2024-2025 年最热的 RAG 范式。",
]
store.add(docs, [mock_embed(d) for d in docs])

def search_docs(query, top_k=2):
    """RAG 检索工具：给 Agent 用的"""
    q_emb = mock_embed(query)
    results = store.query(q_emb, k=top_k)
    return "\n".join(f"- {r}" for r in results)

# === Agent 主循环（mock_llm 驱动）===
class AgentRAG:
    def __init__(self):
        self.tools = {"search_docs": search_docs}
        self.history = []
    def mock_llm(self, user_msg, history):
        # 决策 1: 闲聊 → 直接回答
        if any(kw in user_msg for kw in ["你好", "hello", "hi", "你是谁"]):
            return {"action": "final", "answer": "你好！我是 Agentic RAG 助手，可以帮你查 RAG 相关资料。"}
        # 决策 2: 已经有 tool result → 综合回答
        last_obs = next((m["content"] for m in reversed(history) if m["role"] == "tool"), None)
        if last_obs:
            return {"action": "final", "answer": f"根据检索：{last_obs[:80]}..."}
        # 决策 3: 知识类问题 → 调用 search_docs
        if any(kw in user_msg for kw in ["什么是", "是什么", "怎么", "核心"]):
            return {"action": "tool", "tool": "search_docs", "args": {"query": user_msg}}
        # 默认
        return {"action": "final", "answer": "我不确定这个问题，请换个问法。"}

    def run(self, user_msg, max_steps=3):
        self.history.append({"role": "user", "content": user_msg})
        for step in range(max_steps):
            decision = self.mock_llm(user_msg, self.history)
            if decision["action"] == "final":
                self.history.append({"role": "assistant", "content": decision["answer"]})
                return decision["answer"]
            elif decision["action"] == "tool":
                tool_fn = self.tools[decision["tool"]]
                result = tool_fn(**decision["args"])
                self.history.append({"role": "tool", "content": result})
        return "(超过最大步数)"

# === Run ===
agent = AgentRAG()
print("=== 测试 1: 闲聊（Agent 决定不检索）===")
print(agent.run("你好"))
print("\n=== 测试 2: 知识类问题（Agent 决定检索）===")
print(agent.run("什么是 RAG？"))

9.8.2 RAGAS 4 大核心指标

指标 含义 计算方式 期望
:--- :--- :--- :---:

Context Precision 检索内容的排名质量 排名前 K 的 chunk 中相关 chunk 的占比 > 0.75

9.9 RAG 与 Long-Context 的争论

9.9.1 2025 关键问题

context 已经 128K / 200K / 1M 了，还需要 RAG 吗？这是 2024-2025 年最热的争论。

Long-Context 派的观点：context 装得下，把所有文档直接塞进去，省去检索的麻烦。

RAG 派的反驳：context ≠ 万能。

9.9.2 3 大 RAG 不可替代场景

维度 Long-Context RAG 哪个赢
:--- :--- :--- :---:
成本 $5/M tokens（200K 上下文） $0.5/M（检索后 2K tokens） RAG（便宜 10 倍）
实时性 训练截止日之前 实时更新文档 RAG
精确性 Lost in the middle（中间信息丢失 30%） 命中即引用 RAG
可解释性 黑盒 明确来源 RAG
规模 上限 ~10M tokens 无上限（PB 级向量库） RAG
复杂度 直接塞 需要建索引 Long-Context

9.9.3 RAG / Long-Context / 混用 决策表

场景 推荐方案 理由
:--- :--- :---
文档 < 100K tokens Long-Context 即可 简单 + 一次性塞入
文档 100K-2M tokens RAG 成本 + 精确性优势明显
文档 > 2M tokens RAG 不可能塞进 context
实时更新数据 RAG 文档可即时写入向量库
需要溯源 RAG 每个 chunk 可标注来源
长文档摘要 + 关键信息检索 Long-Context + RAG 混用 Long-Context 理解全文 + RAG 精确定位
多文档交叉对比 Multi-doc RAG 跨文档检索 + cross-doc reasoning

2025 共识：RAG 不会消失，但会从"唯一方案"变成"工具之一"。Anthropic、Google、OpenAI 都同时支持 Long-Context + RAG——告诉用户在哪个场景用哪个。

关键概念摘要：<br>- RAG 的 3 大不可替代：成本 + 实时性 + 精确性<br>- 2025 共识：RAG + Long-Context 混用，而非二选一<br>- 文档 > 100K tokens → RAG 永远是首选

9.10 5 大坑

9.10.1 5 大坑 × 修复表

# 坑 症状 修复
:---: :--- :--- :---
1 chunk 切太大切不到答案 答案在段落中间，被截断 用 Recursive 切分 + chunk_size ≤ 512
2 embedding 模型不匹配 中文用英文模型 → 检索质量差 30-50%（经验值，未公开基准） 中文必须用 BGE-large-zh / M3E / text-embedding-3-large
3 top-K 固定不变 K=5 总是太多或太少 让 Agent 动态决定 K，或根据 query 复杂度调
4 不评估就上线 faithfulness = 60% 都不知道 上线前必跑 RAGAS 4 指标
5 忽略 chunk metadata 文档来源 / 时间戳丢失，无法溯源 切分时保留 doc_id / section / page metadata

9.10.2 5 大坑深度诊断

坑 1：chunk 切太大——最隐蔽的 RAG 失败模式。症状是"答案其实在文档里，但检索不出来"。诊断方法：手工查 top-10 检索结果，看答案所在段落是否被切碎。修复：用 RecursiveCharacterTextSplitter，把 chunk_size 从 1024 降到 512，overlap 从 100 降到 50。

坑 2：embedding 模型不匹配——用 text-embedding-3-small 处理中文 PDF，检索质量会比 BGE-large-zh 低 30-50%（经验值，未公开基准；通用生产结论）。诊断：把 5 篇已知答案的中文文档塞进 RAG，跑 RAGAS Context Recall，看是否 < 0.5。修复：中文场景强制用 BGE-large-zh-v1.5 或 M3E-large。

坑 3：top-K 固定——K=5 对短答案问题太多，对长答案问题太少。诊断：观察 top-5 里有几个 chunk 与 query 相关。修复：让 Agent 动态选 K，或在 ReAct 框架下让 LLM 决定"还要不要再检索一次"。

坑 4：不评估——生产 RAG 上线 1 个月后才发现 faithfulness=0.6，user 已经在投诉。诊断：上线前必须跑 RAGAS 4 指标（faithfulness / answer_relevancy / context_precision / context_recall），每项 < 0.75 就拒绝上线。

坑 5：metadata 丢失——用户问"这段话出自哪份文档第几页？"，回答"我不确定"。修复：切分时把 doc_id / page / section / source / timestamp 都保留到 metadata，生成答案时一并塞进 Prompt。

9.10.4 坑 2 修复示例：中文 embedding 选型

"""
第 9.10.2 节: 中文 RAG embedding 选型决策树
中文场景：避免使用纯英文模型
"""
def select_chinese_embedding(case):
    """根据场景选 embedding 模型"""
    if case == "qa_with_short_query":
        return "text-embedding-3-small"  # 通用，对短 query 友好
    elif case == "chinese_kb":
        return "BGE-large-zh-v1.5"  # 中文最强开源
    elif case == "code_search":
        return "text-embedding-3-small"  # 代码检索
    elif case == "multi_lang":
        return "multilingual-e5-large"  # 多语言
    return "BGE-large-zh-v1.5"  # 默认

# === Run ===
for case in ["chinese_kb", "qa_with_short_query", "code_search"]:
    print(f"{case}: {select_chinese_embedding(case)}")

9.10.5 坑 5 修复示例：chunk metadata 保留

"""
第 9.10.3 节: chunk metadata 保留（避免丢失溯源）
"""
def chunk_with_metadata(doc, chunk_size=200, overlap=30):
    """切分时保留 doc_id / page / section"""
    chunks = []
    start = 0
    while start < len(doc['text']):
        end = min(start + chunk_size, len(doc['text']))
        chunk = doc['text'][start:end]
        chunks.append({
            'text': chunk,
            'metadata': {
                'doc_id': doc['id'],
                'source': doc.get('source', 'unknown'),
                'page': doc.get('page', 1),
                'section': doc.get('section', ''),
                'chunk_index': len(chunks),
            }
        })
        start = max(end - overlap, start + 1)
    return chunks

# === Run ===
doc = {
    'id': 'manual_v3',
    'source': 'product_manual.pdf',
    'page': 12,
    'section': '退款政策',
    'text': '退款必须在 7 天内申请。超过 7 天不予退款。'
}
chunks = chunk_with_metadata(doc)
# 6 个 chunks 是 sliding window + overlap 30 的预期结果；真实场景可调 chunk_size + overlap
for c in chunks:
    print(f"  text={c['text'][:20]}...  metadata={c['metadata']}")

9.10.6 RAG 失败模式速查（按出现频率排序）

排名 失败模式 频率 解决成本
:---: :--- :---: :---:
1 检索不到答案（chunk 切分 / embedding 不匹配） ⭐⭐⭐⭐⭐ 低
2 答案与 query 偏题（top-K 太多噪声） ⭐⭐⭐⭐ 低
3 答案编造（retrieval 召回但生成幻觉） ⭐⭐⭐ 中
4 答案溯源失败（metadata 丢失） ⭐⭐⭐ 低
5 长文档摘要丢关键信息 ⭐⭐ 中
6 多文档交叉对比混乱 ⭐⭐ 高
7 实时性差（向量库未更新） ⭐ 中
8 多语言混合检索失败 ⭐ 高
关键概念摘要：<br>- 坑 1（chunk 切太大）和 坑 2（embedding 不匹配）是两个最常见的 RAG 死亡组合<br>- 坑 4（不评估就上线）= 上线后才发现 faithfulness = 60%<br>- 坑 5（metadata 丢失）= 无法回答"这段话出自哪个文档哪一页"<br>- 失败模式 #1（检索不到答案）占所有 RAG 失败中的 50%+——先把检索质量拉满

9.11 本章小结

9.11.1 8 条速记

  1. RAG = 开卷考试——给模型参考书
  2. 5 阶段流水线 = Document → Chunk → Embed → Store → Retrieve → Augment → Generate
  3. 中文 RAG 甜区：512 字符 chunk + BGE-large-zh embedding + top-K=3-5 + Reranking
  4. Advanced RAG = Pre + Retrieval + Post 三阶段共 8 种优化策略
  5. Agentic RAG = Agent 决定何时检索 / 检索什么 / 检索几次
  6. LlamaIndex = RAG-first 框架；LangChain = 通用编排
  7. RAGAS 4 指标 = Faithfulness / Answer Relevancy / Context Precision / Context Recall
  8. RAG vs Long-Context = 成本 + 实时性 + 精确性 三场景 RAG 必胜，2025 是混用时代
