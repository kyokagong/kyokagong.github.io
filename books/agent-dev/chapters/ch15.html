15.1 引子：ch11/ch13/ch14 留下的 3 个问题 + CrewAI 的回答

15.1.1 ch11/ch13/ch14 留下的 3 个落地问题

问题 1（来自 ch11 §11.10.5）：Supervisor 模式适合 1-to-N 委派，但业务团队不知道怎么把工作流告诉产品经理——

Supervisor 内部 state、worker 委派顺序、终止条件……全部藏在代码里，业务方看不懂。

问题 2（来自 ch13 §13.11.4）：LangGraph 的图编排灵活、checkpoint 强大，但图的边和节点对业务方是"黑盒"——

产品经理不会读 add_conditional_edges，更不会理解 State TypedDict 里的 Reducer。

问题 3（来自 ch14 §14.11.2）：AutoGen 的 GroupChat 灵活、对话驱动，但对话顺序不可预测——

SpeakerSelection 让 Manager 自动选下一个说话的人，业务方无法提前画好"流程图"给老板看。

15.1.2 CrewAI 的回答——"显式 Task 链 + 业务可读性"

CrewAI（João Moura 创立，2023 年发布）的核心哲学：

让 Task 变成代码中的一等公民——<br>每个 Task 都有明确的 description、agent、expected_output，<br>业务方看一眼 Task 列表就能理解工作流的每一步在做什么。

这种哲学带来了三个直接收益：

  1. 业务可读性：Task(description="research AI market", agent=researcher)，产品经理秒懂
  2. 可视化友好：每个 Task 是显式节点，可以直接画成工作流图给老板看
  3. 错误定位：Task 失败时，错误信息会精确指出是哪个 Task、哪个 Agent、为什么失败

15.3 3 大核心组件：Agent + Task + Crew

15.3.1 Agent 定义（role / goal / backstory / tools）

Agent = 一个角色扮演的 LLM 实例：


from crewai import Agent

researcher = Agent(
    role="市场研究员",                    # 角色定位
    goal="收集 AI Agent 市场的最新数据",   # 目标
    backstory="你是一名资深的市场分析师，专注 AI 行业 10 年",  # 背景
    tools=[search_tool, scraper_tool],   # 可用工具
    llm="gpt-4o",                        # 底层 LLM
    verbose=True
)

4 个核心字段：

字段 作用 写不好会怎样
role 角色定位（一句话） 太抽象 → Agent 行为不一致
goal 目标（具体可衡量） 太宽泛 → Agent 跑题
backstory 背景故事（3-5 句） 太短 → Agent 失去角色一致性
tools 可用工具列表 给错工具 → Agent 用错 API

15.3.2 Task 定义（description / agent / expected_output）

Task = 一个具体的工作项：


from crewai import Task

research_task = Task(
    description="调研 2026 年 AI Agent 市场规模和 Top 5 厂商",  # 工作内容
    agent=researcher,                                          # 由谁做
    expected_output="500 字市场报告，含 5 家厂商对比表"        # 交付物
)

3 个核心字段：

字段 作用 写不好会怎样
description 工作内容描述 太模糊 → Agent 不知道做什么
agent 由哪个 Agent 执行 错配 Agent role → 输出质量低
expected_output 期望的输出 不写 → Agent 输出格式不可控

15.3.3 Hello World：单 Agent + 单 Task + Crew 30 行 mock


# requires: pip install crewai
# 30 行 Hello World — 单 Agent + 单 Task + sequential Crew
import os
os.environ["OPENAI_API_KEY"] = "sk-mock"

from crewai import Agent, Task, Crew, Process

# 1. 定义 Agent
researcher = Agent(
    role="市场研究员",
    goal="收集 AI Agent 市场规模数据",
    backstory="10 年 AI 行业分析师",
    llm="gpt-4o",
    allow_delegation=False,   # 单 Agent 不需要委派
    verbose=False
)

# 2. 定义 Task
research_task = Task(
    description="调研 2026 年 AI Agent 市场规模",
    agent=researcher,
    expected_output="200 字市场报告"
)

# 3. 组装 Crew
crew = Crew(
    agents=[researcher],
    tasks=[research_task],
    process=Process.sequential,
    verbose=False
)

# 4. 执行
result = crew.kickoff(inputs={"topic": "AI Agent"})
print(f"输出: {result.raw[:200]}")
# 真实场景需 OPENAI_API_KEY；mock 模式返回空字符串

15.4 完整工作流实战（核心）

15.4.1 多 Agent + 多 Task 工作流

经典 3 角色工作流：

  • Researcher（研究员）→ 调研市场数据
  • Writer（作家）→ 根据调研撰写报告
  • Editor（编辑）→ 审核 + 润色

15.4.2 完整 3 Agent + 3 Task 端到端 50 行 mock（mock 跑通）


# requires: pip install crewai
# 50 行完整工作流 — 3 Agent + 3 Task + sequential
import os
os.environ["OPENAI_API_KEY"] = "sk-mock"

from crewai import Agent, Task, Crew, Process

# === 1. 定义 3 个 Agent ===
researcher = Agent(
    role="高级研究员",
    goal="调研 AI Agent 市场",
    backstory="10 年 AI 行业研究经验",
    llm="gpt-4o", allow_delegation=False, verbose=False
)
writer = Agent(
    role="技术作家",
    goal="把调研写成清晰报告",
    backstory="5 年技术写作经验",
    llm="gpt-4o", allow_delegation=False, verbose=False
)
editor = Agent(
    role="资深编辑",
    goal="审核 + 润色",
    backstory="10 年编辑经验",
    llm="gpt-4o", allow_delegation=False, verbose=False
)

# === 2. 定义 3 个 Task（顺序：research → write → edit）===
research_task = Task(
    description="调研 2026 年 AI Agent 市场规模和 Top 5 厂商",
    agent=researcher,
    expected_output="300 字调研报告"
)
write_task = Task(
    description="基于调研撰写 800 字市场报告",
    agent=writer,
    expected_output="800 字完整报告"
)
edit_task = Task(
    description="审核 + 润色报告",
    agent=editor,
    expected_output="800 字终稿"
)

# === 3. 组装 Crew（sequential 模式）===
crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[research_task, write_task, edit_task],
    process=Process.sequential,    # 任务按顺序执行
    verbose=False
)

# === 4. 执行 ===
result = crew.kickoff()
print(f"最终输出（前 200 字）: {result.raw[:200]}")
print(f"任务执行数: {len(result.tasks_output)}")  # 应为 3

预期输出（mock）：


最终输出（前 200 字）: （mock 模式无 LLM 调用）
任务执行数: 3

真实场景输出：


最终输出（前 200 字）: 2026 年 AI Agent 市场规模约 120 亿美元，Top 5 厂商包括 OpenAI、Google、Anthropic...
任务执行数: 3

15.4.3 CrewOutput 与 task_output

CrewOutput 是 Crew 执行后的产物，包含：


result = crew.kickoff()

result.raw              # 最终输出（字符串）
result.tasks_output     # 每个 Task 的输出（列表）
result.token_usage      # Token 用量统计
result.json_dict        # 如果最后一个 Task 输出是 JSON，可解析

实战技巧：用 result.tasks_output[-1].raw 拿到最后一个 Task 的输出（=最终报告）；用 result.tasks_output[0].raw 拿到第一个 Task 的输出（=调研结果）。

15.4.4 单 Agent vs Crew 多 Agent 对比

维度 单 Agent Crew 多 Agent
代码长度 5-10 行 30-50 行
Token 成本 1x 1-1.2x（sequential）
业务可读性 高 更高（Task 列表清晰）
错误定位 中（一个 LLM 调用） 高（精确到 Task）
角色扮演一致性 低（1 个 prompt 兼顾多角色） 高（每 Agent 独立 backstory）
何时用 单一任务 多步业务工作流

何时用单 Agent：

  • 任务简单（1 步）
  • 不需要业务可读性
  • 不需要多角色扮演

何时用 Crew：

  • 任务 3 步以上
  • 业务方需要看工作流
  • 多角色扮演能提升输出质量（如调研 + 写作 + 审核）

15.5 Process 3 种模式：sequential / hierarchical / consensual

15.5.1 sequential 模式（任务链）

最简单、最常用——任务按定义顺序串行执行：


crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[research_task, write_task, edit_task],
    process=Process.sequential,    # 默认
)

15.5.2 hierarchical 模式（Manager Agent 自动委派）

Manager 自动委派——增加一个 Manager Agent，自动选下一个 Task 由谁做：


crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[research_task, write_task, edit_task],
    process=Process.hierarchical,  # Manager 自动委派
    manager_llm="gpt-4o"           # Manager 用 LLM 选人
)

15.5.3 consensual 模式（协商 / 投票）

协商——多个 Agent 投票决定下一步：


crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[research_task, write_task, edit_task],
    process=Process.consensual,    # 协商模式
)

15.5.4 3 模式选型决策树


Q1: 业务方是否需要提前知道执行顺序？
├─ A. 是（业务可读性优先）→ sequential
└─ B. 否（顺序可灵活）

   Q2: 任务之间是否有明确依赖？
   ├─ A. 是 → sequential
   └─ B. 否 → hierarchical（Manager 委派）
              或 consensual（多 Agent 协商）

15.5.5 3 模式对比表

维度 sequential hierarchical consensual
执行顺序 任务定义顺序 Manager 自动选 多 Agent 协商
业务可读性 ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐⭐
灵活性 ⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐
Token 成本 1x 基准 1.5-2x（Manager 委派开销） 2-3x（投票开销）
错误率 最低（可控） 中（Manager 委派错） 中（投票分歧）
适用场景 报告生成 / 数据流水线 复杂任务拆分 头脑风暴 / 多视角

15.5.6 hierarchical 模式 30 行完整示例


# requires: pip install crewai
# 30 行 hierarchical 模式示例 — Manager 自动委派
import os
os.environ["OPENAI_API_KEY"] = "sk-mock"

from crewai import Agent, Task, Crew, Process

# === 1. 定义 3 个 Worker Agent ===
researcher = Agent(role="研究员", goal="调研 AI 市场",
    backstory="10 年经验", llm="gpt-4o", verbose=False)
writer = Agent(role="作家", goal="撰写报告",
    backstory="5 年写作", llm="gpt-4o", verbose=False)
editor = Agent(role="编辑", goal="审核",
    backstory="10 年编辑", llm="gpt-4o", verbose=False)

# === 2. 定义 3 个 Task（Manager 自动选人）===
research_task = Task(description="调研市场", expected_output="300 字调研")
write_task = Task(description="撰写报告", expected_output="800 字报告")
edit_task = Task(description="审核报告", expected_output="终稿")

# === 3. hierarchical 模式 — Manager 自动委派 ===
crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[research_task, write_task, edit_task],
    process=Process.hierarchical,    # 关键：Manager 自动委派
    manager_llm="gpt-4o",           # Manager 用 LLM 决策
    verbose=False
)

# === 4. 执行（Manager 决定执行顺序）===
result = crew.kickoff()
print(f"任务执行数: {len(result.tasks_output)}")  # 应为 3

与 sequential 的关键区别：

  • Process.hierarchical 启用 manager_llm
  • Manager Agent 根据每个 Task 的 description 自动选最合适的 Worker
  • 适合：任务之间没有强依赖、顺序可灵活的场景

15.5.7 consensual 模式 30 行完整示例


# requires: pip install crewai
# 30 行 consensual 模式示例 — 多 Agent 协商
import os
os.environ["OPENAI_API_KEY"] = "sk-mock"

from crewai import Agent, Task, Crew, Process

# === 1. 定义 3 个对等 Agent（无 Manager）===
researcher = Agent(role="研究员", goal="调研",
    backstory="10 年经验", llm="gpt-4o", verbose=False)
writer = Agent(role="作家", goal="撰写",
    backstory="5 年写作", llm="gpt-4o", verbose=False)
editor = Agent(role="编辑", goal="审核",
    backstory="10 年编辑", llm="gpt-4o", verbose=False)

# === 2. 定义 3 个 Task（Agent 协商决定谁做）===
research_task = Task(description="调研市场", expected_output="300 字")
write_task = Task(description="撰写报告", expected_output="800 字")
edit_task = Task(description="审核报告", expected_output="终稿")

# === 3. consensual 模式 — Agent 之间协商 ===
crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[research_task, write_task, edit_task],
    process=Process.consensual,    # 关键：协商模式
    verbose=False
)

# === 4. 执行（Agent 投票决定执行）===
result = crew.kickoff()
print(f"任务执行数: {len(result.tasks_output)}")  # 应为 3

与 hierarchical 的关键区别：

  • 无 Manager Agent，所有 Agent 对等
  • 每个 Task 由 Agent 投票决定谁做
  • Token 成本：2-3x sequential（投票轮次多）
  • 适合：头脑风暴、多视角决策
Token 成本估算口径：以"sequential + 裸 LLM API"为 1x 基准，基于 2025-Q4 公开 case study 经验估算。<br>框架实际成本受 Manager LLM 调用频率、Agent 协商轮次影响，单个项目的实际值可能在 ±50% 浮动。<br>生产前应在自己的 workload 上做 A/B 测量。

15.6 工具集成与代码执行（CrewAI 特色）

15.6.1 工具集成（@tool 装饰器 / langchain_tools）

方式 1：@tool 装饰器（CrewAI 原生）


from crewai.tools import tool

@tool("获取天气")
def get_weather(city: str) -> str:
    """获取指定城市的天气"""
    return f"{city} 今天晴天，25°C"

researcher = Agent(
    role="天气研究员",
    goal="查天气",
    backstory="天气专家",
    tools=[get_weather],   # 直接传入
    llm="gpt-4o"
)

方式 2：LangChain Tools 集成（v0.86+）


from langchain_community.tools import DuckDuckGoSearchRun

search_tool = DuckDuckGoSearchRun()

researcher = Agent(
    role="研究员",
    goal="搜索 AI Agent 最新资讯",
    backstory="AI 行业专家",
    tools=[search_tool],   # 直接传入 LangChain Tool
    llm="gpt-4o"
)

15.6.2 代码执行（CodeInterpreterTool）

v1.0 新特性——Agent 可以执行代码：


from crewai_tools import CodeInterpreterTool

code_tool = CodeInterpreterTool()

analyst = Agent(
    role="数据分析师",
    goal="用 Python 分析数据",
    backstory="数据科学专家",

    llm="gpt-4o"
)

注意：与 ch14 AutoGen 的 CodeExecutorAgent 类似，生产环境必须用沙箱——LLM 生成的代码可能包含 os.system('rm -rf /')。

15.6.3 自定义工具（BaseTool 子类）

复杂工具用子类：


from crewai.tools import BaseTool
from pydantic import Field

class DatabaseQueryTool(BaseTool):
    name: str = "数据库查询"

15.8.5 Flow 完整示例 30 行（v1.0 新特性）


# requires: pip install crewai
# 30 行 Flow 示例 — 2 个 Crew 串成 DAG
import os
os.environ["OPENAI_API_KEY"] = "sk-mock"

from crewai import Agent, Task, Crew, Process
from crewai.flow import Flow, listen, start

# === 1. 定义 Crew 1（调研）===
researcher = Agent(role="研究员", goal="调研",
    backstory="专家", llm="gpt-4o", verbose=False)
crew_research = Crew(
    agents=[researcher],
    tasks=[Task(description="调研", expected_output="300 字")],
    process=Process.sequential, verbose=False
)

# === 2. 定义 Crew 2（撰写）===
writer = Agent(role="作家", goal="撰写",
    backstory="专家", llm="gpt-4o", verbose=False)
crew_write = Crew(
    agents=[writer],
    tasks=[Task(description="撰写", expected_output="800 字")],
    process=Process.sequential, verbose=False
)

# === 3. 用 Flow 串成 DAG ===
class ReportFlow(Flow):
    @start()
    def research_phase(self):
        return self.crew_research.kickoff().raw

    @listen(research_phase)
    def write_phase(self, research_output):
        return self.crew_write.kickoff(inputs={"research": research_output}).raw

# === 4. 执行 Flow ===
flow = ReportFlow()
flow.crew_research = crew_research
flow.crew_write = crew_write
result = flow.kickoff()
print(f"最终输出（前 200 字）: {result[:200]}")

Flow 的核心价值：把多个 Crew 串成 DAG，每个 Crew 独立可测试。

15.9.1 5 大错误类型 + 修复

错误类型 表现 根因 修复
Agent 委派失败 Task 卡住无输出 Agent role 与 Task 不匹配 重新匹配 Agent.role ↔ Task.description
Task 死循环 Token 用尽仍不结束 hierarchical Manager 反复委派 加 max_iter 限制 / 切 sequential
Token 超限 LLM 报错 "context_length" context 太长 开启 memory=False 或减小 backstory
工具超时 工具调用 60s+ 无响应 工具本身慢 设工具 timeout=10 + 重试
终止条件未达 crew.kickoff() 不返回 最后一个 Task 输出为空 检查最后一个 Task 的 agent + expected_output

# 50 行错误修复示例 — Token 超限 + Task 死循环

# === 修复 1：Token 超限 — 减小 backstory ===

    role="研究员",

    description="调研",

    expected_output="200 字报告"

from crewai.tools import tool

@tool(timeout=10)                           # 10s 超时
def slow_api():
    return "slow result"

# === 修复 4：终止条件 — 检查每个 Task 输出 ===
crew = Crew(agents=[researcher], tasks=[research_task], process=Process.sequential)
result = crew.kickoff()
if not result.tasks_output[-1].raw:
