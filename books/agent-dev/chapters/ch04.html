4.1 引子：为什么需要框架？

在 ch03 我们用 100 行 Python 把"大脑 + 记忆 + 工具 + 规划"拼成了一个能跑的 Agent。看起来也不算太复杂——那为什么工业界几乎所有人都在用框架？

4.1.1 自研 vs 框架的代价

自己写的 100 行代码能跑，但生产环境会很快暴露出三件事：

自研痛点 后果 框架如何解决
工具描述 JSON 自己拼 改协议要改 N 处 框架用装饰器/类型注解自动生成
重试 / 超时 / 限流 每个工具都要重写 框架统一中间件
状态管理 多步任务下变量乱飞 框架用 Checkpoint + 序列化
可观测性 出问题只能 print 框架接 LangSmith / OpenTelemetry
多 Agent 协作 自己写 socket / 锁 框架给你角色 + 消息总线
流式输出 SSE / WebSocket 都要手写 框架内置 stream API

结论：当你的 Agent 从"demo"变成"产品"的那一刻，框架的价值才开始显现。

如果你把 2024-2026 的所有 Agent 框架都拆开看，里面其实就是同一组概念的 7 种方言：

4.2 LangChain——LLM 应用的"Spring"

LangChain 是 2022 年 10 月由 Harrison Chase 发布的"通用 LLM 应用框架"。到 2026 年，它已经是 GitHub 上 Star 最多的 LLM 框架之一（约 11 万+），在通用 LLM 应用框架类别里稳居第一。

4.2.1 核心抽象

LangChain 的核心是 Runnable 协议——所有组件（prompt、model、retriever、tool、chain）都实现同一个接口：

invoke(input)        ← 同步调用
ainvoke(input)       ← 异步调用
stream(input)        ← 流式输出
batch([input1, ...]) ← 批量调用

这意味着你可以像拼管道一样拼 LLM 应用：

prompt | model | parser

这串写法叫 LCEL（LangChain Expression Language），从 v0.1 引入后成为标准。

4.2.2 Hello World（30 行）

# langchain_hello.py
# pip install langchain langchain-openai
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# 1. 模型
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 2. 提示词模板
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个翻译助手，把中文翻成{language}"),
    ("user", "{text}")
])

# 3. 输出解析器
parser = StrOutputParser()

# 4. 用 LCEL 拼成链
chain = prompt | llm | parser

# 5. 调用
print(chain.invoke({"language": "英文", "text": "今天天气真好"}))

输出：The weather is really nice today.

一句话点评：LCEL 写起来像 Unix pipeline，可读性满分。但当你加 5 个工具 + 2 个分支 + 1 个记忆时，链子会变成"长面条"。

4.2.3 优势 / 痛点

  • ✅ 生态最大：所有模型 / 向量库 / 文档加载器都有官方集成
  • ✅ 文档最全：官方 cookbook + 第三方教程铺天盖地
  • ✅ LCEL 标准化：声明式，调试方便
  • ⚠️ 抽象泄漏：底层 API 改一次，链子断一片（v0.0 → v0.1 → v0.2 → 0.3 → 1.0 多次破坏性升级）
  • ⚠️ 学习成本：概念多（Chain、Agent、Tool、Retriever、Memory、Callback...）

4.2.4 2025 年 1.0 重大变化

LangChain 在 2024 年底发布 1.0（从 v0.3 跳到 v1.0），主要做了三件事：

  • 去中心化重构：把 langchain-community 中的集成拆成独立包（langchain-openai、langchain-anthropic），主包只保留核心抽象
  • LCEL 一等公民：1.0 之前 Chain 类和 LCEL 是两套并行 API，1.0 之后 LCEL 成为唯一推荐写法
  • 稳定性承诺：1.0 之后只允许向后兼容的改动，新功能进 langchain-experimental

对老项目的影响：升级到 1.0 通常要把所有 import 改一遍（约 30-50 处），但行为变化不大。建议：新项目直接 1.0，老项目锁 v0.3 维护。

4.3 LangGraph——LangChain 的"严肃兄弟"

LangGraph 是 LangChain 团队 2024 年 6 月发布的"图式 Agent 框架"。它把 Agent 描述成一张有状态图：节点 = 动作，边 = 控制流。

4.3.1 核心抽象

  • State：全局状态（TypedDict 定义）
  • Node：图上的一个动作（LLM 调用、工具调用、决策）
  • Edge：节点之间的连线（普通边、条件边、循环边）
  • Checkpoint：状态快照（用于时间旅行、人在环、容错）

何时用 LangGraph：当你的 Agent 需要循环、回滚、并行分支、人在环时。

4.3.2 Hello World（30 行）

# langgraph_hello.py
# pip install langgraph langchain-openai
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI

# 1. 状态定义
class State(TypedDict):
    messages: list

# 2. 节点：调用 LLM
def chatbot(state: State):
    llm = ChatOpenAI(model="gpt-4o-mini")
    return {"messages": state["messages"] + [llm.invoke(state["messages"])]}

# 3. 构图
graph = StateGraph(State)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)

# 4. 编译
app = graph.compile()

# 5. 调用
result = app.invoke({"messages": [("user", "你好")]})
print(result["messages"][-1].content)

一句话点评：写起来比 LangChain 啰嗦，但当你想做"如果用户问的是订单问题就转人工，否则 AI 回答"这种条件分支时，LangGraph 比 LCEL 清晰 10 倍。

4.3.3 适用场景

  • ✅ 客服多轮对话（需要查订单、退款、政策）
  • ✅ 多 Agent 协作（researcher + writer + critic）
  • ✅ 人在环（Human-in-the-Loop，关键决策暂停让人类介入）
  • ✅ 长跑工作流（10+ 步、有循环、会重试）

4.4 AutoGen——微软的"对话式多 Agent"

AutoGen 是微软 2023 年 9 月发布的"对话式多 Agent 框架"。它把 Agent 想象成"会聊天的角色"——每个 Agent 是一个有名字、有性格、有输入输出的角色。

4.4.1 核心抽象与演进

  • v0.2 (2023-2024)：基于 AssistantAgent / UserProxyAgent，用 group chat 协调
  • v0.4 (2024.11 重写)：引入 Actor Model，每个 Agent 是一个独立 actor，消息通过 topic 路由

重写的原因：v0.2 的中心化调度器在多 Agent 协作时容易死锁，v0.4 用消息队列解耦。

4.4.2 Hello World（30 行，v0.4）

# autogen_hello.py
# pip install autogen-agentchat autogen-ext[openai]
# 运行前需 export OPENAI_API_KEY=sk-...（AutoGen v0.4 强制要求）
import asyncio
from autogen_agentchat.agents import AssistantAgent
from autogen_agentchat.ui import Console
from autogen_ext.models.openai import OpenAIChatCompletionClient

async def main():
    model = OpenAIChatCompletionClient(model="gpt-4o-mini")

    # 1. 定义一个"作家" Agent
    writer = AssistantAgent(
        name="writer",
        model_client=model,
        system_message="你是一个作家，用中文写一段关于春天的短句。"
    )

    # 2. 让它跑一轮
    await Console(writer.run_stream(task="开始吧"))

    await model.close()

asyncio.run(main())

一句话点评：AutoGen 的多 Agent 通信最像"开会"——你给每个 Agent 一段角色描述，让它们轮流发言、自动决策下一个该谁说话。

4.4.3 适用场景

  • ✅ 复杂的协作任务（研究 → 写作 → 评审 → 修改）
  • ✅ 需要自动决定"下一个谁说话"的场景
  • ✅ .NET 生态（AutoGen 是少数支持 .NET 的 Agent 框架）
  • ⚠️ 学习曲线陡：v0.2 → v0.4 几乎完全不兼容，老教程要重写

4.5 CrewAI——"虚拟团队"的隐喻

CrewAI 是 2023 年 11 月发布的"角色扮演式多 Agent 框架"。它把多 Agent 类比成一支 Crew（团队）——每个人有角色、有任务、有顺序。

4.5.1 核心抽象

  • Agent：一个角色（研究员 / 作家 / 审稿人）
  • Task：一个具体任务（"研究 X 主题" / "写 800 字文章"）
  • Crew：把 Agent 和 Task 装在一起，按 Process 执行
  • Process：sequential（顺序）或 hierarchical（带管理者）

4.5.2 Hello World（30 行）

# crewai_hello.py
# pip install crewai crewai-tools
from crewai import Agent, Task, Crew, Process
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.7)

# 1. 定义 Agent
researcher = Agent(
    role="研究员",
    goal="研究 AI Agent 的最新进展",
    backstory="你是硅谷的 AI 分析师，每天看 50 篇论文。",
    llm=llm,
)
writer = Agent(
    role="作家",
    goal="把研究写成 200 字短文",
    backstory="你是《连线》杂志的科技作家。",
    llm=llm,
)

# 2. 定义 Task
task1 = Task(description="研究 2026 年 Agent 框架格局", expected_output="3 个关键趋势", agent=researcher)
task2 = Task(description="把趋势写成 200 字", expected_output="一段中文", agent=writer)

# 3. 组建 Crew
crew = Crew(agents=[researcher, writer], tasks=[task1, task2], process=Process.sequential)

# 4. 启动
result = crew.kickoff()
print(result)

一句话点评：CrewAI 的"角色 + 任务 + 流程"三件套是最少代码描述一个工作流的方式——比 LangGraph 直观，比 AutoGen 简单。

4.5.3 适用场景

  • ✅ 内容流水线（研究 → 写作 → 审核 → 发布）
  • ✅ 流程固定的多 Agent 协作
  • ✅ 不想自己写通信逻辑的产品经理 / 业务人员
  • ⚠️ 过度抽象：复杂分支要 hack Process

4.6 LlamaIndex——RAG 优先的"索引派"

LlamaIndex 是 2022 年 11 月由 Jerry Liu 发布的"RAG-first 框架"。它的核心信念是：LLM 的价值取决于它能访问的数据。

4.6.1 核心抽象

  • Document：一段文本 + 元数据
  • Index：从 Document 派生的数据结构（VectorIndex / SummaryIndex / KnowledgeGraphIndex）
  • QueryEngine：把 query 变成 Index 查询
  • Workflows（2024.10 引入）：把多步 RAG 流程串成图

4.6.2 Hello World（30 行）

# llamaindex_hello.py
# pip install llama-index llama-index-llms-openai
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, Settings
from llama_index.llms.openai import OpenAI

# 1. 配置
Settings.llm = OpenAI(model="gpt-4o-mini")

# 2. 加载文档（假设 ./data 下有 .txt 文件）
documents = SimpleDirectoryReader("./data").load_data()

# 3. 建索引
index = VectorStoreIndex.from_documents(documents)

# 4. 查询
query_engine = index.as_query_engine()
response = query_engine.query("这些文档主要讲了什么？")
print(response)

一句话点评：LlamaIndex 的 "load → index → query" 三步是最短的 RAG 路径。如果你要做的核心是"问文档"，LlamaIndex 是首选。

4.6.3 适用场景

  • ✅ 知识库问答（企业文档 / 产品手册 / 论文库）
  • ✅ 复杂 RAG 流水线（HyDE、ReRank、Self-RAG）
  • ✅ 想要 200+ 种数据连接器（Notion、Slack、Google Drive...）
  • ⚠️ Agent 能力相对弱：需要自己接 LangGraph 做循环

4.7 Agno——"全栈 + 极速"

Agno（原名 Phidata，2024.12 改名）是 2023 年 8 月发布的"从原型到生产"框架。它的两个最大卖点：零装饰器 和 比 LangGraph 快 4 倍。

4.7.1 核心抽象

  • Agent：一个完整 Agent，构造时传 model、tools、instructions
  • Team：多 Agent 协作（Coordinator + Members）
  • Workflow：用 Python 函数描述多步流程

4.7.2 Hello World（30 行）

# agno_hello.py
# pip install agno openai duckduckgo-search
from agno.agent import Agent
from agno.models.openai import OpenAIChat
from agno.tools.duckduckgo import DuckDuckGoTools

# 1. 直接构造
agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    tools=[DuckDuckGoTools()],
    instructions=["用中文回答", "先搜索再总结"],
    markdown=True,
)

# 2. 跑
agent.print_response("2026 年 Anthropic 发布了哪些新模型？", stream=True)

一句话点评：Agno 是最"裸"的 Agent 框架——没有装饰器、没有链式语法、没有抽象层，所有逻辑都在 Python 控制流里。

4.7.3 适用场景

  • ✅ 性能敏感（高并发、Agent Swarm）
  • ✅ 想要纯 Python 控制流，不喜欢装饰器
  • ✅ 快速原型 → 同一套代码上生产
  • ⚠️ 生态较新：相比 LangChain / AutoGen，社区资源少

4.8 OpenAI Agents SDK——官方钦定的"轻量标准"

OpenAI Agents SDK 是 2025 年 3 月 OpenAI 官方发布的 Agent 框架，前身是 2024 年实验性的 Swarm。它不是银弹，但可能是行业标准。

4.8.1 核心抽象

  • Agent：一个 LLM + 指令 + 工具集
  • Runner：执行 Agent 的引擎（同步/异步/流式）
  • Handoff：Agent 之间主动交接（"这事我处理不了，转给 X"）
  • Guardrail：输入/输出校验（"用户问题必须包含订单号"）
  • Tracing：内置 OpenAI 平台 trace 集成

4.8.2 Hello World（30 行）

# openai_agents_hello.py
# pip install openai-agents
import asyncio
from agents import Agent, Runner, function_tool

# 1. 工具
@function_tool
def get_weather(city: str) -> str:
    """查询天气（mock）"""
    return f"{city} 晴天 25 度"

# 2. Agent
agent = Agent(
    name="助手",
    instructions="你是中文助手，能查天气",
    tools=[get_weather],
    model="gpt-4o-mini",
)

# 3. 跑
async def main():
    result = await Runner.run(agent, input="北京今天天气如何？")
    print(result.final_output)

asyncio.run(main())

一句话点评：OpenAI Agents SDK 写起来几乎和 Python 函数一样自然——@function_tool 装饰器 + 类型注解 → 自动 JSON Schema；Handoff 让多 Agent 协作不再需要中央调度器。

4.8.3 适用场景

  • ✅ 用 OpenAI / Azure OpenAI 为主的项目
  • ✅ 想要官方支持 + 平台 trace 集成
  • ✅ 轻量多 Agent 协作（用 Handoff 表达"转人工"）
  • ⚠️ 绑定 OpenAI 模型：用 Anthropic / Gemini 没那么顺

4.8.4 与前身 Swarm 的关系

OpenAI Agents SDK 不是凭空出现的——它的前身是 2024 年 7 月 OpenAI 发布的实验性项目 Swarm（GitHub 上至今可见）。Swarm 提出"基于 Handoff 的多 Agent 协作"概念，但被定位为"教学示例"而非生产框架。2025 年 3 月，OpenAI 把 Swarm 的核心思想产品化：补全了 Trace、Guardrail、Tool schema 校验、错误恢复、并发执行等生产必需能力，正式命名 Agents SDK。

维度 Swarm (2024.7) Agents SDK (2025.3)
定位 教学示例 生产框架
Trace ❌ 无 ✅ 平台原生
Guardrail ❌ 无 ✅ 完整
工具 schema 手写 类型注解自动生成
错误恢复 ❌ ✅ 自动重试 + 兜底
维护承诺 实验性 长期支持

给读者的建议：新项目直接上 Agents SDK，不要从 Swarm 迁移——Swarm 的 API 在 Agents SDK 中保留了 90%，但剩余 10% 的差异足够让你改一天。

4.8.5 限制与备选

OpenAI Agents SDK 不是银弹。它有两个明显边界：

  • OpenAI 模型绑定：虽然 SDK 接受任何兼容 OpenAI Chat Completions 的端点（Together / OpenRouter / 自部署 vLLM），但 trace、eval 等平台功能只对 OpenAI 官方模型开
  • 多 Agent 表达力有限：Handoff 是显式协作，但如果你想要"多 Agent 自动决定下一个谁说话"（如 GroupChat 风格），SDK 没有原生支持——你需要自己写编排层

备选路径：

  • 想用类似 Handoff 概念但用其他模型 → Agno Team
  • 想做"开会型"多 Agent → AutoGen v0.4 GroupChat
  • 想做"图式"多 Agent → LangGraph

4.8.6 与 ch03 minimal_agent 的对应关系

如果你已经把 ch03 的 100 行 minimal_agent 跑通了，理解 OpenAI Agents SDK 会非常快——它本质上就是把我们手写的循环"标准化"了：

ch03 minimal_agent 手写 OpenAI Agents SDK 说明
llm(messages) 调一次 agent.run() / Runner.run() SDK 包装成 Agent 对象
手工判断 tool_call SDK 内部自动解析 工具调用透明化
解析 JSON 参数 类型注解自动生成 schema @function_tool 装饰器
写 while True: ... 循环 SDK 的 Runner 内置 Handoff / 工具错误自动处理
手动 print log 内置 Trace OpenAI 平台可看

这意味着：ch03 的 100 行是我们所有框架的"母语"。一旦你写完 ch03，换任何框架都只是"用框架的术语重新说同一件事"。

4.9.3 反共识建议

  • 单 Agent + 单一工具 + 一次性脚本 → 框架反而拖慢
  • 极致性能要求（延迟 < 50ms）→ 自己写 + 裸 HTTP

4.9.4 架构哲学对比：四种世界观

7 个框架背后其实是 4 种不同的"世界观"——它们对"Agent 是什么"有完全不同的回答：

哲学 代表框架 核心隐喻 一句话回答
管道哲学 LangChain Agent = LLM + 链 "把模型当函数，串联起来"
图哲学 LangGraph Agent = 状态机 "Agent 是一张会走动的图"
对话哲学 AutoGen Agent = 角色 "Agent 是一群会聊天的同事"
任务哲学 CrewAI Agent = 团队 "Agent 是一支有分工的小组"
索引哲学 LlamaIndex Agent = 查询器 "Agent 是数据的嘴和手"
全栈哲学 Agno Agent = 一等公民 "Agent 就是一个对象，没有抽象层"
标准哲学 OpenAI Agents SDK Agent = 可交接的服务 "Agent 是一个能转接给别人的服务"

给读者的判断：

  • 你喜欢"搭积木" → 管道哲学（LangChain）
  • 你喜欢"画流程图" → 图哲学（LangGraph）
  • 你喜欢"开会" → 对话哲学（AutoGen）
  • 你喜欢"看团队" → 任务哲学（CrewAI）
  • 你喜欢"查资料" → 索引哲学（LlamaIndex）
  • 你喜欢"看代码" → 全栈哲学（Agno）
  • 你想"省心" → 标准哲学（OpenAI Agents SDK）

反共识观察：7 个框架里只有 OpenAI Agents SDK 真正做到"5 行代码 + 1 个 Agent + 2 个工具 = 完整应用"。如果你只是想"先跑起来"，它就是 2026 年的答案。但如果你想"搞懂 Agent 的原理"，从 LangGraph 入手最值。

4.10.3 成本与许可证

框架本身大多开源（MIT / Apache 2.0），但真实成本是 LLM API。粗算：

框架 LLM 依赖 每次调用的额外开销 适合预算
LangChain 任意 微秒级（包装层） 中低
LangGraph 任意 微秒级 中低
AutoGen 任意 多 Agent 对话 = N 次 LLM 中高
CrewAI 任意 任务链 = M×N 次 LLM 中高
LlamaIndex 任意 Embedding + LLM = 2-3 次 中（看 RAG 复杂度）
Agno 任意 微秒级 中低
OpenAI Agents SDK OpenAI 微秒级 中（看 Handoff 次数）

经验法则：单 Agent 项目每月 LLM 成本 100-500 美元；多 Agent + 复杂 RAG 项目每月 1000-5000 美元。先算账再选框架。

4.10.4 框架迁移实战经验

团队从 A 框架迁到 B 框架是 2025 年最常见的工程任务之一。三个真实经验：

经验 1：把"业务逻辑"和"框架粘合"分文件。典型反例：所有代码都写在 langchain_helper.py 里，迁移时要全文重写。正例：

project/
├── core/                ← pure Python 业务逻辑
│   ├── tools.py         ← 工具函数（无框架依赖）
│   ├── prompts.py       ← prompt 字符串
│   └── state.py         ← 状态 dataclass
├── framework/           ← 框架粘合（迁移时只改这里）
│   ├── chain.py
│   └── agent.py
└── main.py

经验 2：先抽公共接口，再切框架。如果你要"从 LangChain 迁到 OpenAI Agents SDK"，不要直接重写 100 个文件。先定义一个 AgentRunner 抽象接口（run(query: str) -> str），两边都实现它，再一行一行换。

经验 3：先并行再切换。新框架先在新业务上跑 2-4 周，验证完再切老业务。这样出问题不会影响核心服务。

4.10.6 7 框架 Hello World 跑通实测

在 2026 年的"AI 工程师入门"圈子里有个新问题："我应该学 7 个框架还是 1 个？"答案是：至少跑通 3 个。我们用 ch04 各小节的 Hello World 做了次实测（2026.6 实际执行）：

LangChain 3 分钟 ModuleNotFoundError: langchain-openai pip install langchain-openai 5 分钟
LangGraph 5 分钟 StateGraph 边未指定 type 加 add_edge(START, ...) 8 分钟
AutoGen v0.4 12 分钟 model_client 参数位置变了 查 v0.4 migration guide 18 分钟
CrewAI 8 分钟 Process.sequential 默认值变了 加 verbose=True 调试 12 分钟

4.11 本章小结

关键概念摘要： - LCEL（LangChain Expression Language）—— LangChain 的声明式链式语法，1.0 后成为唯一推荐写法 - StateGraph —— LangGraph 用图描述 Agent 循环的核心抽象，Node + Edge + Checkpoint 三件套 - Actor Model —— AutoGen v0.4 用消息队列解耦多 Agent，解决 v0.2 中心化死锁问题 - Process.sequential / hierarchical —— CrewAI 的两种协作模式，前者按顺序、后者带管理者 - VectorStoreIndex —— LlamaIndex 的 RAG 一等公民，3 行代码完成"读文档→问答" - Workflows —— LlamaIndex 2024.10 引入的"多步 RAG 编排"，用 Python 函数定义步骤 - @function_tool —— OpenAI Agents SDK 的工具装饰器，类型注解 → JSON Schema - Handoff —— Agent 主动交接任务给另一个 Agent，2025 年标准化概念 - Guardrail —— 输入/输出校验器，"用户问题必须包含订单号"这类规则 - Trace —— OpenTelemetry 风格的执行轨迹，框架自带的可观测性 - Runnable —— LangChain 1.0 的统一接口（invoke/ainvoke/stream/batch） - GroupChat —— AutoGen 的多 Agent 开会模式，自动决定下一个谁说话 - Stream —— 流式输出，框架标准接口（token-by-token），用户体验的关键 - Batch —— 批量处理多个输入，框架标准接口（节省 API 往返） - Callback —— LangChain 的回调钩子（on_llm_start / on_tool_end 等），用于日志 / 监控 - Checkpoint —— 状态快照，LangGraph 的"时间旅行"基础 - ReRank —— 检索结果重排，用 Cross-Encoder 给相似度打分（RAG 关键步骤） - VectorStoreIndex —— LlamaIndex 的向量索引，封装了 embedding + 检索 - SummaryIndex —— LlamaIndex 的摘要索引，逐段 LLM 总结后检索

### 8 条速记

  1. LangChain 是生态最大的"通用 LLM 框架"，适合快速原型和需要 200+ 集成的项目
  2. LangGraph 是 LangChain 的"严肃版"，用图描述 Agent 循环，适合需要状态管理 / 人在环 / 复杂分支
  3. AutoGen 是微软的"对话式多 Agent"，v0.4 重写后用 Actor Model，适合开会型协作
  4. CrewAI 是"虚拟团队"隐喻的多 Agent 框架，代码最少，流程最直观
  5. LlamaIndex 是 RAG 之王，200+ 数据连接器，问文档场景首选
  6. Agno 是"全栈 + 极速"，零装饰器，4 倍速，适合高并发
  7. OpenAI Agents SDK 是 OpenAI 钦定的标准，Handoff 概念优雅，OpenAI 项目首选
  8. 选型公式：文档问答 → LlamaIndex / 多 Agent 协作 → CrewAI 或 AutoGen / OpenAI 生态 → Agents SDK / 复杂图 → LangGraph / 其余 → LangChain

### 为什么"7 个框架"不是太多

读到这里你可能会问："7 个框架不是太多吗？我能不能只学 1 个？"这是一个很自然的反应。三个反驳：

反驳 1：7 个框架的"重叠部分"占 80%。你已经学过的 4 大件（ch03）就是这 80% 的核心。剩下 20% 是每个框架的"方言"——LCEL vs CrewAI Process vs Agno Team，都是表达"我要循环 / 分支 / 多 Agent"的不同语法。一旦你理解了 4 大件，框架只是"换皮"。

反驳 2：你的职业生命周期会经历 2-3 个框架。2022 年红的是 LangChain v0.0；2024 年红的是 LangGraph；2025 年红的是 OpenAI Agents SDK。5 年后还会有新的。学会 4 大件，你就能在 2 周内上手任何新框架。

反驳 3：7 个框架代表 7 种设计哲学。理解它们，等于理解"一个工程问题有 7 种解法"——这本身就是工程师的核心能力。不要只学工具，要学"为什么这种工具存在"。

给读者的最终建议：

  • 第一周：跑通 ch03 的 100 行代码 + OpenAI Agents SDK Hello World
  • 第二周：跑通 LangGraph 循环 Agent
  • 第三周：跑通 CrewAI 多 Agent 团队
  • 第四周：跑通 LlamaIndex 文档问答
  • 第五周起：根据你手头的项目按需深入 1-2 个框架

5 周之后，你就具备了"看到新框架能 24 小时内跑通 Hello World"的能力。这才是 ch04 真正想给你的东西。
