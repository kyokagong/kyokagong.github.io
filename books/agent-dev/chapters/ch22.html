22.1.4 评测金字塔

经典评测分四层（表 22.2），每层成本递增、信号越精准：

层级名称成本信号
L4端到端任务成功率🔴 高直接但稀疏（一次任务一个分数）
L3轨迹质量🟡 中看过程，不只看结果
L2单步正确率🟢 低看每一步工具调用是否合理
L1输出合规性🟢 低JSON Schema / 工具签名是否合法

生产 Agent 必须同时跑 L1-L4，只测 L4 是新手最常见的错误——任务完成不代表每一步都对，正如"考试及格不代表每道题都做对"。

22.1.5 一个反直觉的真相

更长的 trace 不代表更强的 Agent——相反，步数越少通常越好。这一步直接呼应 ch21 §21.9.2 引入的熔断器阈值（max_steps=30）：当 Agent 在某步停滞，继续追加步骤几乎不会带来新信息。生产环境统计显示：

  • 2-5 步完成任务：SR 平均 88%（健康）
  • 6-10 步完成任务：SR 平均 76%（正常）
  • 11-20 步完成任务：SR 平均 58%（⚠️ 警惕，可能在绕路）
  • > 20 步完成任务：SR 平均 31%（🔴 几乎肯定在死循环）

这是因为步数增加会同时放大三类风险：(a) 上下文膨胀导致后续推理变差（参 ch03 §3.2 短期记忆局限）；(b) 工具调用次数增加意味着更多失败可能性；(c) 成本与时延几乎线性上升。

22.1.6 评测驱动决策 vs 数据驱动决策

最后必须强调一个哲学差异：LLM 时代之前的"数据驱动决策"看聚合数据（DAU / 留存 / 转化），Agent 时代的"评测驱动决策"看单次 trace。一次失败的客服 Agent 任务不是"成功率 -0.01pp"的抽象数字，而是某个用户等了 3 分钟没解决问题——必须能下钻到这次任务，看每一步工具调用、每次 LLM 输出、每个用户消息。

这就是为什么 trace 是 Agent 时代的"用户行为日志"——它是连接抽象指标与具体事件的唯一桥梁。从这个意义上说，ch22 介绍的 OTel/LangSmith/Langfuse 不是可观测性工具，而是 Agent 产品的"用户研究工具"。

22.2 评测指标体系

22.2.1 5 大硬指标 + 3 大软指标

表 22.2.1 评测指标全景

类别指标定义单位典型阈值
硬成功率（SR）任务最终是否完成%≥ 80%（生产）/ ≥ 60%（研究）
硬步数（Steps）完成任务的 LLM 调用次数count中位数 ≤ 8，最大 ≤ 30
硬成本（Cost）token + 工具 + 时延折算USD单任务 ≤ $0.50
硬时延（Latency）从发送到最终响应sP50 ≤ 10s，P95 ≤ 60s
硬鲁棒性（Robustness）输入扰动后成功率变化ΔppΔ ≤ 5pp
软一致性（Consistency）同样输入是否输出相近σσ ≤ 0.1
软可解释性（Explainability）trace 是否能让工程师 5 分钟内定位问题通过率≥ 90%
软安全性（Safety）越权 / 注入 / 隐私 三类违规次数count / 千次≤ 1

注：pp = percentage point（百分点）；生产环境"成功率"必须配合"步数 + 成本"联合看——完成一次任务花 100 步 $5 美元不算成功，只能算"能跑"。

22.2.2 复合指标：效用-成本比

定义 U/C（Utility / Cost）：

U/C = 成功率 / 单任务平均成本

U/C > 1.5 算"值得用"，U/C < 0.8 算"需要优化"。这个指标比单纯成功率更反映工程价值。

22.2.3 步数分布与"健康曲线"

除了平均值，步数分布的形状比平均值更能反映 Agent 状态：

分布形态健康度含义
单峰 + 右偏🟢 健康大多数任务 2-8 步完成，少数 10-20 步
双峰🟡 警惕一群简单任务 + 一群绕路任务，可能有 case 未覆盖
长尾🟡 警惕中位数 OK 但 P99 极大，可能有死循环
单峰 + 极宽🔴 不健康Agent 行为不可预测，几乎没有"标准路径"

健康度 🟢 的标准：P50 ≤ 8，P95 ≤ 20，P99 ≤ 30。一旦 P99 > 50，必须查 trace。

22.2.4 时延分布与 SLO

时延不像成功率是二值的，而是连续分布。生产 Agent 的 SLO 通常是：

  • P50 ≤ 10s（用户等待"还行"）
  • P95 ≤ 60s（用户等待"勉强接受"）
  • P99 ≤ 180s（用户等待"已放弃"）

长尾是 Agent 时延的最大杀手：单个 LLM 调用可能因推理服务排队 30s，整次任务就被拖到 60s+。应对方案：(a) 设置单步超时 15s；(b) 长 step 自动重试一次；(c) 关键路径 step 走备用模型。

22.2.5 鲁棒性：扰动测试

鲁棒性指标衡量 Agent 对输入变化的容忍度。常见扰动类型：

扰动类型例子鲁棒性测试
同义改写"查订单" → "看下我那个订单"LLM 应识别同一意图
拼写错误"Beijing" → "Beijign"LLM 应自动纠正
多语混合中英混杂的 queryLLM 应稳定处理
极端长度1 字 vs 1000 字 query不应崩溃
注入尝试query 中夹带 "忽略之前指令"应被 guard 拦截

Δ ≤ 5pp 是生产阈值。如果扰动后成功率下降 > 10pp，说明 Agent 对输入分布太敏感，需要 prompt 加固或加 guard。

22.3.2 选基准的 3 个陷阱

  1. 基准漂移：SWE-bench Verified 题目集 6 个月换一批，跨期对比失真
  2. 过拟合：在某个基准调到 90%，换个基准可能只剩 40%
  3. 评测泄漏：基准题目被混入训练集（已在 SWE-bench lite 2025-Q4 出现过一次）

22.3.3 基准组合拳：单跑不够

生产实践推荐"3+1 组合"——3 个公开基准（覆盖不同能力）+ 1 个自建评估集（贴近业务）：

  • SWE-bench —— 代码修改能力下限
  • GAIA —— 多模态 + 推理能力
  • τ-bench —— 多轮对话 + 工具调用
  • 自建评估集 —— 业务真实场景

只跑一个基准会得到片面英雄：在 SWE-bench 上 80% 的 Agent 在客服场景可能只有 30%。

22.3.4 基准与 ch21/ch22 关联

GUI Agent 类任务必须同时跑 OSWorld + WebArena + 自建 GUI 评估集。OSWorld 看桌面 OS 操作能力，WebArena 看浏览器场景能力，自建评估集看真实业务 GUI 流程。三者互补，缺一不可。

进一步，ch21 §21.5.2 提到的 200K 综合 token 上下文对评测有直接影响：上下文越长，trace 越完整，但成本越高。评测时必须把"上下文利用率"作为独立指标，避免 Agent 浪费 context（参 ch03 §3.3 滑动窗口）。

22.4 自建评估集

22.4.1 三步法

生产环境必须自建评估集——公开基准只是 sanity check。三步法（表 22.4.1）：

步名称关键动作工具
1任务采样从生产 trace 中随机抽 200-500 条，按场景分层BigQuery / Snowflake / Pandas
2答案构造人工标注 + LLM 预标 + 双盲交叉Label Studio / Scale AI / 内部标注平台
3评分函数硬指标（成功/失败）+ 软指标（LLM judge）自动化脚本

22.4.2 4 维评分设计

每个任务必须给 4 个分：

  1. 结果分（0/1）：任务是否完成
  2. 效率分（0-1）：步数 / 最优步数
  3. 过程分（0-1）：关键路径是否走对（用 LLM judge 评 trace）
  4. 风格分（0-1）：是否礼貌、是否简洁、是否解释清楚

综合分 = 0.4×结果 + 0.3×效率 + 0.2×过程 + 0.1×风格（权重为示意，生产应根据业务调整）。

22.4.3 数据漂移监控

生产任务分布会随用户行为漂移。每月一次重新采样，对比新旧分布的 KL 散度，> 0.1 触发评估集更新。

22.4.4 评估集的 4 个反模式

反模式表现修正
题量太少只有 50 题，3 题抖动就 ±2pp≥ 200 题，按场景分层
答案太严答案要求"完全匹配字面字符串"允许同义改写，用 LLM judge
题目过时用 2024 年场景评 2026 Agent每月增补新场景
缺乏多样性90% 题都是同一类任务故意覆盖边缘 case

22.4.5 评估集的元数据

每条评估样本应带元数据：

{
  "task_id": "t-2026-04-001",
  "scenario": "order_refund",
  "difficulty": "easy",
  "expected_steps": 4,
  "tags": ["customer_service", "refund", "no_pii"],
  "created_at": "2026-04-15",
  "last_validated": "2026-06-01"
}

元数据让切片分析成为可能：可以分别看"easy 难度 SR 95% vs hard 难度 SR 60%"——这种切片比总平均 SR 更有诊断价值。

22.5.3 Trace 数据量爆炸

一次 Agent 任务平均 8 个 span × 5 KB ≈ 40 KB trace；100 万次任务 = 40 GB / 月。生产必须做采样：1% 全量 + 100% 失败全量 + 关键任务全量。

22.5.4 Span 的 5 个必备字段

每个 span 必须记录以下 5 个字段（缺一不可）：

字段例子缺失后果
span_idspan-7a3f无法串联调用链
parent_span_idspan-5b2e无法看父子关系
start_time2026-07-08T09:00:01.234Z无法算时延
duration_ms1234无法定位慢 span
statusok / error无法统计失败率

少任何一个字段，trace 的诊断价值减半。

22.5.5 Token 消耗的 4 类细分

LLM 调用的 token 必须细分 4 类（表 22.5.5）：

类型含义计费优化方向
input用户消息 + 上下文标准压缩 context
outputLLM 生成的 token1.5-3x input限制 max_tokens
cache_read命中 prompt cache 的 input0.1x input复用 cache
cache_write写入 cache 的 input1.25x input避免重复

生产 Agent 应追求 cache_read 占比 ≥ 60%——这意味着 prompt 模板稳定 + context 复用做得好。

22.5.6 与 ch08 记忆系统的连接

ch08 介绍的长期记忆（向量 / DB / 图谱）也产生 span——每次 retrieve / store 都是一个 span。评测时应单独看"记忆 span 的命中率"和"记忆 span 的时延占比"：

  • 命中率 < 50% → 检索质量差或检索时机不对
  • 时延占比 > 30% → 检索是瓶颈，考虑缓存或预计算

22.6 LLM-as-a-Judge——用模型评模型

22.6.1 何时用 / 何时不能用

场景用 judge不用 judge
主观评分（流畅度 / 礼貌度 / 推理合理性）✅
长答案 vs 短答案✅
自动评分 1000+ 样本✅
评分标准有唯一答案（数学、SQL、JSON Schema 验证）✅ 用规则

22.6.2 4 类 judge 偏差

LLM judge 有 4 个已知的系统性偏差（表 22.6.1）：

偏差表现缓解
位置偏差偏好第一个答案调换顺序双评
长度偏差偏好更长的答案控制长度后评
自我偏好偏好同源模型（如 GPT-4 偏好 GPT-4 输出）换不同源 judge
格式偏差偏好 markdown / bullet / 数字编号控制格式后评

缓解金标准：每个样本用 2-3 个不同源 judge 各评一次，取中位数；偏差 > 0.3 触发人工复核。

22.6.3 Judge Prompt 设计 5 原则

LLM judge 的 prompt 设计直接决定评分质量。5 原则：

  1. 明确评分维度：不要笼统"评一下"，要"按 5 个维度各打 1-5 分"
  2. 给评分 rubric：每个分数段对应什么样的输出
  3. 要求引用原文：让 judge 引用被评答案的具体段落（防止幻觉评分）
  4. 提供 baseline：给一个"标准答案"作为参考锚点
  5. 明确边界条件：什么情况给 0 分、什么情况给满分

22.6.4 GPT-4o judge 实测经验

OpenAI 2026-Q1 公开数据：GPT-4o judge 与人类标注的一致率约 82%（Cohen's κ ≈ 0.82），Claude 4 Opus judge 约 79%（Cohen's κ ≈ 0.79）。两者各有所长：

  • GPT-4o judge 擅长结构化输出（JSON、SQL、表格）
  • Claude judge 擅长开放式推理、代码 review

生产建议：双 judge 串联——GPT-4o 先评结构分，Claude 再评推理分，加权综合。

22.6.5 与 ch06 Prompt 工程的呼应

ch06 介绍的 system prompt 工程方法（角色 / 约束 / 工具描述）同样适用于 judge prompt。一个好的 judge prompt 通常 500-1500 字符，结构与 ch06 §6.2 的 5 块结构一致：

  • 角色："你是一个严格的客服质量评审员"
  • 任务："评估 Agent 的回复是否解决了用户问题"
  • 评分维度：5 个维度 + 每个 1-5 分
  • 评分 rubric：每个分数段的具体描述
  • 输出格式：强制 JSON 输出（含引用原文）

22.7 实战——最小评测流水线

22.7.1 30 行评测流水线（mock mode）

# 文件：minimal_eval_pipeline.py
# 跑通：python3 minimal_eval_pipeline.py
# 零依赖，纯 stdlib（json / dataclasses / statistics）

import json
from dataclasses import dataclass, field
from statistics import mean

@dataclass
class EvalSample:
    task_id: str
    question: str
    expected: str
    actual: str
    steps: int = 0
    cost: float = 0.0
    latency_s: float = 0.0
    judge_score: float = 0.0   # 0-1
    passed: bool = False

@dataclass
class EvalReport:
    total: int = 0
    passed: int = 0
    avg_steps: float = 0.0
    avg_cost: float = 0.0
    avg_latency: float = 0.0
    utility_cost_ratio: float = 0.0
    failures_by_type: dict = field(default_factory=dict)

def mock_llm_judge(expected: str, actual: str) -> float:
    """Mock judge: 字面匹配 1.0，否则 0.0"""
    return 1.0 if expected.strip() == actual.strip() else 0.0

def run_eval(samples: list) -> EvalReport:
    report = EvalReport()
    for s in samples:
        s.judge_score = mock_llm_judge(s.expected, s.actual)
        s.passed = s.judge_score >= 0.8
        report.total += 1
        report.passed += int(s.passed)
        report.failures_by_type.setdefault(
            "wrong_answer" if not s.passed else "ok", 0
        )
        report.failures_by_type[
            "wrong_answer" if not s.passed else "ok"
        ] += 1
    report.avg_steps = mean(s.steps for s in samples) if samples else 0
    report.avg_cost = mean(s.cost for s in samples) if samples else 0
    report.avg_latency = mean(s.latency_s for s in samples) if samples else 0
    success_rate = report.passed / max(report.total, 1)
    report.utility_cost_ratio = success_rate / max(report.avg_cost, 0.01)
    return report

if __name__ == "__main__":
    samples = [
        EvalSample("t1", "1+1=?", "2", "2", steps=2, cost=0.001, latency_s=1.2),
        EvalSample("t2", "capital of France?", "Paris", "Paris", steps=3, cost=0.002, latency_s=1.8),
        EvalSample("t3", "5*7=?", "35", "34", steps=2, cost=0.001, latency_s=1.0),
        EvalSample("t4", "JSON of empty list?", "[]", "[]", steps=4, cost=0.003, latency_s=2.5),
    ]
    report = run_eval(samples)
    print(json.dumps(report.__dict__, indent=2, ensure_ascii=False))

预期输出：3/4 通过，avg_steps 2.75，avg_cost $0.00175，U/C ≈ 75。

22.7.2 Trace 持久化

每条评测样本的 trace 应单独存盘：

# 持久化 trace 到 JSONL
def save_traces(samples: list, path: str):
    with open(path, "w", encoding="utf-8") as f:
        for s in samples:
            f.write(json.dumps(s.__dict__, ensure_ascii=False) + "\n")

22.8.2 评测集版本管理

每次 prompt 改动、tool 改动、模型升级前先跑评测集：

  • ✅ SR 不下降（≤ 2pp）
  • ✅ 步数不增（≤ 10%）
  • ✅ 成本不增（≤ 20%）

不满足三者之一禁止合并——这是 Agent CI 的硬门禁。

22.8.3 EDD 的 4 个最佳实践

  1. 评测集即代码：评测集进 git，与 prompt / tool 同步版本
  2. 回归门禁：每次 PR 必跑评测，不达标禁止合并
  3. 金标集：保留 100 条"从未见过"的样本做月度金标测试
  4. 失败即工单：评测失败的样本自动开 GitHub issue，分配给相关人

22.8.4 EDD 与 A/B 测试的分工

  • EDD = 离线，改 prompt 前跑，看是否回归
  • A/B 测试 = 在线，上线后跑，看真实用户是否更喜欢

两者必须串联：EDD 通过 → 灰度 5% → A/B 显著 → 全量。任何一环失败就回滚。

22.8.5 与 ch04 框架的连接

ch04 介绍的 7 大框架（LangChain / LangGraph / AutoGen / CrewAI / LlamaIndex / Agno / OpenAI Agents SDK）都内建或支持评测集成：

  • LangGraph + LangSmith：原生 trace，EDD 几乎零成本
  • AutoGen：内置 test agent 框架
  • OpenAI Agents SDK：内置 tracing 模块
  • CrewAI：通过 OpenTelemetry 集成

选框架时，可观测性支持应作为权重 ≥ 20% 的考量指标——否则后期改造代价巨大。

22.9.3 Trace Replay

生产 trace 可离线 replay：用真实 trace 输入到新版本 Agent，对比新旧输出 diff。这是模型升级 / prompt 改动前最关键的回归测试。

# 监控告警示例（监控 5 大失败模式）
from dataclasses import dataclass, field
from collections import Counter

@dataclass
class AlertRule:
    name: str
    threshold: float
    severity: str  # P0 / P1 / P2

@dataclass
class FailureDetector:
    rules: list = field(default_factory=lambda: [
        AlertRule("hallucination", 0.10, "P1"),
        AlertRule("loop", 0.05, "P1"),
        AlertRule("unauthorized", 0.0, "P0"),
        AlertRule("latency_p95_60s", 0.20, "P2"),
        AlertRule("cost_1usd", 0.05, "P2"),
    ])

    def detect(self, hourly_stats: dict) -> list:
        """hourly_stats = {"hallucination": 0.12, "loop": 0.03, ...}"""
        alerts = []
        for rule in self.rules:
            rate = hourly_stats.get(rule.name, 0.0)
            if rate > rule.threshold:
                alerts.append({
                    "rule": rule.name,
                    "rate": rate,
                    "threshold": rule.threshold,
                    "severity": rule.severity,
                })
        return alerts

if __name__ == "__main__":
    detector = FailureDetector()
    fake_stats = {"hallucination": 0.12, "loop": 0.03, "unauthorized": 0.0,
                  "latency_p95_60s": 0.15, "cost_1usd": 0.02}
    print(detector.detect(fake_stats))
    # 预期输出：[{"rule": "hallucination", "rate": 0.12, "threshold": 0.10, "severity": "P1"}]

22.10.3 评测成本的"二八法则"

80% 的评测价值来自 20% 的核心指标。盲目堆指标只会拖慢迭代速度。推荐的指标优先级：

优先级指标必须？实现成本
🔴 P0SR / Steps / Cost / Latency必须🟢 低
🟡 P1失败模式分类 / 工具成功率强烈建议🟡 中
🟢 P2鲁棒性扰动 / LLM judge / trace replay成熟期做🔴 高

新项目只做 P0，等 P0 跑稳了再加 P1，最后才考虑 P2。一次性堆 12 个指标的项目 100% 会在第 3 个月废弃指标收集。

22.10.4 评测数据的隐私

trace 数据往往包含敏感信息（用户消息、查询内容、工具返回）。评测数据必须脱敏：

  • ❌ 不存原始用户消息，存 hash
  • ❌ 不存 PII（手机号 / 邮箱 / 身份证），替换为 <PII>
  • ✅ 存 query 意图分类（"查订单" / "退款" / "投诉"）
  • ✅ 存工具调用 + 参数 hash（不存明文参数）

评测数据若泄漏，等同于用户隐私泄漏——这条线不容妥协，也直接呼应 ch23 提示注入防御章节中"trace 中的 PII 是注入攻击者的金矿"这一论断。

评测发现弱点，防御修补弱点。

22.11.4 ch22 内部 4 个核心 takeaway

  1. 评测是 Agent 时代的第一性原理：没有评测就没有改进，没有改进就没有上线。
  2. trace 是一切诊断的根：指标告诉你"发生了什么"，trace 告诉你"为什么"。两者缺一不可。
  3. EDD 应取代裸跑：任何 prompt / tool 改动必须过评测门禁，否则就是"凭感觉改 Agent"。
  4. 告警必须分级：P0 熔断 / P1 15 min / P2 1h。没有分级的告警系统就是"噪声发生器"。

这 4 个 takeaway 是把 ch22 从"知识章节"变成"工程章节"的关键——只讲概念不讲落地的评测章节是失败的。

22.11.5 给读者的 3 步上手建议

如果你是第一次接触 Agent 评测，建议按以下顺序上手：

  1. 本周：把 22.7.1 的 30 行评测流水线跑起来，给自己的 Agent 加 4 个核心指标（SR / Steps / Cost / Latency）
  2. 本月：把 trace 接入 LangSmith 或 Langfuse，把 5 大失败模式告警配好
  3. 本季度：搭评测集 + EDD 流程，做到"任何 prompt 改动都过评测门禁"

三步走完，你的 Agent 就从"能跑"升级为"可度量、可改进、可信任"。这正是 ch22 想要传达的核心理念（时间估算基于 1 人开发小项目，大团队按比例延长）。

22.11.6 给资深工程师的 3 条进阶
