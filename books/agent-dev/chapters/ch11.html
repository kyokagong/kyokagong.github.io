第 11 章：多 Agent 协作模式——Supervisor、Crew、Pipeline、Debate

承上启下：ch10 讲了单 Agent 的 5 大范式（CoT / ToT / Plan-and-Execute / ReAct / LATS）——一个 Agent 自己想、自己做。<br>当任务规模上去、需要多个角色协作时，就要进入多 Agent 系统。<br>本章讲 4 种主流协作模式：Supervisor / Crew / Pipeline / Debate。

11.1 引子：为什么需要多 Agent

11.1.1 单 Agent 的 3 大局限

回想 ch03 的"四大件"——LLM 大脑 + 记忆 + 工具 + 规划。一个 Agent 拥有全部四大件，是不是就能解决所有问题？

现实是：单 Agent 在生产中频繁踩到 3 类天花板。

局限 1：Context Window 瓶颈。

一个 Agent 的所有"思考"都要塞进同一个 context window（ch06 / ch08 都讲过）。哪怕 GPT-5 是 200K tokens、Claude 4.5 是 1M tokens，长视野任务（如分析 50 个文件的代码库、写 2 万字的报告）仍然超出单 context 能力。

局限 2：专业深度不够。

LLM 是个"通才"——什么都懂一点，但任何单一垂直领域（医学 / 法律 / 量化金融）都比不上专门的领域模型。让一个 Agent 同时做需求分析 + 架构设计 + 代码实现 + 测试 = "样样通，样样松"。

局限 3：错误放大。

单 Agent 长链路（规划 → 执行 → 反思 → 重试）每一步都可能出错。错误会沿着链条向下游传播——ch03 的 minimal_agent.py 跑 50 步，第 30 步错了，到第 50 步基本就是错的（即使每步只有 5% 错误率，50 步累计失败率 = 1 - 0.95^50 = 92.3%）。

关键洞察：单 Agent 失败率 5% × 50 步 = 92.3% 累计失败。多 Agent 通过专业化分工 + 多视角校验可降到 30-50%。

11.1.2 多 Agent = 协作涌现

把一个"全能 Agent"拆成 N 个"专精 Agent"，让它们协作：

协作价值 解释 典型场景
专业化 每个 Agent 只负责一件事，可精调 prompt / 选不同模型 / 接专属工具 写代码：架构师 Agent + 程序员 Agent + 测试 Agent
并行化 多个 Agent 同时干活，总耗时 = max(各 Agent) 而非 sum 研究报告：5 个研究员 Agent 各自查 1 个子主题
校验性 一个 Agent 的输出被另一个 Agent 审阅，错误能被捕获 辩论模式（11.5）：正方 Agent + 反方 Agent
可调试性 失败发生在哪个 Agent 一目了然，不用看 100 步的主循环日志 supervisor 模式：每个 worker 出错时 supervisor 单独重试
可扩展性 加一个新角色 = 加一个新 Agent，不用改主循环 客服系统：加"法语客服 Agent"只注册一下
核心论断：多 Agent 不是"性能更强"，是"结构更清晰 + 失败更局部 + 可调试性更高"。

11.1.3 多 Agent 的隐性代价

别急着上多 Agent——它有 3 类隐性代价：

  1. 通信成本 O(N²)：N 个 Agent 两两通信 = N(N-1)/2 条消息（监督者模式下中心化 = O(N)，去中心化 = O(N²)）。5 个 Agent 全连通 = 10 条消息，每个都要 LLM 调用，token 烧得快。
  2. 失败传播：单个 Agent 失败 ≠ 单点失败——它会让下游所有 Agent 都基于错误输入继续。多 Agent 系统需要"熔断"机制（一个 Agent 失败 3 次，整个链路回滚）。
  3. 调试复杂度：单 Agent 1 条主循环日志；多 Agent N 条并行日志 + 消息总线 + 状态共享。没有好的可观测性工具 = 调试黑洞。
决策规则：任务能用单 Agent 干完就别上多 Agent；多 Agent 是结构复杂度的代价换可维护性 + 可扩展性。

11.2 模式 1：Supervisor（监督者模式）

11.2.1 什么是 Supervisor

最经典的多 Agent 模式。1 个 supervisor（监督者）+ N 个 worker（工人）：


            ┌─→ worker_1 (researcher)
supervisor ─┼─→ worker_2 (writer)  
            └─→ worker_3 (reviewer)

supervisor 的职责：决定"下一步让哪个 worker 干活"，根据 worker 的返回决定继续 / 终止 / 重试。

worker 的职责：只负责被分配的具体任务，把结果返回给 supervisor。

典型场景：客服系统、AI 研究助手、复杂任务拆解。

11.2.2 集中调度 vs 去中心化

维度 Supervisor（集中调度） 去中心化（Peer-to-Peer）
消息复杂度 O(N)（全部走 supervisor） O(N²)（N 个 Agent 两两通信）
决策点 1 个（supervisor） N 个（每个 Agent 都决策）
调试难度 低（看 supervisor 日志） 高（消息总线难追踪）
扩展性 加 worker 容易 加 Agent 难（要重新设计通信协议）
典型实现 LangGraph StateGraph + supervisor 节点 AutoGen GroupChat Manager

经验法则：80% 的多 Agent 系统选 Supervisor 就够；去中心化只在"无明确主控者"时用（如多 Agent 辩论）。

11.2.3 Supervisor 的核心数据结构


# LangGraph 风格的状态
state = {
    "messages": [],          # 消息历史（所有 worker 共享）
    "next_worker": "researcher",  # supervisor 决定下一个 worker
    "task": "研究 2026 年 AI Agent 趋势",  # 原始任务
    "results": {},           # 各 worker 的产出（researcher→报告初稿、writer→最终文稿）
    "iteration": 0,          # 循环计数器（防 supervisor 死循环）
}

关键字段：iteration 是防死循环的核心——supervisor 可能一直让同一个 worker 重试，每轮 iteration += 1，超过 10 就强制终止。

11.2.4 Supervisor 模式 Python 完整示例


# ch11_supervisor.py — 60 行最小 Supervisor 模式（mock LLM，可直接跑）
# 场景：研究助手（researcher → writer → reviewer）

from typing import TypedDict, Literal
import json

# ============ 1. 状态定义 ============
class State(TypedDict):
    task: str
    research: str
    draft: str
    review: str
    next_agent: Literal["researcher", "writer", "reviewer", "END"]
    iteration: int

# ============ 2. Mock LLM ============
def mock_llm(prompt: str) -> str:
    """最简 mock：根据 prompt 关键词返回不同结果"""
    if "reviewer 反馈" in prompt or "reviewer_review" in prompt:
        return json.dumps({"next": "END", "approved": True, "comment": "通过"})
    if "已研究" in prompt or "has_research" in prompt:
        return json.dumps({"next": "writer", "instruction": "基于研究写初稿"})
    if "已写初稿" in prompt or "has_draft" in prompt:
        return json.dumps({"next": "reviewer", "instruction": "审阅初稿"})
    return json.dumps({"next": "researcher", "instruction": "开始研究"})

# ============ 3. 3 个 Worker ============
def researcher(state: State) -> State:
    """模拟研究：返回 3 条搜索结果"""
    state["research"] = f"[研究结果] 关于 '{state['task']}':\n1. 2026 多 Agent 系统成为主流\n2. Supervisor 模式最常用\n3. 通信成本是关键挑战"
    state["next_agent"] = "supervisor"
    state["iteration"] += 1
    print(f"  → researcher 完成（iteration={state['iteration']}）")
    return state

def writer(state: State) -> State:
    """模拟写作：把 research 包装成 draft"""
    state["draft"] = f"[初稿] 基于研究：{state['research']}\n\n—— 总结：多 Agent 系统以 supervisor 为主流。"
    state["next_agent"] = "supervisor"
    state["iteration"] += 1
    print(f"  → writer 完成（iteration={state['iteration']}）")
    return state

def reviewer(state: State) -> State:
    """模拟审阅：检查 draft 长度和关键词"""
    ok = len(state["draft"]) > 20 and "supervisor" in state["draft"]
    state["review"] = "通过" if ok else "打回重写（draft 太短）"
    state["next_agent"] = "supervisor"
    state["iteration"] += 1
    print(f"  → reviewer 完成（iteration={state['iteration']}） → {state['review']}")
    return state

# ============ 4. Supervisor 路由 ============
def supervisor(state: State) -> State:
    """决定下一步调用哪个 worker"""
    # 防死循环：iteration > 10 强制结束
    if state["iteration"] > 10:
        print("  → supervisor: 超过 10 轮，强制结束")
        state["next_agent"] = "END"
        return state

    # 构建 prompt 给 mock_llm 决策
    prompt_parts = [f"任务：{state['task']}"]
    if state.get("research"):
        prompt_parts.append("已研究 has_research=True")
    if state.get("draft"):
        prompt_parts.append("已写初稿 has_draft=True")
    if state.get("review"):
        prompt_parts.append(f"reviewer 反馈：{state['review']}")

    prompt = "\n".join(prompt_parts)
    decision = json.loads(mock_llm(prompt))
    state["next_agent"] = decision["next"]
    print(f"  → supervisor 决策：下一步 = {state['next_agent']}")
    return state

# ============ 5. 主循环 ============
def run_supervisor(initial_task: str, max_steps: int = 15):
    state = State(task=initial_task, research="", draft="", review="",
                  next_agent="supervisor", iteration=0)
    print(f"=== Supervisor 模式启动 ===\n任务：{initial_task}\n")
    for step in range(max_steps):
        print(f"[Step {step+1}] 当前 next_agent = {state['next_agent']}")
        if state["next_agent"] == "END":
            break
        if state["next_agent"] == "supervisor":
            state = supervisor(state)
        elif state["next_agent"] == "researcher":
            state = researcher(state)
        elif state["next_agent"] == "writer":
            state = writer(state)
        elif state["next_agent"] == "reviewer":
            state = reviewer(state)
    print(f"\n=== 完成 ===\n最终 draft: {state['draft'][:80]}...")
    return state

if __name__ == "__main__":
    run_supervisor("2026 年 AI Agent 趋势研究")

运行结果：


=== Supervisor 模式启动 ===
任务：2026 年 AI Agent 趋势研究

[Step 1] 当前 next_agent = supervisor
  → supervisor 决策：下一步 = researcher
[Step 2] 当前 next_agent = researcher
  → researcher 完成（iteration=1）
...（writer 完成 + reviewer 通过）
  → supervisor 决策：下一步 = END
=== 完成 ===

11.3 模式 2：Crew（角色团队模式）

11.3.1 什么是 Crew

CrewAI 把多 Agent 抽象成"虚拟团队"：


Crew = Agent_1 (研究员) + Agent_2 (作家) + Agent_3 (编辑)
       +
       Task_1 (收集资料) + Task_2 (写报告) + Task_3 (校对)
       +
       Process (sequential / hierarchical)

每个 Agent 有角色 + 目标 + 背景故事 + 工具；每个 Task 有描述 + 期望输出 + 分配给的 Agent；Process 决定任务执行顺序。

11.3.2 Crew vs Supervisor 的关键区别

维度 Supervisor Crew
控制流 supervisor 动态决定下一步 Task 列表预定义（CrewAI 默认 sequential）
灵活性 高（任务变化时 supervisor 调整） 低（Task 顺序预先定）
易用性 中（要自己实现 supervisor 逻辑） 高（CrewAI 框架封装好）
典型场景 客服、研究助手（动态决策） 报告生成、批量任务（固定流水线）

11.3.3 CrewAI 标准范式


# ch11_crewai.py — 30 行最小 CrewAI 示例
# 场景：3 人虚拟团队生成 2026 AI Agent 趋势报告

from crewai import Agent, Task, Crew

# ============ 1. 定义 3 个 Agent ============
researcher = Agent(
    role="高级研究员",
    goal="收集 2026 年 AI Agent 发展趋势的最新资料",
    backstory="你是一个专注 AI Agent 领域 10 年的研究员，擅长从海量信息中提炼关键趋势。",
    verbose=False,
)

writer = Agent(
    role="技术作家",
    goal="把研究资料写成结构清晰的技术报告",
    backstory="你是一个有 5 年技术写作经验的作家，擅长把复杂概念讲清楚。",
    verbose=False,
)

editor = Agent(
    role="资深编辑",
    goal="审阅报告，确保逻辑通顺 + 数据准确 + 语言流畅",
    backstory="你是一个有 15 年编辑经验的资深编辑，对细节极其敏感。",
    verbose=False,
)

# ============ 2. 定义 3 个 Task ============
task_research = Task(
    description="调研 2026 年 AI Agent 的 3 大关键趋势，输出每条趋势的来源 + 证据。",
    expected_output="3 条趋势，每条 100-200 字，含 1-2 个数据点。",
    agent=researcher,
)

task_write = Task(
    description="基于 task_research 的输出，写一份 800-1000 字的技术报告。",
    expected_output="完整报告，含引言 + 3 节趋势 + 总结。",
    agent=writer,
)

task_edit = Task(
    description="审阅 task_write 的报告，标注需要修改的地方。",
    expected_output="审阅意见（通过 / 修改建议）。",
    agent=editor,
)

# ============ 3. 组建 Crew ============
crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[task_research, task_write, task_edit],
    process="sequential",  # 任务依次执行
    verbose=False,
)

# ============ 4. 启动 ============
if __name__ == "__main__":
    result = crew.kickoff(inputs={"topic": "2026 AI Agent 趋势"})
    print(result)

11.3.4 Crew 模式的 3 大坑

  1. 角色重叠：2 个 Agent 角色太像（如"研究员" + "高级研究员"），互相争抢任务。解决：角色定义要差异化（"调研员" vs "分析师" vs "写作者"）。
  2. Task 依赖：Task 链太长（5+ 步）容易在某一步卡死。解决：把长 Task 拆成多个短 Task。
  3. Process 选错：sequential 适合"线性流水线"；hierarchical 适合"自动委派"。选错会导致任务卡死或乱跳。

11.4 模式 3：Pipeline（流水线模式）

11.4.1 什么是 Pipeline

最古老、最稳定的多 Agent 模式。数据沿固定路径单向流动，每个 Agent 是流水线上的一个"加工站"：


Input → [Agent_1: 解析] → [Agent_2: 转换] → [Agent_3: 输出] → Output

典型场景：数据 ETL（日志 → 解析 → 富化 → 入库）、内容审核（用户输入 → 敏感词过滤 → LLM 改写 → 输出）、RAG 检索增强（ch09）。

11.4.2 Pipeline vs Crew 的本质区别

维度 Pipeline Crew
控制流 固定的 DAG（有向无环图） 可变的（基于 LLM 决策）
状态 中间结果明确（每步产物） 共享上下文（Task 间共享状态）
失败处理 重试该步骤 重做整个 Task
可观测性 极高（每步输入输出明确） 中（Task 内部黑盒）
典型实现 LangGraph StateGraph（显式节点） CrewAI Process

11.4.3 Pipeline vs Crew 的"失败重试"哲学差异

失败场景 Pipeline 哲学 Crew 哲学
单个节点出错 重跑该节点（输入可重放） 重做整个 Task（Task 内部可能修改了外部状态）
节点超时 跳过该节点 + 标记 partial output 整个 Crew 终止 + 人工介入
数据不一致 用 schema 校验（pydantic）拒绝不合规数据 用 reviewer Task 兜底

关键洞察：Pipeline 假设每步是"纯函数"（输入相同 = 输出相同），所以能安全重试；Crew 假设 Task 是"有副作用"（Task A 写了数据库，Task B 读数据库），所以重试可能重复副作用——Pipeline 比 Crew 更适合金融 / 医疗等可重试性要求高的场景。

11.4.4 Pipeline Python 完整示例


# ch11_pipeline.py — 50 行最小 Pipeline 模式
# 场景：用户评论自动处理（解析 → 情感分析 → 回复生成）

from typing import TypedDict
from langgraph.graph import StateGraph, END

# ============ 1. 状态定义 ============
class PipelineState(TypedDict):
    raw_text: str        # 原始评论
    parsed: dict         # 解析后：{用户, 平台, 时间}
    sentiment: str       # 情感：正面/负面/中性
    reply: str           # 自动回复

# ============ 2. 3 个加工节点 ============
def parse_node(state: PipelineState) -> PipelineState:
    """步骤 1：解析原始文本（提取用户、平台、时间）"""
    text = state["raw_text"]
    state["parsed"] = {
        "用户": text.split("@")[1].split("：")[0] if "@" in text else "匿名",
        "平台": "微博" if "微博" in text else "其他",
        "时间": "2026-06-22",
    }
    print(f"  [parse] → {state['parsed']}")
    return state

def sentiment_node(state: PipelineState) -> PipelineState:
    """步骤 2：情感分析（mock）"""
    text = state["raw_text"]
    if any(k in text for k in ["好", "棒", "喜欢", "满意"]):
        state["sentiment"] = "正面"
    elif any(k in text for k in ["差", "糟", "失望", "退款"]):
        state["sentiment"] = "负面"
    else:
        state["sentiment"] = "中性"
    print(f"  [sentiment] → {state['sentiment']}")
    return state

def reply_node(state: PipelineState) -> PipelineState:
    """步骤 3：生成自动回复（基于情感）"""
    if state["sentiment"] == "正面":
        state["reply"] = "感谢您的好评，期待您再次光临！"
    elif state["sentiment"] == "负面":
        state["reply"] = "非常抱歉给您带来不便，客服将尽快联系您处理。"
    else:
        state["reply"] = "感谢您的反馈。"
    print(f"  [reply] → {state['reply']}")
    return state

# ============ 3. 构建 Pipeline ============
workflow = StateGraph(PipelineState)
workflow.add_node("parse", parse_node)
workflow.add_node("sentiment", sentiment_node)
workflow.add_node("reply", reply_node)

workflow.set_entry_point("parse")
workflow.add_edge("parse", "sentiment")
workflow.add_edge("sentiment", "reply")
workflow.add_edge("reply", END)

app = workflow.compile()

# ============ 4. 启动 ============
if __name__ == "__main__":
    sample = "@张三：你们家的产品太差了，我要退款！"
    result = app.invoke({"raw_text": sample, "parsed": {}, "sentiment": "", "reply": ""})
    print(f"\n最终回复：{result['reply']}")

运行结果：


  [parse] → {'用户': '张三', '平台': '其他', '时间': '2026-06-22'}
  [sentiment] → 负面
  [reply] → 非常抱歉给您带来不便，客服将尽快联系您处理。
最终回复：非常抱歉给您带来不便，客服将尽快联系您处理。

11.5 模式 4：Debate（辩论模式）

11.5.1 什么是 Debate

多个 Agent 扮演不同立场，互相辩论，最终由"裁判 Agent"裁决。

源自 Du et al. 2023《Improving Factuality and Reasoning in Language Models through Multiagent Debate》——核心发现：多 Agent 辩论比单 Agent 自问自答在事实性 / 推理任务上提升 5-15 pp。

11.5.2 Debate 的 3 类角色

角色 职责 典型 prompt
正方 持 A 立场，给出证据 "你是 X 派，列出 3 条支持 X 的证据"
反方 持 B 立场，攻击正方 "你是 Y 派，指出正方的 2 个漏洞"
裁判 综合双方，给最终结论 "基于以上辩论，给出最终答案 + 理由"

11.5.3 Debate 适用场景 vs 不适用场景

适用：

  • 事实核查（多视角校验减少幻觉）
  • 复杂决策（买股票、选技术栈，列出正反面）
  • 教育 / 培训（苏格拉底式提问）

不适用：

  • 创意写作（辩论会扼杀发散思维）
  • 快速响应（辩论 = 至少 3 轮，慢）
  • 成本敏感任务（每轮 3 个 Agent = 3× token 成本）

11.5.4 Debate Python 完整示例


# ch11_debate.py — 50 行最小 Debate 模式
# 场景：是否应该在生产环境用多 Agent 系统（正反方辩论 + 裁判）

# ============ 1. 正方 Agent ============
def pro_agent(topic: str) -> str:
    return f"""[正方观点] 关于 '{topic}'：
  证据 1：多 Agent 系统提升 5-15 pp 事实性（Du et al. 2023）
  证据 2：supervisor 模式让失败局部化，可调试性高
  证据 3：可扩展性好——加 worker 即可，不必改主循环"""

# ============ 2. 反方 Agent ============
def con_agent(topic: str) -> str:
    return f"""[反方观点] 关于 '{topic}'：
  论点 1：通信成本（详见 §11.9.1：5 个 Agent 全连通 = 10 条消息 / Supervisor 集中 = O(N)），token 烧得快
  论点 2：失败传播——单 Agent 失败会影响下游所有 Agent
  论点 3：调试复杂——N 条并行日志 + 状态共享是调试黑洞"""

# ============ 3. 裁判 Agent ============
def judge_agent(topic: str, pro: str, con: str) -> str:
    """综合双方 + 给出最终建议"""
    # 模拟 LLM 裁判：基于关键词做最简决策
    if "通信成本" in con and "局部化" in pro:
        return f"""[裁判结论] '{topic}'：
  推荐：**任务能用单 Agent 干完就别上多 Agent**。
  理由：正方的"可调试性 + 失败局部化"是真实价值，但反方的"通信成本 + 调试复杂"也是真实代价。
  决策规则：单 Agent 失败率 < 5% 用单 Agent；> 5% 或 > 30 步才考虑多 Agent。"""
    return f"[裁判结论] 数据不足，无法裁决。\n正方：{pro[:50]}\n反方：{con[:50]}"

# ============ 4. 启动辩论 ============
if __name__ == "__main__":
    topic = "是否应该在生产环境用多 Agent 系统？"
    print(f"=== Debate 模式启动 ===\n辩题：{topic}\n")
    pro = pro_agent(topic)
    print(pro)
    print()
    con = con_agent(topic)
    print(con)
    print()
    final = judge_agent(topic, pro, con)
    print(final)

11.6.4 4 大模式的"失败处理"统一对照表

失败类型 Supervisor 怎么处理 Crew 怎么处理 Pipeline 怎么处理 Debate 怎么处理
单 worker / 节点失败 让同一 worker 重试 N 次 整个 Task 重做 重跑该节点 让反方攻击正方漏洞

11.7 实战：用 LangGraph 实现 Supervisor 模式（完整版）

11.7.1 目标

用 LangGraph StateGraph 写一个生产级 Supervisor——比 §11.2.4 的 60 行手写循环更稳健（带图结构 + 显式路由 + 防死循环）。

§11.2.4 vs §11.7.2 的关系：§11.2.4 是"60 行手写循环"（理解 Supervisor 本质），§11.7.2 是"80 行 LangGraph StateGraph"（生产级实现）。两者讲同一模式的不同抽象层级——读完两份才能完整理解 Supervisor。

11.7.2 完整代码


# ch11_langgraph_supervisor.py — 80 行 LangGraph Supervisor
# pip install langgraph langchain-openai  （mock 模式无需真实 API）

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, END

# ============ 状态 ============
class ResearchState(TypedDict):
    task: str
    research: str
    draft: str
    review: str
    next: Literal["researcher", "writer", "reviewer", "__end__"]
    iteration: int
    max_iter: int

# ============ Mock LLM（生产替换为 ChatOpenAI） ============
def mock_llm_decide(state: ResearchState) -> str:
    """基于 state 决定下一步（mock）"""
    if state.get("review") and "通过" in state["review"]:
        return "__end__"
    if state.get("research") and not state.get("draft"):
        return "writer"
    if state.get("draft") and not state.get("review"):
        return "reviewer"
    return "researcher"

# ============ 3 个 Worker ============
def researcher(state: ResearchState) -> ResearchState:
    state["research"] = f"[研究] '{state['task']}': 2026 多 Agent 系统主流，supervisor 模式估计占 50-70%（业界估算，非严格统计）。"
    state["iteration"] += 1
    print(f"  [worker:researcher] 完成 (iter={state['iteration']})")
    return state

def writer(state: ResearchState) -> ResearchState:
    state["draft"] = f"[初稿] {state['research']} —— 总结：supervisor 模式最适合动态决策。"
    state["iteration"] += 1
    print(f"  [worker:writer] 完成 (iter={state['iteration']})")
    return state

def reviewer(state: ResearchState) -> ResearchState:
    ok = "supervisor" in state.get("draft", "") and len(state["draft"]) > 20
    state["review"] = "通过" if ok else "打回（draft 缺关键词或太短）"
    state["iteration"] += 1
    print(f"  [worker:reviewer] 完成 (iter={state['iteration']}) → {state['review']}")
    return state

# ============ Supervisor 路由节点 ============
def supervisor_node(state: ResearchState) -> ResearchState:
    if state["iteration"] >= state["max_iter"]:
        print(f"  [supervisor] 达到 max_iter={state['max_iter']}，强制结束")
        state["next"] = "__end__"
        return state
    state["next"] = mock_llm_decide(state)
    print(f"  [supervisor] 决策：next = {state['next']}")
    return state

# ============ 路由函数（决定图走向） ============
def route_decision(state: ResearchState) -> str:
    return state["next"]

# ============ 构建图 ============
workflow = StateGraph(ResearchState)
workflow.add_node("supervisor", supervisor_node)
workflow.add_node("researcher", researcher)
workflow.add_node("writer", writer)
workflow.add_node("reviewer", reviewer)

workflow.set_entry_point("supervisor")

# supervisor → worker
workflow.add_conditional_edges("supervisor", route_decision, {
    "researcher": "researcher",
    "writer": "writer",
    "reviewer": "reviewer",
    "__end__": END,
})

# worker → supervisor（每次 worker 完成后回到 supervisor 决定下一步）
workflow.add_edge("researcher", "supervisor")
workflow.add_edge("writer", "supervisor")
workflow.add_edge("reviewer", "supervisor")

app = workflow.compile()

# ============ 启动 ============
if __name__ == "__main__":
    initial = ResearchState(
        task="研究 2026 多 Agent 系统趋势",
        research="", draft="", review="",
        next="supervisor", iteration=0, max_iter=10,
    )
    print("=== LangGraph Supervisor 启动 ===\n")
    result = app.invoke(initial)
    print(f"\n=== 完成 ===\n最终 draft：{result['draft'][:80]}...")

11.8 实战：用 CrewAI 实现 Crew 模式

CrewAI 是当前最成熟的"虚拟团队"框架。ch11.3.3 已给最小示例，本节补充生产级 3 个要点。

11.8.1 Agent 定义三大纪律

  1. role 单一职责："研究员"和"高级研究员"是 2 个角色，不要写 1 个 role 把 3 件事干完。
  2. backstory 200 字以内：用 1 段话定义"我是谁、专长什么、风格如何"，别写小说（LLM 不会读 500 字 backstory）。
  3. goal 可衡量：写"输出 3 条趋势，每条 100 字"而非"调研 AI Agent"。

11.8.2 Task 定义三大纪律

  1. expected_output 写明：LLM 才知道交付什么形态（"3 条 100 字趋势" vs "1000 字报告"）。
  2. agent 显式指定：别用 crew.kickoff() 自动分配，Task 必须明确 agent。
  3. dependencies 显式声明：task_write.context = [task_research] —— 让 Task 知道依赖。

11.8.3 Process 三选项

选项 行为 适用
sequential Task 按列表顺序执行 大多数场景
hierarchical 自动选 manager + 委派 复杂任务，manager 自动拆分
consensual Manager 协商（2026 新功能） 需多视角校验

11.9 通信成本与失败传播

11.9.1 通信成本 O(N²) 详解

N 个 Agent 的两两通信消息数：

N 全连通消息数 Supervisor 模式 成本比
2 2 2 1×
3 6 3 2×
5 20 5 4×
10 90 10 9×

经验法则：去中心化多 Agent 不要超过 5 个 Agent（否则通信爆炸）。超过就用分层 Supervisor（supervisor 管 supervisor）。

11.9.2 失败传播模型

单 Agent：失败率 p，每步独立。n 步后累计失败 = 1 - (1-p)^n。

多 Agent：N 个 Agent 串联，失败率 = 1 - (1-p)^(N × n/N) = 1 - (1-p)^n（等价）。

但：多 Agent 引入协作失败（消息丢失 / 上下文不一致），实际失败率 = (1-p)^n × (1-q)^m，q 是协作失败率（典型经验值 1-3% / 消息），m 是消息数。

关键洞察：多 Agent 不直接降低失败率，它降低的是失败的爆炸半径——单 Agent 全链路崩，多 Agent 只崩 1 个 worker。

11.9.3 3 种熔断机制

机制 做法 适用
重试上限 同一 worker 失败 N 次 → 跳过 所有场景
断路器 整个链路失败率 > 阈值 → 暂停 5 分钟 生产 API
降级 worker 失败 → 退回单 Agent 模式 关键路径

11.10 5 大坑

11.10.1 坑 1：单 Agent 化（"多 Agent 假装是单 Agent"）

症状：supervisor 把所有任务都委派给同一个 worker，本质还是单 Agent。

诊断：看日志，如果 1 个 worker 被调用 > 80% 步数 = 出了问题。

修复：worker 角色要差异化；supervisor 路由逻辑要分散。

11.10.2 坑 2：Supervisor 死循环

症状：supervisor 一直让 researcher 重试，iteration 飙到 50 还没完。

诊断：iteration > 10 应该自动终止。

修复：max_iter 必填 + 每轮 iteration += 1 + 超过强制 END。

11.10.3 坑 3：Crew 任务冲突

症状：Task_A 修改了 Task_B 需要的输入，导致 Task_B 输出错乱。

诊断：Task 顺序错乱 + 共享状态没隔离。

修复：每个 Task 的输入显式声明，不依赖隐式共享。

11.10.4 坑 4：通信风暴

症状：5 个 Agent 全连通，每轮 20 条消息，token 成本 ×10。

诊断：消息总线消息数 > Agent 数 × 5。

修复：改 Supervisor 集中模式；或分层 Supervisor。

11.10.5 坑 5：调试黑洞

症状：多 Agent 系统报错，不知道哪个 Agent 出问题。

诊断：没有结构化日志（每条消息带 agent 名 + 时间戳 + 输入输出）。

修复：用 LangSmith / LangGraph Studio / AutoGen Studio 等可观测性工具。

11.11 本章小结

11.11.1 8 条速记

  1. 单 Agent 失败率 5% × 50 步 = 92.3% 累计失败——多 Agent 的真正价值是失败局部化
  2. 4 大模式：Supervisor（动态）/ Crew（团队）/ Pipeline（流水线）/ Debate（辩论）
  3. Supervisor 是 80% 多 Agent 的默认选择（集中调度 + 易调试）
  4. Pipeline 是数据流动场景的最优解（RAG / ETL / 内容审核）
  5. Debate 只在多视角校验时用（事实核查 / 复杂决策），代价是 ×10-30 token
  6. 通信成本 O(N²)——多 Agent 不要超过 5 个
  7. 失败传播——多 Agent 不降低失败率，降低失败爆炸半径
  8. 决策规则：单 Agent 能干完就别上多 Agent
