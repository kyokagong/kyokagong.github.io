第1章 什么是 AI Agent

“从一个会聊天的窗口，到一个会替你做事的同事——这是过去两年 AI 行业最值得讲清楚的变化。”

1.1 引子：从 ChatGPT 到 Agent——一个被反复念叨的"下一步"

2022 年 11 月，ChatGPT 发布。两个半月，月活用户突破 1 亿——这是人类历史上消费级软件扩张最快的一次。

但如果你仔细回想 2023 年整个 AI 行业最热闹的词，它不是 GPT-4，不是 GPTs，也不是 Sora。它是 Agent。

从 2023 年 3 月的 AutoGPT，到 4 月的 BabyAGI，再到 2024 年 Anthropic 的 Computer Use、OpenAI 的 Operator、Google 的 Gemini Agent……每隔几个月，就有一家公司站出来说："我们做出了真正的 Agent。" 但每家公司对"真正"的定义又都不太一样。

2026 年的今天，Agent 这个词已经渗透到了 AI 行业的每一个角落。翻开任何一家大厂的发布会幻灯片、招聘 JD、GitHub README，你都会看到它。但与此同时，它也是被滥用得最严重的词——

  • 一个加了"工具调用"（function calling）的 ChatGPT 接口，可以被叫做 Agent。
  • 一个预设了若干 if-else 分支的工作流，也会被叫 Agent。
  • 一个能在浏览器里点鼠标的脚本，同样叫 Agent。

所以在我们深入到第 28 章的 AGI 远景之前，我们得先把一件事讲清楚——

到底什么是 AI Agent？它和 LLM 有什么区别？它和"传统的"软件程序又有什么不一样？

这是这一章的全部任务。

1.2 Agent 的工作定义——三家头部厂商的口径对比

定义这种东西，普通人写出来叫"个人观点"，头部厂商写出来的才叫"行业事实"。下面我们看三家——Anthropic、OpenAI、Google——在 2024-2026 年陆续给出的官方定义。

1.2.1 Anthropic 的定义

Anthropic 在 2024 年 12 月发表的工程博客 Building Effective Agents 中这样描述：

Agents are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.

翻译过来就是：Agent 是让 LLM 动态决定自己的处理流程和工具使用、掌控任务完成方式的一类系统。

Anthropic 特别强调了一个关键区分：

  • Workflow：开发者预先定义好"先 A 再 B 再 C"的固定路径，LLM 只是流水线上的一个执行者。
  • Agent：开发者只给目标，具体怎么走由 LLM 现场决定。

举例：用户说"帮我订一家今晚 7 点、距离我公司 3 公里内、人均 200 块以内、有包间的川菜馆"。

  • Workflow 版的做法：先调地图 API 拿 3 公里内餐厅列表 → 再调筛选 API 按价格过滤 → 再调评论 API 选评分最高的 → 再调预订 API 下单。每一步都写死。
  • Agent 版的做法：模型自己思考"我需要先拿到候选列表"→ 调地图 API → 拿到结果后思考"接下来要按价格筛"→ 调筛选工具 → 继续思考"包间这个信息可能在评论里"→ 调评论 API → ……整个决策链是模型自己生成的。

1.2.2 OpenAI 的定义

OpenAI 在 2025 年发布的 A Practical Guide to Building Agents 中给出这样的描述：

Agents are AI systems that can independently work towards goals by combining language models with tools.

OpenAI 的定义比 Anthropic 短得多，但多了一个关键词：goal（目标）。OpenAI 把 Agent 拆成三个核心要素：

  1. Model（模型）——驱动推理的 LLM。
  2. Tools（工具）——模型可以调用的函数、API、代码执行环境。
  3. Instructions / Guardrails（指令与护栏）——告诉模型"你是什么、你的目标是什么、什么不能做"。

OpenAI 还在文档中专门指出，很多被叫 Agent 的东西其实只是 Workflow——这一点和 Anthropic 看法完全一致。

1.2.3 Google / DeepMind 的定义

Google 在 2024-2025 年陆续发布的 Agent 文档中，倾向于使用"agentic systems"（能动系统）这个稍微学究的术语，强调 Agent 是一个连续运行的能动实体，而不是一次性函数调用。

DeepMind 的论文 Levels of AGI（Morris et al., 2023）主要讨论"AGI 的层级（Level 0-5）"，虽不直接定义 Agent，但为"什么算自主系统"提供了一些思考；Google Cloud 在 2025 年发布的 Agents Companion 白皮书则更直接地把 Agent 定义为"能感知环境、做出决策、并在世界中行动的 AI 系统"（"AI systems that can perceive their environment, make decisions, and take actions in the world"）。

1.2.4 一个综合定义

把三家放在一起，我们可以拼出一个折中的工作定义：

AI Agent 是一个由 LLM 驱动的、能够根据用户目标自主决策、调用工具、维护状态、并完成多步任务的软件系统。

这个定义里有 5 个关键词：

  • LLM 驱动——大脑。
  • 自主决策——不是被脚本牵着走。
  • 调用工具——能伸手碰外部世界。
  • 维护状态——有记忆。
  • 多步任务——能连续做事。

任何系统只要缺了其中之一，它要么是"带 LLM 的 workflow"，要么是"加了 prompt 的传统软件"，不是我们这本书要讲的 Agent。

1.3 Agent 五大核心特征

抽象的定义看完了，我们来拆得再细一点。一个真正"够格"的 Agent，必须具备以下 5 个核心特征。

1.3.1 特征一：自主性（Autonomy）

Agent 收到一个目标后，可以自己决定要分几步走、用什么工具、中间如果失败要不要重试。

这是和"传统软件"最大的区别。传统软件里，每一行代码、每一个分支都是程序员写死的；Agent 里，至少有一部分决策权是让给 LLM 的。

举一个更具体的例子。一个"自动订机票 Agent"，用户说"下周去上海开个会"：

  • 自主性弱的版本：按"查航班 → 比价 → 出票"固定三步走。如果航班全卖完了，它就停在那里报错。
  • 自主性强的版本：航班卖完了，自己决定改查高铁、查附近机场、甚至问用户"要不要把会议挪一天"。

自主性不是"无约束"，而是"在约束下自己选路径"。你仍然可以给 Agent 加"不许自行下单超过 500 块"这种护栏，但护栏之内的部分，模型是有自由度的。

1.3.2 特征二：目标驱动（Goal-driven）

Agent 是被目标驱动的，不是被指令驱动的。

  • 指令驱动的对话（ChatGPT）："请把这段话翻译成英文。"
  • 目标驱动的 Agent："帮我把这份季度报告做好。"

用户给的是终点，路径由 Agent 自己规划。

这个区别听起来抽象，但它直接决定了用户体验的天差地别。

  • 指令式：你需要自己知道"季度报告要先列大纲、再填数据、再画图"，然后一条条告诉 ChatGPT。
  • 目标式：你只需要说"做季度报告"——Agent 自己会追问你"Q3 的数据用哪份？需要包含哪些竞品对比？"

好的 Agent 在目标驱动的同时还会主动澄清模糊目标（clarification），而不是一接到目标就闷头乱跑。这一能力在 2025 年后的 Agent 框架（OpenAI Agents SDK、LangGraph）里已经被产品化。

1.3.3 特征三：工具使用（Tool Use）

光靠 LLM 本身什么都做不了——它只会"说话"。Agent 必须能调用外部工具：

  • 搜索引擎
  • 数据库查询
  • 代码执行环境
  • 文件读写
  • 第三方 API（订餐、发邮件、订机票）
  • 甚至真实的键盘鼠标（Computer Use）

工具是 Agent 的"手"。

值得展开说的是：工具的设计本身就是 Agent 工程的核心难点。

一个反例：你给 Agent 写一个工具叫 book_flight(from, to, date)。模型传进来的 date 是 "next Friday"。你的工具崩了——因为它要 YYYY-MM-DD。一个好的 Agent 工具，应该把"自然语言 → 工具参数"这一步也做掉，定义成 book_flight(from_city, to_city, natural_date, ...)，内部用 LLM 把 "next Friday" 解析成 "2026-06-13"。

我们会在第 7 章详细讲"如何设计一个好的 Agent 工具"。

⚠️ 关于"代码执行环境"特别提醒：这是列表中安全风险最高的工具——它让 Agent 拥有"自我编程"的能力，但也是攻击面最大的入口。任何允许 Agent 跑代码的系统，都必须做沙箱隔离（Docker / Firecracker / gVisor / Wasm）。2024-2025 年多起 Agent 安全事件（Vanna AI 提示注入导致数据外泄、Replit 误删生产数据库）都和这个工具有关。第 23 章会深入讲 Agent 安全。

1.3.4 特征四：记忆（Memory）

LLM 单次对话是"金鱼脑"——超过上下文窗口就忘。Agent 需要显式地管理记忆：

  • 短期记忆：当前对话上下文。
  • 长期记忆：跨会话的用户偏好、历史任务记录。
  • 工作记忆：任务执行到第几步、已经查过哪些数据。

记忆是 Agent 的"经验"。

记忆的工程实现有 3 种主流方案：

  1. 全量塞进上下文窗口——最简单，超过限制就崩。
  2. 滑动窗口 + 摘要压缩——保留最近 N 轮 + 早期对话的 LLM 摘要。
  3. 向量数据库 + 检索——把历史消息存成 embedding，必要时按相似度检索回来。

第 8 章会专门讲记忆系统。

1.3.5 特征五：规划（Planning）

一个复杂任务不能一锤子搞定。Agent 需要先规划、后执行：

  • 把"做一份市场调研报告"拆成 5 步：列大纲 → 搜数据 → 写各章节 → 校对 → 出 PDF。
  • 任务执行中如果某一步失败，要能重新规划（replan）。

规划是 Agent 的"脑子"。

规划有两种实现方式：

  • 静态规划（Plan-and-Execute）：先一次性把整个计划生成好，然后按计划走。优点是可解释；缺点是遇到意外不灵活。
  • 动态规划（ReAct / Reflexion）：每执行一步就重新决定下一步。优点是灵活；缺点是容易跑偏、容易死循环。

实际生产中，大多数 Agent 框架都用"先静态规划一个大框架，过程中允许局部动态调整"的混合方式。第 10 章会展开。

一个常见的误区是觉得"加了 function calling 就算 Agent"。但如果你把决策树全部写死、工具调用顺序由代码控制、模型没有任何自主权——那只是一个带 LLM 的传统程序。真正的 Agent 至少要在"决策链"上让出部分控制权。

1.4 Agent vs. LLM：本质差异

很多人初学 Agent 时的第一个困惑：LLM 本身不就是对话的吗？Agent 和 LLM 到底是什么关系？

我们用一个表格讲清楚：

维度LLMAgent
核心能力文本生成、推理在 LLM 之上加自主行动
输入一段 prompt一个目标
输出一段文字一连串动作 + 最终结果
工具使用取决于 API 本身（GPT-4 可以做 function calling，但模型本身不会主动调）模型自己决定何时调、调哪个
状态管理上下文窗口（受 token 限制）显式的记忆系统
典型交互"写一首关于秋天的诗""帮我组织一次秋季团建"
失败处理模型"尽力"回答能重试、回滚、换工具

一句话总结：LLM 是大脑，Agent 是大脑 + 手 + 眼睛 + 记忆组成的一个完整的人。

1.5 Agent vs. Chatbot：交互范式差异

我们日常用的 ChatGPT、文心一言、Claude.ai……它们是 Chatbot。Chatbot 和 Agent 的区别，本质是"会话轮次"和"任务深度"的差异。

  • Chatbot 的核心单位是"一次对话"。你说一句，它答一句。整段对话结束时，任务通常就完成了。
  • Agent 的核心单位是"一个目标"。目标完成前，Agent 可以做无数次工具调用、跨多个系统、跨很长时间。

经典场景对比：

用户："帮我订明天早上 8 点去北京的高铁票，要靠窗。"

  • Chatbot 的回答："建议您使用 12306 购买。常见车次有 G1、G3……"
  • Agent 的反应：自动登录 12306 → 查询明早 8 点车次 → 筛选靠窗座位 → 询问用户"已为您找到 3 个车次，确认下单 G3（08:00 北京西，座位 12A）吗？" → 用户确认 → 自动下单 → 返回订单号。

差别巨大。一个是"告诉你怎么办"，另一个是"替你办"。

1.6 Agent vs. 传统软件程序

这一节是给"程序员"写的。

传统软件程序（一个 HTTP 服务、一个 CLI 工具、一个桌面 App）它的本质是：

程序员预定义了所有可能的情况，并为每种情况写了处理代码。

传统软件的优势是确定性强、可测试、可审计；劣势是遇到没预设的情况就崩。

Agent 的本质则是：

程序员只预定义了"目标"和"可用工具"，具体路径由 LLM 现场生成。

Agent 的优势是灵活、能处理开放性问题；劣势是不可预测、需要护栏、需要可观测性。

两者不是替代关系，而是互补关系。一个生产环境的 Agent 系统几乎一定是"传统软件 + Agent 模块"组合：核心业务流程还是确定性代码（订单系统、支付系统），只有"理解用户意图、调用决策"这种开放性环节才交给 Agent。

举一个真实生产架构的例子。一个电商客服 Agent：

  • 传统软件部分（确定性强）：订单查询 API、支付状态 API、退款流程、退款金额校验、欺诈检测。
  • Agent 部分（开放性强）：理解用户抱怨、识别用户意图（是要查订单？要投诉？要退货？）、决定是否需要追问、向用户解释处理结果。

这种"传统软件搭骨架、Agent 做皮肉"的混合架构，是 2026 年工业界 Agent 落地的主流形态。第 27 章我们会用更多真实案例来拆解这种架构。

1.7 一个最小可运行的 Agent

光说不练假把式。这一节我们写一个真的能跑的最简 Agent。

它不依赖任何外部 API、不调 OpenAI 或 Claude——我们手写一个"假 LLM"，演示 Agent 的核心循环：观察 → 思考 → 行动。

在写代码之前，我们先讲讲它背后的"Agent 循环"（Agent Loop）思想。几乎所有 Agent 框架（LangChain、LangGraph、AutoGen、CrewAI、Agno、OpenAI Agents SDK）底层都是这个循环的某种变体。

Agent 循环的本质是 4 件事：把"我现在的状态 + 我的目标 + 我的工具"喂给 LLM；让 LLM 决定下一步做什么；执行这一步；把执行结果塞回状态，再喂给 LLM——直到 LLM 认为任务完成。看起来简单，但工程上的所有难点都藏在这 4 步里：怎么管理状态、怎么压缩历史、怎么处理工具错误、怎么防止 LLM 跑偏、怎么让循环停下来、怎么记录每一步做审计……这本书的后 27 章，会逐一拆开这些难点。

"""
minimal_agent.py
一个最小可运行的 Agent 演示
不需要任何外部依赖，python3 直接跑
"""

import json  # noqa: F401  # 保留以示 JSON 化输出
import re  # noqa: F401  # 实际工程中常用 re 解析 LLM 输出
from typing import Callable


# ============ 1. 假 LLM：用规则模拟模型思考 ============
class FakeLLM:
    """一个完全用规则驱动的'假 LLM'，用来演示 Agent 思考链"""

    def __init__(self):
        self.step = 0
        self.answers = ["北京", "晴天", "今天北京晴天"]

    def think(self, history: list, tools: list) -> dict:
        """模型看到历史和可用工具，'思考'后返回 JSON"""
        self.step += 1

        if self.step == 1:
            return {
                "thought": "用户想知道天气，我需要先查城市对应的天气代码",
                "action": "lookup_weather_code",
                "action_input": {"city": "北京"}
            }
        elif self.step == 2:
            return {
                "thought": "拿到城市代码后，我需要去查实时天气",
                "action": "query_weather",
                "action_input": {"code": "BJ"}
            }
        else:
            return {
                "thought": "我已经拿到结果，可以直接回答用户",
                "action": "FINISH",
                "action_input": {"answer": self.answers[2]}
            }


# ============ 2. 工具集：模型可以调用的'手' ============
TOOLS: dict[str, Callable] = {
    "lookup_weather_code": lambda city: "BJ" if city == "北京" else "UNKNOWN",
    "query_weather": lambda code: "晴天" if code == "BJ" else "未知",
}


# ============ 3. Agent 主循环 ============
class MinimalAgent:
    """Agent 的核心循环：观察 → 思考 → 行动 → 观察 → ... → 完成"""

    def __init__(self, llm, tools, max_steps=10):
        self.llm = llm
        self.tools = tools
        self.max_steps = max_steps
        self.history = []  # 记忆：所有历史动作

    def run(self, goal: str) -> str:
        print(f"\n🎯 目标: {goal}\n")
        self.history.append({"role": "user", "content": goal})

        for step in range(1, self.max_steps + 1):
            print(f"───── Step {step} ─────")

            # 1. 思考：让 LLM 决定下一步
            decision = self.llm.think(self.history, list(self.tools.keys()))
            print(f"🤔 思考: {decision['thought']}")

            # 2. 是否结束
            if decision["action"] == "FINISH":
                answer = decision["action_input"]["answer"]
                print(f"✅ 完成: {answer}")
                return answer

            # 3. 行动：调用工具
            action = decision["action"]
            params = decision["action_input"]
            print(f"🛠  行动: {action}({params})")

            if action not in self.tools:
                result = f"错误：未知工具 {action}"
            else:
                try:
                    result = self.tools[action](**params)
                except Exception as e:
                    result = f"错误：{e}"

            print(f"👀 观察: {result}")

            # 4. 把这一轮记到记忆里
            self.history.append({
                "role": "assistant",
                "thought": decision["thought"],
                "action": action,
                "action_input": params,
                "observation": result,
            })

        raise RuntimeError("达到最大步数仍未完成目标")


# ============ 4. 跑起来 ============
if __name__ == "__main__":
    llm = FakeLLM()
    agent = MinimalAgent(llm, TOOLS)
    final = agent.run("北京今天天气怎么样？")
    print(f"\n📝 最终答案: {final}")

跑一下你会看到这样的输出：

🎯 目标: 北京今天天气怎么样？

───── Step 1 ─────
🤔 思考: 用户想知道天气，我需要先查城市对应的天气代码
🛠  行动: lookup_weather_code({'city': '北京'})
👀 观察: BJ
───── Step 2 ─────
🤔 思考: 拿到城市代码后，我需要去查实时天气
🛠  行动: query_weather({'code': 'BJ'})
👀 观察: 晴天
───── Step 3 ─────
🤔 思考: 我已经拿到结果，可以直接回答用户
✅ 完成: 今天北京晴天

📝 最终答案: 今天北京晴天

核心循环就 3 步：

  1. 思考（LLM 决策）
  2. 行动（调用工具）
  3. 观察（工具结果回填到记忆）

下一轮再循环，直到模型说 "FINISH"。

这个最小例子里的"假 LLM"在真实工程中换成 GPT-4 / Claude / DeepSeek 即可，其他部分完全不变。这是几乎所有 Agent 框架（LangChain、LangGraph、AutoGen、CrewAI）底层共同的模式。

1.7.1 这段代码里学到的工程模式

仔细看这段 60 行的最小 Agent，其实已经包含了所有真实 Agent 框架的几个核心工程模式：

  1. JSON Schema 化的输出——LLM 每次 think 返回 {"thought", "action", "action_input"} 的结构化 JSON，而不是一段自由文本。真实工程中你应该用 response_format={"type": "json_schema", ...} 强制约束输出格式（OpenAI 和 Anthropic 都支持）。
  2. 显式的工具注册表——TOOLS: dict[str, Callable]。这就是 LangChain 的 @tool 装饰器、OpenAI Agents SDK 的 function_tool 在做的事——把 Python 函数包装成 LLM 能看到的"工具描述"。
  3. 轨迹记录（trace）——self.history 这个 list 记录了所有"思考-行动-观察"三元组。LangSmith、Langfuse 这些可观测性平台干的就是把这个 list 持久化、可视化、可回放。
  4. 最大步数保护——max_steps=10。生产环境绝对必须有，否则 Agent 死循环能把你的 token 账单刷爆。
  5. 结束条件——action == "FINISH"。这是一个特殊动作名，不是任何工具。所有 Agent 框架都需要一个明确的"结束信号"——OpenAI 用 transfer_to_human、LangGraph 用 END 节点。

1.8 Agent 能做什么、不能做什么

讲完了"是什么"，我们来现实一点：Agent 现在到底能干什么、不能干什么。

1.8.1 Agent 擅长的场景

  1. 开放性研究任务——"调研 2025 年 Agent 框架的对比"，模型自己规划搜索、阅读、整合。
  2. 跨系统协调——"帮我在 Notion 里总结上周客户反馈、然后同步到 Slack #product 频道"。
  3. 重复性文案/数据处理——"把这 200 份简历按候选人经验分类"。
  4. 代码相关——代码生成、单元测试、Bug 修复、PR Review。
  5. 个人助理——订餐、查邮件、安排日程、订机票。
  6. GUI 操作（Computer Use）——代替人点鼠标。

一个有趣的统计：截至 2026 年初，GitHub 上 top 100 的 Agent 仓库，70%+ 都是"研究/调研"类——这反映了 LLM 在"理解并综合多源信息"上的强项。代码生成、自动化操作类增长最快。

1.8.2 Agent 还不擅长的场景

  1. 需要 100% 准确性的场景——医疗诊断、金融下单（Agent 只能做"建议"和"预审"）。
  2. 超长链条推理（>50 步）——容易在中间环节出错或遗忘早期状态。
  3. 强实时性——多步工具调用累积延迟无法避免。
  4. 复杂物理操作——抓杯子、修水管还得靠机器人。
  5. 新颖创造——Agent 在"组合已知"上很强，在"创造全新范式"上和人类顶尖还有差距。

1.8.3 一个有用的判断框架

接到一个任务时，问自己三个问题：

  1. 这个任务是否能被分解成 3-30 步的子任务？ 如果不能（比如"想出一个全新的物理定律"），Agent 不适合。
  2. 每一步子任务是否能用现有工具完成？ 如果不能（"让 Agent 学会读心术"），Agent 不适合。
  3. 每一步是否需要判断和决策？ 如果是纯机械重复（"把 100 张图片缩放到 800x600"），传统脚本更省 token。

三个问题答案都是"是"——这个任务就适合交给 Agent。

1.9 2024-2026 Agent 爆发的三大推力

为什么是 2024-2026 这三年 Agent 集中爆发？我们认为是三大推力同时到位。

1.9.1 推力一：模型推理能力质变

2024 年，OpenAI o1 把"思维链推理"做成了产品级能力；2025 年的 o3、DeepSeek-R1、Claude 3.7 Sonnet 进一步把"在脑子里多转几圈"变成日常能力。

之前的 GPT-4 在多步推理上会"走神"——做到第 5 步忘了第 1 步的目标。o 系列模型出现后，Agent 的"长链决策"才真正稳定。

一个具体数据：在 SWE-bench（衡量 Agent 修复真实 GitHub Issue 能力的基准）上，2023 年的 Agent 解决率不到 5%，2024 年底达到 20%+，2025 年 o3 模型上达到 70%+。这不是 Agent 框架的进步，是底层模型推理能力的跃迁。

1.9.2 推力二：Function Calling 标准化

2023 年 6 月 OpenAI 在 GPT-4 中加入 function calling；2024 年 Anthropic 在 Claude 中加入 tool use；2024 年 11 月 MCP（Model Context Protocol）发布，统一了"模型和外部工具对话"的协议。

这意味着：

  • 之前：每个 Agent 框架自己造一套工具调用协议，互相不兼容。
  • 现在：写一个 MCP server，所有兼容 MCP 的客户端都能用。

标准化让 Agent 生态在 2025-2026 年像当年 npm 一样爆发。

MCP 的关键意义在于它和 2014 年的 HTTP、2017 年的 gRPC 类似——是"协议级"的标准化。一旦协议被采纳，所有工具开发者只需要写一份 MCP server，所有 Agent 客户端立刻就能用。Anthropic 把它类比为"AI 时代的 USB-C 接口"，这个比喻不夸张。第 12 章我们会深入 MCP 协议本身。

1.9.3 推力三：框架与可观测性成熟

2024-2025 年，LangChain、LangGraph、AutoGen、CrewAI、Agno、OpenAI Agents SDK 等框架相继稳定；同时 LangSmith、Langfuse、AgentOps 等可观测性平台成熟。

这意味着：

  • 之前：写一个 Agent，跑到第 3 步崩了，你不知道为什么。
  • 现在：每一步的 prompt、token 用量、工具调用、耗时、错误全程可回放。

可观测性是 Agent 从"能跑"走向"能上生产"的关键拼图。

一个业内共识：2024 年 90% 的 Agent 失败案例都是因为"不知道哪里错了"。LangSmith、Langfuse 把这一步变成可回放的 trace 之后，调试时间从平均 4 小时降到 30 分钟。第 22 章会专门讲 Agent 可观测性。

本章小结

  1. 定义：Agent 是 LLM + 工具 + 记忆 + 规划组成的、能自主决策的系统。Anthropic、OpenAI、Google 三家口径略有不同但核心一致。
  2. 五大特征：自主性、目标驱动、工具使用、记忆、规划。
  3. 与 LLM 区别：LLM 是大脑，Agent 是"大脑 + 手 + 记忆 + 规划"组成的完整人。
  4. 与 Chatbot 区别：Chatbot 是"对话"，Agent 是"完成任务"。
  5. 与 Workflow 区别：Workflow 路径写死，Agent 路径由 LLM 现场决定。
  6. 最小可运行 Agent：核心循环是"思考 → 行动 → 观察 → 思考 → ... → 完成"。
  7. 能力边界：Agent 擅长"3-30 步、可分解、需判断"的任务，不擅长需要 100% 准确或超长链条的场景。
  8. 爆发原因：模型推理能力 + 工具调用协议标准化 + 可观测性成熟。
