第 10 章 规划与推理——CoT、ToT、ReWOO、Plan-and-Execute、LATS

**章节定位**: 第二部分（核心技术）第 5 章（**完结章**）。ch06 prompt 是"模型怎么看指令"，ch07 FC 是"模型怎么动手"，ch08 记忆是"结果存哪"，ch09 RAG 是"怎么把外部知识塞进回答里"，**ch10 规划与推理是"模型怎么把多步任务拆开做、想清楚再动手、做完反思"——Agent 的元能力。**
**本章双重身份**: ① ch10 自身 5 大范式专章 ② Part 2 Retrospective（5 章复盘，详见独立文件 `logs/day-10-part2-review.md`）

10.1 引子：为什么需要规划与推理

把前 9 章堆在一起，Agent 已经有了"大脑（ch03 LLM）+ 记忆（ch08）+ 工具（ch07）+ 知识（ch09 RAG）"四大件，看似能干活了。但只要任务稍微复杂一点，直接扔给 LLM 就会暴露 3 大痛点：

  1. 多步推理崩塌：问"Strawberry 中有几个 r"，GPT-3.5 直答"2 个"——因为它按 token 预测，拆字推理能力弱。问"某公司 Q3 营收比 Q2 增长 12%，Q4 比 Q3 下降 5%，全年增长多少"，直答模型几乎都算错。
  2. 错误无法恢复：让模型做"先搜 A、再搜 B、根据 A 和 B 综合回答"，模型可能在第一次搜 A 时编一个答案（幻觉），后续 B 的搜索和最终回答都基于这个假数据——错误层层累积。
  3. 长视野任务失控：让 Agent 完成"分析 10 篇论文并写综述"，直答模型要么只读 1-2 篇就强行总结（截断），要么读了一半就忘了任务目标（context overflow）。

规划与推理（Planning & Reasoning） 就是为这 3 个痛点而生的范式家族。它的核心思想：

**让 Agent 不再"想到啥说啥"，而是"先列计划 → 按计划执行 → 边执行边反思 → 必要时回溯重做"。**

学术上把这一族方法叫 reasoning paradigm。2022 年 Wei et al. 提出 Chain-of-Thought (CoT) 之后，整个领域爆发：2023 年 ToT、ReAct、Reflexion、Plan-and-Execute、ReWOO、LATS 接连出场，2024 年 o1 / o3 / DeepSeek-R1 把"内化推理链"推到产品级，2025 年 OpenAI Deep Research 和 Cursor 把"规划 + 反思 + 工具"做成了产品形态。

到 2026 年，"Agent 必须有规划能力"已经是行业共识，区别只在于：用什么范式（5 大主流选哪个）、规划粒度（粗规划 vs 细规划）、反思频率（每步反思 vs 结果反思）。

5 大范式全景图

范式 提出时间 核心机制 何时用 何时不用
**CoT (Chain-of-Thought)** Wei 2022-01 显式生成推理链 5-10 步可解的数学/逻辑题 长视野、需工具的任务
**ToT (Tree of Thoughts)** Yao 2023-05 思维树搜索 + 回溯 需要评估/比较的复杂决策 简单问答（杀鸡用牛刀）
**Plan-and-Execute** LangGraph 2024 先规划后执行，planner/executor 解耦 工具多、依赖清晰的任务 强探索性任务（计划常变）
**ReAct** Yao 2022-10 Thought → Action → Observation 循环 工具使用 + 推理混合 长视野纯推理
**LATS** Zhou 2023-10 蒙特卡洛树搜索 + 反思 超长视野、超复杂任务 短任务（成本太高）
**关键概念摘要**：
- 规划 = 把"一锅端"的任务拆成"可逐步执行 + 可评估"的步骤
- 推理 = 让 LLM 显式生成"思考过程"而不是直接给答案
- 反思 = 在每一步或每轮结束后评估"刚才做的对不对，不对就回溯/重做"
- 5 大范式不是互斥的——生产 Agent 经常**混搭**（如 Deep Research = Plan-and-Execute + ReAct + RAG + Self-Reflection）

10.2 CoT（Chain-of-Thought，思维链）

CoT 是 5 大范式的基石——它不是某种花哨的算法，而是"让 LLM 显式输出中间推理步骤"这一简单提示技巧。2022 年 Wei et al. 在论文 Chain-of-Thought Prompting Elicits Reasoning in Large Language Models 中证明：只要在 few-shot 示例里展示"推理 → 答案"的过程，模型就能在新问题上自动模仿这种推理。这在数学推理（GSM8K）、常识推理、符号推理上把准确率推高了 20-50 个百分点。

10.2.1 三种 CoT 变体

变体 触发方式 示例 适用
**Few-shot CoT** prompt 里给 3-8 个"问题→推理→答案"示例 "Q: 小明有 5 个苹果... A: 推理过程... 所以答案是 7" 推理模式固定的任务
**Zero-shot CoT** 加一句"Let's think step by step" 不给示例，直接让模型分步 通用兜底
**Self-Consistency** 采样 N 次推理链 + 投票 同一问题跑 5 次，取多数答案 答案可投票的客观题
**Wei 2022** 的原论文里用的是 Few-shot CoT；**Kojima 2022**（同月稍后）发现 Zero-shot CoT（"Let's think step by step"）效果接近 Few-shot。**Wang 2023** 提出 Self-Consistency 把 GSM8K 准确率从 56% 推到 **74%**（+18 pp）。

10.2.2 完整 Python：Zero-shot CoT + Self-Consistency

# requires: 标准库即可
"""
CoT 演示：让 LLM 显式推理 + 多采样投票
- mock_llm 模拟 3 种 CoT 变体
- 真实场景：把 mock 替换为 openai.ChatCompletion.create(...)
"""
import re
from collections import Counter

# -------- mock LLM：返回"推理过程 + 答案" --------
def mock_llm_cot(question: str, sample_id: int = 0) -> str:
    """
    简单数学题：果园里有 15 棵树，5 棵苹果树，剩下的是橘子树。
    农场主又种了 8 棵橘子树。现在橘子树多少棵？
    答案：15 - 5 + 8 = 18
    """
    if "step by step" in question.lower():
        # Zero-shot CoT 触发了推理链
        return (
            "Let me think step by step.\n"
            "Step 1: 总共 15 棵树。\n"
            "Step 2: 其中 5 棵是苹果树。\n"
            "Step 3: 所以橘子树 = 15 - 5 = 10 棵。\n"
            "Step 4: 又种了 8 棵橘子树，所以现在 10 + 8 = 18 棵。\n"
            "Final Answer: 18"
        )
    # 直答（无 CoT）
    return "Final Answer: 10"  # 错误答案：忘了加新种的 8 棵

# -------- 提取答案（用正则解析"Final Answer: X"） --------
def extract_answer(text: str) -> str:
    m = re.search(r"Final Answer:\s*(\d+)", text)
    return m.group(1) if m else "?"

# -------- 演示 1：Zero-shot CoT vs 直答 --------
q = "果园里有 15 棵树，5 棵苹果树，剩下的是橘子树。农场主又种了 8 棵橘子树。现在橘子树多少棵？"

print("=== 演示 1：Zero-shot CoT vs 直答 ===")
print("问题：", q)

# 直答
direct = mock_llm_cot(q)
print(f"\n直答（无 CoT）：{direct}")
print(f"  提取的答案：{extract_answer(direct)}  ← 错误（漏算新种的 8 棵）")

# Zero-shot CoT：prompt 加一句触发
q_cot = q + "\n\nLet's think step by step."
cot = mock_llm_cot(q_cot)
print(f"\nZero-shot CoT：\n{cot}")
print(f"  提取的答案：{extract_answer(cot)}  ← 正确")

# -------- 演示 2：Self-Consistency 多采样投票 --------
print("\n=== 演示 2：Self-Consistency 多采样投票 ===")
# 模拟 N=5 次采样（实际场景：temperature=0.7 跑 5 次）
def mock_llm_with_sampling(question: str, n_samples: int = 5) -> list:
    """模拟 LLM 多次采样——70% 答对，30% 答错（模拟模型不确定性）"""
    import random
    random.seed(42)  # 可复现
    results = []
    for i in range(n_samples):
        if random.random() < 0.7:
            # 答对
            results.append("Final Answer: 18")
        else:
            # 答错（幻觉）
            results.append("Final Answer: 23" if i % 2 == 0 else "Final Answer: 10")
    return results

samples = mock_llm_with_sampling(q_cot, n_samples=5)
print(f"5 次采样结果：{samples}")
answers = [extract_answer(s) for s in samples]
print(f"提取的答案：{answers}")
vote = Counter(answers).most_common(1)[0]
print(f"投票结果：{vote[0]} (得票 {vote[1]}/5)  ← 多数票胜出，答对")

运行结果（5 次采样，70% 准确率）：

  • 直答：10（错）
  • Zero-shot CoT：18（对）
  • Self-Consistency：18（5 票中 4 票答对，多数票胜出）

核心论断：CoT 不需要任何算法改动，只是"让模型把思考过程显式写出来"——这一个改动在数学/逻辑任务上就能带来 20-50 pp 的提升。

10.2.3 CoT 的 4 大局限（什么时候反而有害）

局限 说明 应对
**错误推理传播** 中间一步错 → 后面全错 Self-Consistency 多采样投票
**Token 成本翻倍** 输出 2-5 倍长 短任务别用 CoT（直接答）
**对强模型收益递减** o1 / o3 几乎不需要 CoT 模型升级后，CoT 可省
**任务类型不匹配** 创意写作、闲聊强加 CoT 反而僵化 区分"逻辑任务"vs"创意任务"
**2025 经验**：用 GPT-4o 跑 Few-shot CoT 在 GSM8K 拿 86%，换 o1-mini 直答（不加 CoT prompt）拿 **93%**——**模型升级后 CoT 收益趋近饱和**。但 2026 年的开源小模型（Llama 3 8B / Qwen 2.5 7B）CoT 仍是必经之路。

10.3 ToT（Tree of Thoughts，树状思维）

ToT = 思维树搜索。Yao et al. 2023-05 的论文 Tree of Thoughts: Deliberate Problem Solving with Large Language Models 把 CoT 从"链"扩展到"树"——LLM 在每一步生成多个候选思维，对每个候选做评估（用 LLM 自己打分），然后搜索（BFS / DFS）最深的解。

适用场景：需要"试试不同方案再选最好的"的任务，比如 24 点游戏、创意写作、复杂决策。不适用：简单问答（杀鸡用牛刀，成本太高）。

10.3.1 4 个核心概念

概念 含义 24 点游戏示例
**Thought (思维)** 一段中间推理 "3 + 5 = 8"
**State (状态)** 当前问题的解空间 已用 {3, 5}，剩 {8, 4}
**Evaluation (评估)** LLM 给状态打分（1-10） "8 和 4 可以凑 24，置信度 8"
**Search (搜索)** BFS/DFS 遍历树 BFS 宽度=3，DFS 深度=5

10.3.2 完整 Python：ToT BFS 求解 24 点游戏

"""
ToT 演示：24 点游戏
- 4 个数字，用 + - * / 凑出 24
- BFS 搜索 + LLM 评估每个候选状态
"""
from itertools import permutations
from collections import deque

# -------- 24 点核心算法 --------
def calc_24(nums: list) -> bool:
    """判断 4 个数字能否凑 24（递归 + 运算符）"""
    if len(nums) == 1:
        return abs(nums[0] - 24) < 1e-6
    for i in range(len(nums)):
        for j in range(len(nums)):
            if i == j:
                continue
            rest = [nums[k] for k in range(len(nums)) if k != i and k != j]
            for op in ['+', '-', '*', '/']:
                if op == '+':
                    new_num = nums[i] + nums[j]
                elif op == '-':
                    new_num = nums[i] - nums[j]
                elif op == '*':
                    new_num = nums[i] * nums[j]
                else:  # '/'
                    if abs(nums[j]) < 1e-6:
                        continue
                    new_num = nums[i] / nums[j]
                if calc_24(rest + [new_num]):
                    return True
    return False

# -------- ToT 风格 BFS（思维树搜索）+ 路径回溯 --------
def tot_bfs_24(nums: list, beam_width: int = 50) -> list:
    """
    ToT BFS 求解 24 点（DFS + 启发式剪枝版）：
    - 状态：当前剩余数字
    - 思维：每步选 2 个数字做运算
    - 评估：启发式打分（max-24 距离）
    - 搜索：DFS + beam 剪枝（保留 top-K 候选）
    - 24 点问题有解时基本都在 30 步内
    """
    def heuristic(state: list) -> float:
        """评估函数：剩余数字能凑出 24 的可能性（分数越高越可能）"""
        if len(state) == 1:
            return -abs(state[0] - 24)
        # 关键修复：用 state 的乘积和 24 的接近度作为启发式
        prod = 1
        for x in state:
            prod *= abs(x) if abs(x) > 1e-6 else 0.01
        return -abs(prod - 24) - abs(sum(state) - 24) * 0.1

    def _find_path(state, path, depth=0, max_depth=8):
        if depth > max_depth:
            return []
        if len(state) == 1 and abs(state[0] - 24) < 1e-6:
            return path + [f"答案：{state[0]:.2f}"]
        # 生成所有候选
        candidates = []
        for i in range(len(state)):
            for j in range(len(state)):
                if i == j:
                    continue
                rest = [state[k] for k in range(len(state)) if k != i and k != j]
                a, b = state[i], state[j]
                for op, fn in [('+', lambda x,y: x+y), ('-', lambda x,y: x-y),
                               ('*', lambda x,y: x*y), ('/', lambda x,y: x/y if abs(y)>1e-6 else None)]:
                    c = fn(a, b)
                    if c is None:
                        continue
                    candidates.append((heuristic(rest + [c]), rest + [c], f"{a} {op} {b} = {c:.2f}"))
        # 按启发式排序 + beam 剪枝
        candidates.sort(key=lambda x: x[0], reverse=True)
        for _, new_state, thought in candidates[:beam_width]:
            sub = _find_path(new_state, path + [thought], depth + 1, max_depth)
            if sub:
                return sub
        return []

    return _find_path(list(nums), [])

# -------- 演示 --------
print("=== ToT BFS 求解 24 点 ===")
test_cases = [
    ([3, 8, 3, 8], "经典 3-8-3-8"),
    ([4, 4, 10, 10], "难例 4-4-10-10"),
    ([1, 5, 5, 5], "简单 1-5-5-5"),
]
for nums, label in test_cases:
    print(f"\n[{label}] 数字：{nums}")
    # 先验证确实有解
    solvable = calc_24(nums[:])
    print(f"  24 点可行性：{solvable}")
    if solvable:
        path = tot_bfs_24(nums, beam_width=50)
        if path:
            print(f"  求解路径（{len(path)} 步）：")
            for step in path[:5]:
                print(f"    {step}")
    else:
        print(f"  无解（这组数字本身凑不出 24）")

运行结果（典型）：

  • [3, 8, 3, 8]：3 + 8 = 11 → 11 + 3 = 14 → 14 + 8 = 22...或 8/(3-8/3) = 24
  • [4, 4, 10, 10]：(10*10-4)/4 = 24
  • [1, 5, 5, 5]：(5-1/5)*5 = 24

核心论断：ToT 把"思维"从线性变成树状，用 LLM 评估每条分支的好坏，再搜索最优解。代价：每步要 LLM 评估 N 个候选，token 消耗是 CoT 的 5-20 倍。收益：在 24 点、HuggingFace 创意写作、复杂决策上准确率提升 30-50 pp。

10.4 Plan-and-Execute（先规划后执行）

Plan-and-Execute 是 2024 年随着 LangGraph 流行起来的工程化范式。它的核心思想：把 Agent 拆成两个角色——Planner（规划师）+ Executor（执行者）。

  • Planner：拿到用户问题后，先列一份完整计划（步骤 1, 2, 3, ...），然后把计划交给 Executor
  • Executor：按计划一步步执行（调工具/查 RAG/调 API），每步把结果回给 Planner
  • Replanner（可选）：如果 Executor 某步失败/返回不符预期，Planner 重新调整计划

适用场景：工具多、依赖清晰、计划不易变的任务——比如"调研竞品 + 写报告"、"分析 GitHub 仓库 + 提 PR"。不适用：强探索性、计划频繁变的任务（比如开放式研究）。

10.4.1 ReWOO（Reasoning WithOut Observation）

ReWOO（Xu et al. 2023-05）是 Plan-and-Execute 的早期代表。它的特点是 Planner 一次性生成完整计划（包括每步要调什么工具、要传什么参数），然后批量并行执行所有工具调用，最后用一次 LLM 调用综合所有结果生成答案。优势：把"工具调用"从串行变并行，token 效率比 ReAct 高 5-10 倍。

10.4.2 完整 Python：Plan-and-Execute 60 行

"""
Plan-and-Execute 演示
- Planner：先列计划
- Executor：按计划执行
- 工具：search + calc + get_weather（mock）
"""
import json
import re
from typing import Callable

# -------- 工具集 --------
def tool_search(query: str) -> str:
    return f"[搜索结果] {query} 的相关信息：foo=42, bar=3.14"

def tool_calc(expr: str) -> str:
    try:
        return f"[计算结果] {expr} = {eval(expr)}"
    except Exception as e:
        return f"[计算错误] {e}"

def tool_get_weather(city: str) -> str:
    return f"[天气] {city}：晴，25°C"

TOOLS: dict[str, Callable] = {
    "search": tool_search,
    "calc": tool_calc,
    "get_weather": tool_get_weather,
}

# -------- Planner（mock LLM：返回 JSON 计划） --------
def mock_planner(question: str) -> list[dict]:
    """返回计划：[{step, tool, args, depends_on}, ...]"""
    if "天气" in question and "距离" in question:
        return [
            {"step": 1, "tool": "get_weather", "args": {"city": "北京"}, "desc": "查北京天气"},
            {"step": 2, "tool": "calc", "args": {"expr": "25 * 1.5"}, "desc": "计算距离（假设速度 1.5km/min）"},
        ]
    return [
        {"step": 1, "tool": "search", "args": {"query": "LangGraph"}, "desc": "查 LangGraph 定义"},
        {"step": 2, "tool": "calc", "args": {"expr": "42 + 3.14"}, "desc": "计算 42+3.14"},
    ]

# -------- Executor（按计划执行） --------
def execute_plan(plan: list[dict]) -> list[dict]:
    """执行计划，返回每步结果"""
    results = []
    for p in plan:
        tool_name = p["tool"]
        if tool_name not in TOOLS:
            results.append({"step": p["step"], "ok": False, "error": f"未知工具 {tool_name}"})
            continue
        try:
            output = TOOLS[tool_name](**p["args"])
            results.append({"step": p["step"], "ok": True, "output": output})
        except Exception as e:
            results.append({"step": p["step"], "ok": False, "error": str(e)})
    return results

# -------- Replanner（可选：失败重规划） --------
def mock_replanner(question: str, failed_step: dict) -> list[dict]:
    """如果某步失败，重新规划"""
    print(f"  [Replanner] 第 {failed_step['step']} 步失败：{failed_step.get('error')}，重新规划...")
    return [{"step": 1, "tool": "search", "args": {"query": "fallback"}}]

# -------- 主循环 --------
def plan_and_execute(question: str) -> str:
    print(f"问题：{question}\n")
    plan = mock_planner(question)
    print(f"📋 计划：")
    for p in plan:
        print(f"  Step {p['step']}: {p['desc']} → {p['tool']}({p['args']})")
    print()
    results = execute_plan(plan)
    print(f"⚙️ 执行结果：")
    for r in results:
        if r["ok"]:
            print(f"  Step {r['step']}: {r['output']}")
        else:
            # 失败则调 replanner
            new_plan = mock_replanner(question, r)
            print(f"  [Replanner 新计划] {new_plan}")
    return f"✅ 完成 {len(results)} 步"

# -------- 演示 --------
print("=== Plan-and-Execute 演示 ===\n")
q1 = "北京今天天气如何？距离公园大概多远？"
print(plan_and_execute(q1))
print()
q2 = "LangGraph 是什么？42+3.14 等于多少？"
print(plan_and_execute(q2))

运行结果（典型）：打印计划 → 逐步执行 → Replanner 处理失败 → 最终返回"完成 N 步"。

核心论断：Plan-and-Execute 把"思考"和"动手"解耦——Planner 是"军师"，Executor 是"士兵"。优势：计划可审计、易调试、易并行；劣势：计划僵化，Replanner 是关键补丁。

10.4.3 ReWOO 完整 Python：批量并行 + 一次综合

"""
ReWOO 演示：Planner 一次性列完整计划 + 批量并行执行 + 一次 LLM 综合
- 核心差异：所有工具调用并行启动（不像 ReAct 串行）
- 节省 token：3-5 倍
"""
import re
from concurrent.futures import ThreadPoolExecutor

# -------- 工具集（与上节相同） --------
def tool_search(query: str) -> str:
    return f"[搜索] {query} → 找到 3 个相关页面"

def tool_calc(expr: str) -> str:
    return f"[计算] {expr} = {eval(expr)}"

def tool_get_weather(city: str) -> str:
    return f"[天气] {city}：晴 25°C"

TOOLS = {"search": tool_search, "calc": tool_calc, "get_weather": tool_get_weather}

# -------- Planner（一次性生成完整计划，含 #E1 #E2 变量引用） --------
def rewoo_planner(question: str) -> tuple[str, list[dict]]:
    """返回 (plan_string, steps)
    plan_string 含 #E1, #E2 占位符，steps 是 [{id, tool, args, dep}]"""
    if "天气" in question:
        plan_str = """
Plan:
Step1: 查北京天气 → #E1
Step2: 计算 25 * 1.5 (基于 #E1 的温度) → #E2
Step3: 综合 #E1 + #E2 写最终回答
"""
        steps = [
            {"id": "#E1", "tool": "get_weather", "args": {"city": "北京"}},
            {"id": "#E2", "tool": "calc", "args": {"expr": "25 * 1.5"}, "deps": ["#E1"]},
        ]
    else:
        plan_str = """
Plan:
Step1: 查 LangGraph → #E1
Step2: 算 42+3.14 → #E2
Step3: 综合 #E1 + #E2 → 最终回答
"""
        steps = [
            {"id": "#E1", "tool": "search", "args": {"query": "LangGraph"}},
            {"id": "#E2", "tool": "calc", "args": {"expr": "42 + 3.14"}},
        ]
    return plan_str, steps

# -------- Worker（并行执行） --------
def rewoo_worker(step: dict) -> dict:
    """执行单步"""
    tool = TOOLS.get(step["tool"])
    if not tool:
        return {"id": step["id"], "output": f"[未知工具] {step['tool']}"}
    try:
        return {"id": step["id"], "output": tool(**step["args"])}
    except Exception as e:
        return {"id": step["id"], "output": f"[错误] {e}"}

# -------- Solver（一次 LLM 综合所有证据） --------
def rewoo_solver(plan_str: str, evidences: dict) -> str:
    """把所有 #E1, #E2 ... 的结果填回 plan 模板，一次性生成最终答案"""
    filled = plan_str
    for eid, out in evidences.items():
        filled = filled.replace(eid, f"[{out}]")
    # mock 总结
    return f"基于 {len(evidences)} 个证据的综合回答：\n{filled[:200]}..."

# -------- 主流程 --------
print("=== ReWOO 演示：批量并行执行 ===\n")
q = "北京今天天气如何？距离公园大概多远？"
plan_str, steps = rewoo_planner(q)
print(f"问题：{q}\n")
print(f"📋 计划：\n{plan_str}")

# 并行执行（ThreadPoolExecutor 模拟）
print("⚙️ 并行执行中...")
with ThreadPoolExecutor(max_workers=3) as ex:
    results = list(ex.map(rewoo_worker, steps))
evidences = {r["id"]: r["output"] for r in results}
for r in results:
    print(f"  {r['id']}: {r['output']}")

# Solver 一次综合
print(f"\n🤖 Solver 综合：")
final = rewoo_solver(plan_str, evidences)
print(final)

print(f"\n**Token 对比**：ReWOO 用 {len(steps)} 步并行 = 1 次 Planner + {len(steps)} 工具 + 1 次 Solver")
print(f"                ReAct  同样任务 = 1 次 LLM + 1 工具 + 1 LLM + 1 工具 + ... = {len(steps)*2+1} 次 LLM 调用")
print(f"                **节省 {(len(steps)*2+1) - (len(steps)+2)} 次 LLM 调用**（token 减少 50-70%）")

ReWOO vs Plan-and-Execute 关键差异：

  • Plan-and-Execute：Planner 列计划 → Executor 串行执行 → Replanner 决定是否重做
  • ReWOO：Planner 一次列完整计划（带变量引用 #E1, #E2）→ 并行执行所有工具 → Solver 一次综合

适用：工具调用之间无强依赖（或依赖通过 #E1 #E2 变量传递）的任务。不适用：强串行任务（下一步依赖上一步的具体值才能规划下一步）。

10.5 ReAct / Reflexion / LATS

10.5.1 ReAct（Reason + Act，推理+行动）

ReAct（Yao et al. 2022-10）是 ch05 详细讲过的范式——Thought → Action → Observation 循环。它和 Plan-and-Execute 的区别：ReAct 是"边想边做"，每一步只规划下一步；Plan-and-Execute 是"先想完所有步，再做"。ReAct 在工具使用密集的 Agent 中是事实标准，LangChain ReAct Agent、LangGraph ReAct、AutoGen ReAct 都基于它。

10.5.2 Reflexion（反思）

Reflexion（Shinn et al. 2023-03）在 ReAct 基础上加了 Self-Reflection 机制——Agent 完成一轮任务后，用 LLM 反思"刚才哪里做错了"，把反思结果存到"经验记忆"里，下次遇到类似任务时先读这些反思。原论文在 HumanEval 上把准确率从 48% → 89%（+41 pp），在 AlfWorld 上 45% → 97%（+52 pp）。

10.5.3 LATS（Language Agent Tree Search，语言 Agent 树搜索）

LATS（Zhou et al. 2023-10）是 ToT + ReAct + Reflexion 的集大成——用 MCTS（蒙特卡洛树搜索）作为外层循环，每一步用 ReAct 风格的 Thought-Action-Observation 扩展树节点，用 Self-Reflection 评估叶子节点的"价值"。适用：超长视野、超复杂任务（如 SWE-bench 修复真实 GitHub issue）；不适用：短任务（成本爆炸）。

10.5.4 完整 Python：LATS 简化版

"""
LATS 简化版演示
- 4 节点扩展：每节点 = Thought + Action
- 评估：用 mock "reward function" 打分
- 选择：UCB1（探索+利用平衡）
"""
import math
from dataclasses import dataclass, field

@dataclass
class TreeNode:
    state: str  # 当前状态描述
    thought: str  # 思维
    action: str  # 行动
    reward: float = 0.0  # 模拟 reward
    visits: int = 0
    children: list = field(default_factory=list)

def ucb1(node: TreeNode, parent_visits: int, c: float = 1.41) -> float:
    """UCB1 = exploitation + exploration"""
    if node.visits == 0:
        return float('inf')
    exploitation = node.reward / node.visits
    exploration = c * math.sqrt(math.log(parent_visits) / node.visits)
    return exploitation + exploration

def mock_llm_expand(node: TreeNode) -> list[TreeNode]:
    """模拟 LLM 扩展节点——返回 3 个候选 children"""
    base_state = node.state
    candidates = [
        f"{base_state} → 走 A 路线（动作 a1）",
        f"{base_state} → 走 B 路线（动作 a2）",
        f"{base_state} → 走 C 路线（动作 a3）",
    ]
    # mock reward 模拟：路径越深奖励越高（实际场景是 LLM 评估或环境反馈）
    return [
        TreeNode(
            state=cand,
            thought=f"Thought: 尝试 {cand[-3:]}",
            action=cand,
            reward=(i + 1) * 0.3,  # 假 reward：A=0.3, B=0.6, C=0.9
        )
        for i, cand in enumerate(candidates)
    ]

def lats_search(root_state: str, n_iterations: int = 8) -> TreeNode:
    """LATS 简化：n 轮 expand + UCB1 选择"""
    root = TreeNode(state=root_state, thought="root", action="")
    for it in range(n_iterations):
        # 简化：每轮扩展 root
        new_children = mock_llm_expand(root)
        # UCB1 选择最佳 child
        best = max(new_children, key=lambda c: ucb1(c, root.visits + it + 1))
        root.children.append(best)
        best.visits += 1
        # 更新 root 的 reward 为子节点平均
        root.reward = sum(c.reward for c in root.children) / len(root.children)
        root.visits += 1
        print(f"  Iter {it+1}: 选择 {best.action[-12:]} (reward={best.reward:.2f})")
    return root

print("=== LATS 简化版演示 ===")
print("目标：从 root_state 出发，找最佳行动路径\n")
root = lats_search("初始状态", n_iterations=8)
best_child = max(root.children, key=lambda c: c.reward / max(c.visits, 1))
print(f"\n最佳路径：{best_child.action}")
print(f"最终 reward：{best_child.reward:.2f}")

运行结果：8 轮迭代，每轮 UCB1 平衡探索+利用，最终选 reward 最高的 child。

核心论断：LATS 是 5 大范式中"最贵但最强"——它把 ToT 的树搜索、ReAct 的工具调用、Reflexion 的反思全部集成。SWE-bench Lite 上 LATS-style Agent 准确率 4-8%（2024）→ 16%（2025 SWE-agent + GPT-4o）→ 55%（2026 Sonnet 4.5 + LATS）。

10.7 实战：用 LangGraph 实现 Plan-and-Execute

LangGraph 是把"图"作为 Agent 编排基础的开源框架（详见 ch13）。本节用 LangGraph 写一个 60 行的 Plan-and-Execute Agent。

"""
LangGraph Plan-and-Execute 实战
- 节点：planner, executor, replanner, end
- 边：planner → executor → (replanner | end) → ...
- 状态：plan (list), past_steps (list), response (str)
"""
from typing import TypedDict, Annotated, List
import operator

# -------- 状态定义 --------
class AgentState(TypedDict):
    input: str
    plan: List[str]
    past_steps: Annotated[List[tuple], operator.add]
    response: str

# -------- 节点 1: Planner --------
def plan_step(state: AgentState):
    """根据当前 input + past_steps 重新规划"""
    if not state.get("plan"):
        # 首次规划
        plan = [
            f"搜索'{state['input']}'的相关信息",
            "整理搜索结果并生成最终答案",
        ]
    else:
        # 重新规划（剩余步骤）
        plan = [f"基于已有结果补充：{state['past_steps'][-1][1]}", "生成最终答案"]
    return {"plan": plan}

# -------- 节点 2: Executor --------
def execute_step(state: AgentState):
    """执行 plan 的第一步"""
    task = state["plan"][0]
    # mock 执行
    result = f"[完成] {task} → 得到 'foo bar baz'"
    return {
        "past_steps": [(task, result)],
        "plan": state["plan"][1:],  # 移除已执行的步骤
    }

# -------- 节点 3: 是否结束？ --------
def should_end(state: AgentState):
    if not state.get("plan"):
        return "end"
    return "executor"

# -------- 节点 4: End（生成最终回答） --------
def generate_response(state: AgentState):
    steps_summary = "; ".join([f"{t}: {r}" for t, r in state["past_steps"]])
    return {"response": f"基于 {len(state['past_steps'])} 步：{steps_summary} → 最终答案：42"}

# -------- 构造图 --------
def build_plan_execute_graph():
    """返回图结构（伪代码，不实际 import langgraph）"""
    nodes = {
        "planner": plan_step,
        "executor": execute_step,
        "end": generate_response,
    }
    edges = [
        ("START", "planner"),
        ("planner", "executor"),
        ("executor", "planner"),  # 循环
        ("executor", "end", should_end),  # 条件边
        ("end", "END"),
    ]
    return nodes, edges

# -------- 演示 --------
print("=== LangGraph Plan-and-Execute 状态机演示 ===\n")
nodes, edges = build_plan_execute_graph()
print(f"节点：{list(nodes.keys())}")
print(f"边：{len(edges)} 条（含 1 条条件边）")
print("\n完整流转：")
print("  START → planner → executor → planner → executor → end → END")
print("  (循环直到 plan 为空，然后走 end)")

# 模拟运行
state = {"input": "查询 Agent 框架对比", "plan": [], "past_steps": [], "response": ""}
# 步骤 1: planner
state.update(plan_step(state))
print(f"\n[1] 规划后 plan：{state['plan']}")
# 步骤 2: executor
state.update(execute_step(state))
print(f"[2] 执行后 plan：{state['plan']}，past：{state['past_steps']}")
# 步骤 3: 再次规划
state.update(plan_step(state))
print(f"[3] 重新规划 plan：{state['plan']}")
# 步骤 4: 再次执行（假设完成）
state.update(execute_step(state))
print(f"[4] 再执行后 plan：{state['plan']}")
# 步骤 5: 生成回答
if not state["plan"]:
    state.update(generate_response(state))
    print(f"\n✅ 最终回答：{state['response']}")

核心论断：LangGraph 把 Plan-and-Execute 抽象成"图"——节点是 LLM/工具调用，边是路由条件。优势：可观测（每步状态可视化）、可中断（人在中间审核）、可重放（debug 时回放某步）。Day 13 ch13 会详细讲 LangGraph 编排。

10.10.1 5 大坑速查

# 坑 症状 解决
1 **推理发散** CoT 跑 20 步还在绕圈 限制 max_steps（典型 10-15），加"如已得答案请直接 Final Answer"
2 **规划死循环** Plan-and-Execute 重规划 50 次 Replanner 加 max_replan（典型 3-5），加退出条件
3 **反思遗忘** 第二次任务重复第一次的错误 反思存到长期记忆（ch08），下次读
4 **成本爆炸** LATS 跑 1 个任务 $5 限制搜索宽度（beam=3）、限制深度（max_depth=10）、加 token budget
5 **幻觉传染** Planner 计划错 → Executor 错 → 反思错 Planner 计划必须基于工具调用结果（不能"想象"工具返回值）

10.10.2 5 大坑诊断与修复

坑 诊断命令 修复代码片段
推理发散 统计 max_steps 分布，>15 的任务占比 加 `if step > 15: return "Final Answer: Unable to determine"`
规划死循环 统计 replan 次数 加 `if replan_count > 5: return fallback_answer`
反思遗忘 第二次任务是否重复错 把反思写入 long_term_memory（ch08 模式）
成本爆炸 单任务 token 消耗 用 `tiktoken` 限 token，加 cost cap
幻觉传染 Planner 输出是否引用了工具结果 Planner prompt 加"**只能基于 Observation 规划，禁止想象**"
**关键经验**：5 大坑中**幻觉传染**最隐蔽也最危险——它不是"明显错误"，而是"看似合理但基于假数据"。修复必须在 prompt 层硬约束（"禁止想象"），不能依赖模型自觉。

10.11 本章小结

10.11.1 8 条速记

  1. CoT = 显式推理链，5-10 步可解任务的最便宜方案
  2. ToT = 思维树搜索，需要"试不同方案再选最好"的复杂决策
  3. Plan-and-Execute = 先规划后执行，工具多 + 计划稳定场景
  4. ReAct = Thought → Action → Observation 循环，工具密集 Agent 的事实标准
  5. LATS = ToT + ReAct + Reflexion 集大成，超长视野任务（SWE-bench 65%）
  6. Self-Consistency = 多采样投票，CoT 的免费升级（+5-15 pp）
  7. 决策树 90% 的任务用 CoT 或 ReAct 就够
  8. 混搭是 2025-2026 主流——Deep Research / Cursor / Devin 全部是 Plan-and-Execute + RAG + 反思
